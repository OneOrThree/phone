팀원 작업 지시 티켓 생성: **$ARGUMENTS**

## 이 커맨드가 만드는 것

받는 사람이 **되물을 필요 없이 바로 착수할 수 있는 지시서**다.
지시서는 아래 8가지를 전부 갖춘다 — 하나라도 비면 만들지 않는다.

| 요소 | 어디에 들어가나 |
| --- | --- |
| 목표 | 본문 `🎯 목표` |
| 완료 조건 | 본문 `✅ 완료 조건` (체크박스) |
| 참고 자료 | 본문 `📎 참고 자료` |
| 산출물 유형 · 결과물 남길 위치 | 본문 `📦 산출물` |
| 예상 작업 시간 | 본문 `⏱ 예상 작업 시간` + Story point 환산 |
| 담당자 | `담당자` 필드 |
| 마감 | `기한` 필드 |
| 스프린트 | `스프린트` 필드 — **기본으로 현재 활성 스프린트** |

`도메인` 은 규약상 필수라 여기에 더해 반드시 채운다 (`docs/conventions/jira-conventions.md`).

## 실행 흐름

### 1. 인자 파싱
`$ARGUMENTS` 에서 시킬 일(자유 서술)과 플래그를 뽑는다.

- `--assignee <이름>` · `--due <YYYY-MM-DD>` · `--label <값>` · `--epic <GROMO-###>`
- `--no-sprint` → 스프린트에 넣지 않는다 (백로그로만)
- 일이 여러 건이면 티켓도 여러 건으로 나눈다. **한 티켓 = 한 사람이 끝까지 끌고 갈 수 있는 한 덩어리.**

인자가 비면 중단하고 무슨 일을 시킬지 물어본다.

### 2. 메타데이터 조회 — 분류보다 먼저
```bash
python3 .claude/jira_assign.py meta
```
`도메인` 옵션 · 배정 가능 인원 · **활성 스프린트(id·종료일)** · 열린 릴리스 · 열린 에픽을 준다.

**여기서 조회하는 이유**: 옵션도 인원도 스프린트도 계속 바뀐다.
스프린트 id 는 매주 넘어가므로 **절대 하드코딩하지 않는다.**
분류는 반드시 이 출력 안의 값으로만 한다.

### 3. 맥락 조사 — 참고 자료를 실제로 확보한다
"참고 자료: 알아서 찾아보세요" 는 지시가 아니다. 시킬 일과 관련된 것을 직접 찾아 링크로 박는다.

- 관련 PRD·정책 문서: `docs/prd/<기능>/`, `docs/conventions/`
- 따라야 할 기존 코드 패턴: 같은 도메인의 `api/`·`service/`·`domain/` 중 **비슷한 것 한 개를 지목**
- 선행 티켓·PR 이 있으면 `GROMO-####` / PR 번호
- 스키마가 걸리면 `server/data-api/docs/db/schema.dbml`

**경로는 실제로 존재하는지 확인하고 적는다.** 없는 경로를 참고 자료로 주면 지시가 무너진다.

### 4. 빠진 것 질의
8요소 중 인자·조사로 채워지지 않은 것만 `AskUserQuestion` 으로 **한 번에 묶어** 묻는다
(한 개씩 여러 턴에 걸쳐 묻지 않는다). 전형적으로 비는 것:

- **담당자** — 2단계에서 받은 실제 인원 목록을 선택지로 준다
- **예상 작업 시간** — `30m` · `4h` · `1d` · `2.5d` 형식
- **산출물 유형** — PR · 문서 · 조사 리포트 · 디자인 시안 · 설정 변경 등
- **결과물 남길 위치** — 어느 레포에 PR / 어느 경로에 문서 / 어느 지라 코멘트

마감은 안 주면 **활성 스프린트 종료일**로 잡는다 — 물을 필요 없다.
도메인·라벨은 일의 내용에서 추론하고, 애매할 때만 묻는다.

### 5. 완료 조건 쓰는 법
받는 사람이 **자기 손으로 체크할 수 있는 관찰 가능한 항목**으로 쓴다.

| ❌ 이렇게 쓰지 않는다 | ✅ 이렇게 쓴다 |
| --- | --- |
| 잘 동작하게 한다 | `POST /api/groups/{id}/invite` 가 201 + 링크를 반환한다 |
| 테스트 추가 | 만료 링크 재사용 시 409 를 검증하는 테스트가 있다 |
| 문서화 | `docs/prd/invite/policy.md` 에 만료 정책 D 항목이 추가돼 있다 |

3~6개가 적당하다. 10개를 넘으면 티켓을 쪼갤 때다.

### 6. 목록 제시 → 승인
표로 보여주고 승인을 받는다. **승인 전에는 생성하지 않는다.**

```
📋 생성 예정 (스프린트: SCRUM Sprint 13, 종료 2026-09-14)
──────────────────────────────────────────────────────────
 1. 초대 링크 만료 정책 적용        안수빈 · 그룹 · BE · 마감 09-14 · 4h(2sp)
    산출물: PR → server/data-api  |  완료 조건 4개  |  참고 3건
 2. 초대 화면 만료 안내 문구 추가    권태화 · 그룹 · App · 마감 09-14 · 2h(1sp)
    산출물: PR → app/app-dev      |  완료 조건 3개  |  참고 2건
──────────────────────────────────────────────────────────
전체 생성할까요? ("전부" / "1만" / "2 제외" / "취소")
```

### 7. 생성
승인분만 payload 로 만들어 실행한다. payload 스키마는 `.claude/jira_assign.py` 상단 docstring 에 있다.

```bash
cat > "$SCRATCH/assign.json" <<'JSON'
{ "sprint": true, "tickets": [ ... ] }
JSON
python3 .claude/jira_assign.py create "$SCRATCH/assign.json"
```

- payload 는 스크래치패드에 쓴다. 레포에 남기지 않는다.
- 확신이 안 서면 `--dry-run` 을 먼저 붙여 필드 해석 결과만 본다.
- 스크립트가 막아주는 것: 알 수 없는 필드(오타) · 필수 필드 누락 · 없는 도메인 ·
  모호한 담당자 이름 · 대괄호 접두 · **같은 제목의 미완료 티켓(중복 지시)**.
  중복 경고가 정당한 재발주면 `--allow-dup` 을 붙인다.

### 8. 결과 보고
생성된 키와 담당자·마감을 한 줄씩 보고하고 보드 링크를 준다.
팀원에게 따로 알릴 필요가 있으면 그때 알린다 — 이 커맨드는 지라까지만 한다.

## 규약 (어기면 티켓이 조회에서 샌다)

- summary 에 `[그룹]` · `[BE]` · `[BUG]` 같은 **대괄호 접두를 붙이지 않는다.** 에픽만의 특권이다.
- `도메인` 은 **작업당 정확히 하나.** 활동(qa·chore·refactor)은 도메인이 아니라 라벨이다.
- 에픽은 **지금 굴러가는 시한부 덩어리의 일부일 때만** 붙인다. 아니면 비운다.
- 스토리 포인트는 예상 시간에서 자동 환산된다 (`≤2h`=1 · `≤5h`=2 · `≤8h`=3 · `≤3d`=5 · 그 이상=8).
  직접 주려면 payload 에 `story_points` 를 넣는다.

정본: `docs/conventions/jira-conventions.md`
