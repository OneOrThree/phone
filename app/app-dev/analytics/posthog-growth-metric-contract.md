# 섬 성장·경제·집중 장소 대시보드 지표 계약

작성일: 2026-10-21. 대상: Catus 조직의 프로젝트 `669473`.

**2026-10-21 PostHog MCP로 카드 8개를 게시하고 재조회·실행했습니다.** [섬 성장과 경제](https://us.posthog.com/project/669473/dashboard/2236458)에 6개, [첫 섬과 집중](https://us.posthog.com/project/669473/dashboard/2220995)의 기존 마지막 행 뒤에 2개를 추가했습니다. 모든 새 카드 제목·설명에 미계측 상태를 표시했습니다. 기존 카드 8개의 ID·쿼리·레이아웃·안내문, 대시보드 필터 및 프로젝트 테스트 계정 제외 설정을 보존했습니다.

게시 정의는 `posthog-growth-dashboard.json`, `posthog-focus-location-additions.json`에 원격 ID·URL·쿼리·레이아웃과 함께 기록했고 두 `.pending.json`을 대체했습니다. `posthog-growth-publication-verification.json`에는 검증 결과와 합성 표본 SQL을 기록했습니다. 실제 Catus에서 8개 SQL과 저장된 인사이트를 실행하고 대시보드 강제 재실행까지 확인했으며 모두 빈 결과입니다. Data Catalog에는 일치하는 승인 지표가 없어 이 계약은 아직 승인된 카탈로그 정의가 아닙니다.

필수 이벤트 4종은 최근 30일 수집 목록과 이벤트 조회에서 확인되지 않았습니다. 대시보드 게시와 앱·서버 계측 구현·배포는 별도 상태이며, 이 작업에서 이벤트나 앱의 동작을 변경하지 않았습니다. 빈 결과는 실제 0을 뜻하지 않습니다. 합성 CTE 표본으로 중복 제거·취소·갱신 지연·미완료 NULL·실제 잔액 0·미분류 거래·장소 시간 합계 오류 제외를 검증했지만, 실제 수신 표본·원장·완료 기록의 대조와 서버 사건에 대한 프로젝트 제외 필터의 포함 여부는 계측 배포 후 검증해야 합니다. 합성 표본은 이벤트로 수집하지 않았습니다.

실행 과정에서 날짜 변환과 미지원 조건부 분위수 함수의 호환성 오류를 수정했습니다. `quantileExact(if(..., value, NULL))`로 완공 표본만 집계하며, 건설 관측에는 세 구간 시간 합계 검증과 관측 시각 하한을 추가했습니다. `{filters}`와 `filterTestAccounts=true`는 모든 게시 쿼리에 유지했습니다.

## 배치와 읽는 방법

새 **Catus · 섬 성장과 경제** 대시보드:

| 카드                             | 답하려는 질문                                           | 집계 단위                                       |
| -------------------------------- | ------------------------------------------------------- | ----------------------------------------------- |
| 건물별 건설 진행 상황            | 목표를 고른 뒤 준비·공사·완공 중 어디에 있나?           | 건설 목표 선택 시도. 취소·변경 포함             |
| 건물을 짓는 데 걸린 시간         | 자원 준비, 착수 대기, 실제 공사 중 무엇이 오래 걸리나?  | 완공 시도별 시간. 미완료·취소 표본 수 함께 표시 |
| 건설이 어디서 기다리고 있을까    | 잔액 부족인가, 주민 몫 부족인가, 조건 충족 후 대기인가? | 최근 상태를 확인한 미완료 목표                  |
| 매일 들어오고 나간 물고기        | 공동 통장에 쌓이는 양과 쓰는 양이 균형적인가?           | 확정 거래의 입금·출금·순증감                    |
| 물고기는 어디서 벌고 어디에 쓸까 | 집중·퀘스트 보상과 건설·상점 소비의 규모는?             | 거래 원인별 금액·거래 수·섬 수                  |
| 섬 통장에는 얼마나 남아 있을까   | 물고기가 쌓이거나 바닥나는 섬이 많은가?                 | 섬마다 최신 잔액 한 건                          |

기존 **Catus · 첫 섬과 집중**(`2220995`)의 마지막에 추가:

| 카드                         | 답하려는 질문                                   | 집계 단위                                     |
| ---------------------------- | ----------------------------------------------- | --------------------------------------------- |
| 섬과 바다 중 어디서 집중할까 | 실제 집중시간과 이용자가 어느 장소에 많은가?    | 완료 세션의 장소별 유효 집중시간, 고유 사용자 |

표본이 없는 결과는 빈 결과 또는 NULL로 둡니다. 원인을 모르거나 누락된 값을 실제 잔액 0·집중시간 0으로 치환하지 않습니다. 카드 제목·설명은 짧게 유지하고, 아래 구현 계약은 대시보드 본문에 넣지 않습니다.

## 정책·코드 근거

- [건설 정책](../../../docs/prd/fishcat/island-construction/policy.md): 회관·게시판 이후 일부 건물의 순서는 자유입니다. 건물별로 비교하며 고정 7단계 순서 퍼널로 만들지 않습니다. 목표 변경은 별도 epoch이고 주민 몫 조건과 섬 총잔액 조건은 다릅니다. 착수는 방장의 명령, 완공은 서버 확정입니다.
- [집중·보상 정책](../../../docs/prd/fishcat/focus-rest-session/policy.md): 물고기는 섬 공동 통장에 적립됩니다. 집중 보상은 분 단위 적립이므로 `focus_completed.earned_fish`의 합을 전체 입금 원장으로 쓰지 않습니다. 보상 일일 한도의 UTC 경계를 변경하지 않습니다.
- [현재 집중 이벤트](../src/services/sessionCommands.ts): `focus_completed`에는 `duration_seconds`, `earned_fish`만 있으며 실제 장소별 시간이 없습니다. 소속 섬 유무·화면 노출 시간을 집중 장소·유효 시간으로 대신 쓰지 않습니다.
- [상점 주문](../../../server/data-api/src/main/java/com/oneorthree/phone/shop/repository/domain/ShopOrder.java): 주문 ID와 거래 직후 잔액, `analyticsDeliveredAt`가 있습니다. 이는 전달 의도를 보관하는 근거이며 현재 PostHog로 전송된다는 증거는 아닙니다. 서버 구현 시 기존 의도와 중복 발행하지 않도록 통합해야 합니다.

## 공통 계약 — 구현 예정

새 이벤트의 이름·속성은 이 준비안의 계약입니다. 기존 서버 API에 이 필드들이 이미 있다는 뜻이 아닙니다.

- `metrics_schema_version=1`, `analytics_environment=production|development`.
- 날짜별 집계는 한국 시간, 오늘 포함 최근 28일입니다. 오늘 값은 진행 중입니다. SQL에 기간이 고정돼 있으므로 게시할 때 카드 설명을 유지합니다.
- `timestamp`는 관측 또는 거래·완료가 실제 확정된 시각입니다. 전송 재시도로 발생 시각을 바꾸지 않습니다.
- 서버 집계는 `island_id` 단위입니다. 주민 수만큼 동일 거래·스냅샷을 복제하지 않습니다. 안정적인 사건 ID로 내구 전달하고 재시도는 같은 사건 ID·원본 내용을 사용합니다. 단순 화면 방문 때만 발행하면 돌아오지 않는 섬이 빠지므로 서버에서 전수 수집해야 합니다.
- 서버 사건에는 `analytics_excluded=0|1`이 필수입니다. 테스트 섬은 1로 표시하고 쿼리는 명시적 0만 포함합니다. 개인의 내부 계정 필터만으로 서버의 섬 단위 사건이 제외된다고 가정하지 않습니다. 혼합 주민 섬의 포함 여부는 섬의 명시적 분류를 따릅니다.
- 기존 프로젝트의 내부·테스트 계정 제외를 보존합니다. 모든 SQL은 `{filters}`와 `filterTestAccounts=true`를 사용합니다. 최종 게시 전 프로젝트 필터가 서버 사건을 의도대로 포함하는지 확인해야 합니다.
- 조회 실패·미확인 필드는 `null`/누락입니다. 숫자 0은 서버에서 확인한 실제 0에만 사용합니다. 섬 이름·주민 이름·이메일·집중 과목은 필요하지 않습니다.

## 건설: `island_construction_observed`

필수 속성:

| 속성                      | 의미                                                                      |
| ------------------------- | ------------------------------------------------------------------------- |
| `island_id`, `attempt_id` | 섬과 목표 선택 epoch의 안정적인 식별자. 같은 건물을 다시 선택해도 새 시도 |
| `building_id`             | `hall`, `board`, `gram`, `library`, `mail`, `tower`, `shop`               |
| `observation_version`     | 시도 안에서 단조 증가하는 관측 버전. 동일 버전 재전송은 동일 내용         |
| `selected_at_ms`          | 해당 시도의 실제 목표 선택 시각, Unix 밀리초                              |
| `stage`                   | 아래 6개 중 하나                                                          |
| `saving_seconds`          | 잔액 또는 주민 몫 조건이 부족했던 누적 초                                 |
| `ready_wait_seconds`      | 조건은 모두 충족됐으나 착수하지 않은 누적 초                              |
| `build_seconds`           | 착수 후 서버 완공 확정까지의 누적 초. 미완료는 관측 시점까지              |
| `elapsed_seconds`         | 목표 선택부터 관측 또는 종결까지의 전체 경과 초                           |

단계는 `waiting_balance`(섬 잔액 부족), `waiting_contribution`(잔액 충족·주민 몫 부족), `ready`(착수 가능), `building`, `completed`, `cancelled`입니다. 잔액·주민 몫이 모두 부족하면 `waiting_balance`로 분류합니다. 권한에 따라 UI 버튼이 비활성화된 것을 자원 부족으로 분류하지 않습니다.

상태 전환 시와 진행 중 매일 최소 한 번 관측하고, 취소·변경·섬 종료 시 마지막 상태도 보존합니다. 준비 조건이 충족됐다가 소비나 주민 변경으로 다시 부족해질 수 있으므로 최초 ready 시각 하나로 시간을 계산하지 않습니다. 각 상태에 머문 구간을 합산하며, 세 시간 합계는 전체 경과와 일치해야 합니다. 선택 취소·변경은 이전 시도를 닫고 새 시도를 시작합니다. 서버 완공 이전의 클라이언트 타이머 만료로 completed를 발행하지 않습니다.

쿼리는 최근 28일에 선택한 시도마다 **가장 높은 관측 버전의 동일 스냅샷 전체**를 사용합니다. 같은 섬의 복수 시도가 존재하므로 시도 수와 섬 수를 구분합니다. 취소를 삭제하거나 분모에서 숨기지 않습니다.

속도 카드는 완공한 시도의 분포입니다. 미완료를 시간 0으로 넣지 않고 건수로 함께 표시하며, 전체 시도의 예상 완공시간이나 목표 선택 후 7일 전환율로 해석하지 않습니다. 최근 시작한 시도는 관찰 기간이 짧으므로 건물 간 인과 비교에도 쓰지 않습니다. 미완료 상태가 24시간 넘게 갱신되지 않으면 진행 상황 카드에서 갱신 지연 수로 표시하고, 현재 대기 원인 카드에서는 제외합니다.

## 공동 통장 거래: `island_currency_transaction`

- `island_id`, `transaction_id`, `amount_delta`, `reason`이 필수입니다.
- `amount_delta`는 실제 원장에 확정된 부호 있는 물고기 증감입니다. 입금 양수·출금 음수, 목표 선택·실패 요청·중복 재시도는 거래를 만들지 않습니다.
- `reason`: `focus`, `quest`, `construction`, `shop`, `refund`, `adjustment`. 새 원인이 생겨도 총액에서 버리지 않고 미분류로 보여줍니다.
- 동일 거래는 섬·거래 ID로 중복 제거합니다. 정정은 기존 사건의 금액을 덮어쓰지 않고 별도 원장 거래로 기록합니다. 원장 확정과 분석 전달 의도를 같은 트랜잭션에 남기고 재시도합니다.
- 집중 분당 적립과 퀘스트를 각각 기록합니다. 집중 종료 때 같은 보상을 추가 입금으로 발행하지 않습니다. 건설·구매 역시 실제 차감 확정마다 한 번만 기록합니다.
- 날짜는 원장 거래의 효력 시각을 사용합니다. 지연 전송·밀린 집중 틱을 전송일 거래로 바꾸지 않습니다.
- 입출금이 없는 날짜는 현 준비 쿼리에서 행이 없습니다. 수집 정상 여부를 확인하기 전 빈 날짜를 자동 0으로 채우지 않습니다.

## 통장 상태: `island_wallet_snapshot`

- `island_id`, `wallet_version`, `balance`가 필수입니다. `balance`는 음수가 아닌 실제 공동 통장 잔액입니다.
- 운영 중인 모든 섬을 적어도 매일 한 번 관측합니다. 앱에 들어온 섬·거래한 섬만 수집하면 안 됩니다. 잔액이 0인 섬과 조용한 섬도 포함합니다.
- 최근 24시간 관측 중 섬마다 가장 높은 wallet version을 사용합니다. 같은 버전이면 최신 관측을 택합니다. 같은 버전의 잔액은 같아야 합니다.
- 누락·오래된 관측은 잔액 0으로 대체하지 않습니다. 카드는 관측 섬 수를 표시하며, 완전성 검증 전 그 합을 서비스 전체 잔액으로 부르지 않습니다.
- 거래 원장으로 기초 잔액 + 순증감 = 기말 잔액을 대조해야 합니다. 이벤트 수신 성공만으로 경제 집계가 완전하다고 판단하지 않습니다.

## 집중 장소: `focus_location_summary`

- `record_id`, `duration_seconds`, `island_seconds`, `sea_seconds`, `unknown_seconds`가 필수입니다. 기존 앱 사용자 식별자를 사용합니다.
- 서버가 확정한 실제 완료 세션의 기록 ID와 총 유효 집중초가 기준입니다. 안내용 체험·휴식 시간은 제외합니다.
- 장소가 바뀌면 해당 구간을 나눕니다. 세 장소 초의 합은 서버의 `duration_seconds`와 같아야 합니다. 총시간·부분시간이 음수이거나 합계가 맞지 않으면 검증 실패로 분리합니다.
- 실제 장소가 확인된 유효 집중 구간만 섬·바다로 분류합니다. 크래시·다른 기기 복구 등으로 구간을 복원할 수 없으면 `unknown_seconds`로 남깁니다. 정상 백그라운드 집중을 자동으로 미확인으로 만들 필요는 없지만, 경과시간만으로 장소를 추측해서도 안 됩니다.
