# 실시간 차단 필터 dev 검증 — GROMO-2182

실시간 차단 필터(티켓 2182, PR #1059)를 dev 에서 켜고 검증하는 시나리오와 결과 기록이다.
필터는 **기본 OFF 스위치 두 개** 뒤에 배포된다. 이 문서의 시나리오를 모두 통과해야 스위치를 켠 상태로 확정하고,
그 뒤 후속 PR 에서 스위치를 제거한다(항상 켜짐).

결정 근거: `docs/prd/fishcat/decision-log.md` RP-실시간차단필터 · `docs/prd/fishcat/realtime-events/low-level-design.md` §4.3.

## 대상 동작

- Realtime 은 **받는 세션 기준**으로, 받는 사람이 차단한 사용자가 보낸 섬·그룹 채팅과 응원(emote) MESSAGE 를 그 세션에 보내지 않는다.
  한 방향이다 — 차단당한 쪽은 차단한 사람의 메시지를 그대로 받는다.
- 차단 집합은 Realtime Redis 에 캐시한다(`cache:chat:block:{userId}`, TTL 120초는 백스톱). Data 가 차단·해제 트랜잭션에서
  `user.blocks.updated` 를 REALTIME outbox 로 적고, Realtime 이 받으면 차단 세대(`cache:chat:blockgen:{userId}`)를 올려 캐시를 즉시 무효화한다.
- 차단 집합 조회 실패·timeout·비정상 응답이면 **전달하지 않는다(fail-closed)**.

## 스위치와 켜는 순서

| 순서 | 대상 | 설정 | 기본 |
| --- | --- | --- | --- |
| 0 | 공통 | Realtime→Data 서비스 토큰 `SVC_TOKEN_REALTIME_TO_DATA` · `REALTIME_AUTHORIZATION_DATA_URL` · Data `realtime-authorization` 프로필 배선(티켓 2160 과 같은 배선) | 미배선 |
| 1 | Data | `USER_BLOCKS_REALTIME_EVENTS_ENABLED=true` (`user-blocks.realtime-events-enabled`) — 차단 변경 사건 생산 | false |
| 2 | Realtime | `REALTIME_BLOCKS_FILTER_ENABLED=true` (`realtime.blocks.filter-enabled`) — 전송 직전 필터 | false |

- 0 이 dev 에 반영되기 전에 2 를 켜면 차단 집합 조회가 모두 실패해 **모든 채팅·응원이 막힌다**(fail-closed). 반드시 0 → 1 → 2 순서.
- 2 만 켜고 1 이 꺼져 있으면 차단 변경은 캐시 TTL(최대 120초) 뒤에야 반영된다 — 즉시 차단이 아니다.
- 되돌리기: 2 → 1 순서로 false 로 돌리고 해당 서비스를 재배포한다.

## 시나리오

### QA-RB-01 한 방향 차단

1. A·B·C 가 같은 섬 채팅(또는 집중 중 응원) 화면을 연다.
2. A 가 B 를 차단한다.
3. B 가 채팅을 보내고 응원을 보낸다.
4. A 가 채팅을 보내고 응원을 보낸다.

기대 결과:

- A 화면에 B 의 채팅·응원이 도착하지 않는다.
- B 화면에는 A 의 채팅·응원이 그대로 도착한다.
- C 화면에는 A·B 의 채팅·응원이 모두 도착한다.

### QA-RB-02 즉시 반영

1. 차단 직후(수 초 안) B 가 채팅을 보낸다.
2. A 가 B 차단을 해제하고, 직후 B 가 채팅을 보낸다.

기대 결과:

- 차단 직후 첫 메시지부터 A 에게 도착하지 않는다(120초를 기다리지 않는다).
- 해제 직후 메시지부터 A 에게 다시 도착한다.
- Realtime 로그에 `user.blocks.updated` 수신과 세대 증가가 남는다.

### QA-RB-03 차단 없는 사용자의 정상 동작

1. 차단 관계가 없는 사용자끼리 채팅·응원을 10회 이상 주고받는다.
2. 스위치를 켜기 전과 메시지 도착 여부·지연을 비교한다.

기대 결과:

- 모든 메시지가 도착한다(누락 0).
- Realtime 로그에 차단 집합 조회 실패·timeout 이 없다.
- 체감 지연이 켜기 전과 같다.

### QA-RB-04 Data 장애와 자동 복구

1. 채팅 중 dev data-api 컨테이너를 재시작한다.
2. 재시작 동안과 재시작 뒤에 채팅을 보낸다.

기대 결과:

- Data 가 내려간 동안 캐시가 없는 사용자의 메시지는 전달되지 않을 수 있다(fail-closed, 의도된 동작).
- Data 가 올라온 뒤 별도 조치 없이 채팅·응원이 정상 전달된다(계속 막힌 채로 남지 않는다).

### QA-RB-05 부하

1. 사용자 5명 이상이 한 섬에서 1분간 채팅·응원을 연속으로 보낸다. `loadtest/` 에는 아직 STOMP 채팅 시나리오가 없다 —
   API·STOMP 스크립트로 보내거나, 필요하면 k6 WebSocket 시나리오를 먼저 추가한다.
2. Realtime→Data 차단 집합 조회 횟수(Realtime 로그·Data 접근 로그)와 메시지 지연을 본다.

기대 결과:

- 조회가 메시지마다 나가지 않는다(캐시 적중).
- 메시지 지연이 스위치를 켜기 전과 유의미한 차이가 없다.

### QA-RB-06 배포 순서

1. Realtime 만 재배포하고 채팅·차단을 확인한다.
2. Data 만 재배포하고 채팅·차단을 확인한다.

기대 결과:

- 어느 쪽을 따로 재배포해도 오류가 쌓이지 않고, 재배포 뒤 QA-RB-01·02 결과가 유지된다.
