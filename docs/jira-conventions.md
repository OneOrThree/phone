# 지라 규약 — 4축 분리

GROMO 지라(`romance.atlassian.net`, 프로젝트 키 `GROMO`)에서 티켓을 어떻게 분류하고
이름 붙이는지에 대한 정본이다. 2026-08-09 전면 재편으로 확정했다.

## 왜 4축인가

재편 전에는 **성격이 다른 두 축이 에픽 필드 하나에 섞여** 있었다.

- 영구 버킷형 에픽: `그룹 기능`(자식 45) · `[Stats] 통계` · `Production 환경`
  → 안 닫히니 계속 비대해진다
- 시한부 작업형 에픽: `TT 포커스 모드` · `기획 심의` · `콜드 메일`
  → 닫히니 후속 작업이 갈 곳을 잃는다

그 결과 비에픽 티켓의 **64%가 에픽 없이** 떠 있었고, `온보딩`이 닫히자
`[Onboarding] 온보딩 플로우`가 새로 생기는 식으로 같은 도메인의 에픽이 세대별로 쌓였다.

축을 넷으로 나누면 이 문제가 구조적으로 사라진다.

| 축 | 필드 | 닫히나 | 답하는 질문 |
| --- | --- | --- | --- |
| **도메인** | Component | ❌ 영원히 안 닫힘 | "그룹 관련 전부" |
| **플랫폼** | Label | ❌ 영원히 안 닫힘 | "iOS 할 일" |
| **이니셔티브** | **Epic** | ✅ 끝나면 닫는다 | "지금 무엇을 하는 중" |
| **출시** | fixVersion | ✅ 릴리스로 끊는다 | "다음 출시에 뭐가 나가나" |

### 기능을 디벨롭하면 에픽은 어떻게 되나

**새 에픽을 만든다.** 컴포넌트가 그대로라 도메인 조회는 안 깨지고,
에픽 목록이 그 도메인의 **연혁**이 된다.

```
Component: 챌린지·내기        (영원히 안 닫힘 — 도메인 조회의 앵커)
 ├ Epic [챌린지·내기] 챌린지 v0 — 초기 API
 ├ Epic [챌린지·내기] 챌린지·내기 v1 — 에스크로 · 정산 엔진      ✅ 닫힘
 ├ Epic [챌린지·내기] 용어 정비 · 참여 흐름 하드닝               ✅ 닫힘
 └ Epic [챌린지·내기] 챌린지 재구축 (웨이브 1~4)                🔵 진행중
```

## 1. Component — 도메인 (필수)

**모든 티켓에 정확히 하나.** 에픽에는 붙이지 않는다(에픽 이름의 `[...]`가 그 역할).

| 제품 도메인 | 엔지니어링 | 비즈니스 |
| --- | --- | --- |
| 그룹 · 챌린지·내기 · 집중세션 | 인프라·배포 · QA | 마케팅·그로스 |
| 리그 · 통계 · 스크린타임 | 개발환경·워크플로 · 관측·분석 | 기획·리서치 |
| 인증·계정 · 온보딩 · 설정 | 데이터·스키마 · 디자인 시스템 | |
| 캐릭터·상점 · 친구 · 알림·푸시 | | |

권위 있는 목록은 지라 프로젝트 설정의 컴포넌트 화면이다. 위 표는 스냅샷이라 낡을 수 있다.

**경계가 헷갈릴 때**
- 그룹 ↔ 챌린지·내기 — 챌린지·회차·내기·참가비·정산·판정은 **챌린지·내기**.
  그룹 생성·검색·공지·멤버·초대 링크는 **그룹**.
- 컴포넌트를 새로 만들기 전에 자문한다: **앞으로도 티켓이 계속 생기는 도메인인가?**
  아니라면 그건 컴포넌트가 아니라 에픽이다.

## 2. Label — 플랫폼과 성격 (해당될 때만)

플랫폼: `iOS` · `Android` · `BE` · `App`(프론트) · `Infra`
성격: `chore` · `refactor` · `wave2` 같은 배치 표식

**도메인을 라벨로 넣지 않는다.** 그건 컴포넌트의 일이다.

## 3. Epic — 시한부 이니셔티브

### 이름
```
[<컴포넌트>] <이니셔티브 이름>
예) [챌린지·내기] 챌린지 재구축 (웨이브 1~4)
    [인프라·배포] prod 환경 구축 · 심사 준비
```

### 규칙
- **시작과 끝이 있는 작업 덩어리**에만 만든다. 끝나면 **닫는다**.
- 도메인 이름(`그룹`, `통계`)을 에픽 이름으로 쓰지 않는다 — 컴포넌트와 역할이 겹친다.
- **모든 티켓이 에픽에 속할 필요는 없다.** 단발 버그·잡무는 컴포넌트 + 릴리스로 충분하다.
  억지로 묶으면 다시 버킷형 에픽이 생긴다.
- 에픽 하나가 30~40건을 넘어가면 쪼갤 때가 된 것이다.

### 계층
지라 FREE·팀관리형이라 계층은 **3단**이고 에픽 위로는 없다.

```
에픽 (1)          ← 시한부 이니셔티브
 └ 작업·버그 (0)   ← Component · Label · fixVersion 이 붙는 층
    └ Subtask (-1) ← parent 가 이미 작업이라 에픽에 직접 못 붙는다
```

Subtask는 **에픽에 붙이지 않는다**(붙이면 부모-자식 관계가 깨진다).
컴포넌트·fixVersion은 부모 작업과 같은 값을 준다.
2026-07 이후 신규 사용이 없으니, 새로 만들 일이 있으면 그냥 작업으로 만드는 편이 낫다.

## 4. fixVersion — 출시

- **완료 티켓은 반드시 버전을 갖는다.** 어느 릴리스로 나갔는지가 이력이다.
- **미완료 티켓은 비워도 된다.** 어느 릴리스에 실을지는 아직 결정이 아니다.
- 릴리스가 끝나면 `released` 로 끊는다.
- ⚠️ **버전을 archive 하지 않는다.** archived 버전에는 이슈를 할당할 수 없고
  (`400 — 보관되었으므로 해당 버전에 이슈를 할당할 수 없습니다`),
  릴리스 페이지에서도 숨겨져 `released` 마킹이 무의미해진다.

## 5. Summary — 대괄호는 에픽만

```
에픽    [챌린지·내기] 챌린지 재구축
작업    챌린지 삭제 시 OPEN 회차 무효화 + 전원 환불
        Component=챌린지·내기 · Label=BE · Epic=[챌린지·내기] 챌린지 재구축
```

작업·버그 summary에는 `[Group]` · `[BE]` · `[BUG]` 같은 접두를 **붙이지 않는다.**
그 정보는 전부 다른 필드에 있다. `[BUG]`는 이슈타입이 이미 말해준다.

## 신규 티켓 체크리스트

- [ ] Component 하나 (필수)
- [ ] Label — 플랫폼이 명확하면
- [ ] Epic — **지금 굴러가는 덩어리 작업의 일부라면.** 아니면 비워둔다
- [ ] summary에 대괄호 접두 없음
- [ ] 완료 처리할 때 fixVersion 확인

## 자주 쓰는 JQL

```sql
component = "챌린지·내기" AND statusCategory != Done   -- 이 도메인에서 지금 굴리는 것
component = "그룹"                                     -- 그룹 관련 전부 (과거 + 현재)
component = "리그" AND labels = BE                     -- 리그 백엔드
parent = "GROMO-####"                                  -- 특정 이니셔티브
fixVersion = 1.0.1                                     -- 다음 출시분
component IS EMPTY AND issuetype != Epic               -- 규약 위반 — 주워담아야 할 것
```

마지막 쿼리는 **정기적으로 확인한다.** 결과가 0이 아니면 누군가 컴포넌트 없이 티켓을 만든 것이다.
