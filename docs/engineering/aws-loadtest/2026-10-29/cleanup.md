추가 부하의 400개와 앞선 사전 시험의 10개, **총 410개 더미 계정**을 물리 삭제했다. 추가 부하 400개 계정의 소유 데이터는 2026-10-29 03:35 UTC에 운영 Data·Chat·Notification DB에서 물리 삭제했다. 약 125초 뒤 독립 재조회에서 삭제 대상의 재생성은 없었다. Redis의 남은 시험 키 10개도 제거했다. 아래 숫자는 이번 400개 계정의 정확한 생성 목록을 기준으로 한다.

## 탈퇴와 물리 삭제의 차이

일반 탈퇴는 계정을 비활성화하고 집중·통계를 익명화한다. 또한 연결·실시간·점수 서비스에 탈퇴 사실을 보내는 후처리 이벤트를 만든다. 앞선 보고의 `LINK·REALTIME·SCORE 각 400건 pending`은 이 전달이 남았다는 뜻이었다.

이번에는 사용자 요청에 따라 해당 더미만 별도 물리 정리했다. 후처리 대기 행을 정상 전달로 위장하지 않고, 더미의 실제 서비스 데이터를 지운 뒤 관련 이벤트와 전달 이력을 제거했다. 탈퇴 1,200건 외에도 같은 시험에서 발생한 LINK 전달 대기 440건이 있었으며, 총 1,640개 대기 행이 삭제 범위에 포함됐다. 운영 후처리 장애가 해결되거나 배포됐다는 뜻은 아니다.

## 소유 범위를 확인한 방법

- 생성 목록의 사용자 400개·인증 세션 400개·섬 40개와, 탈퇴 전에 동결한 집중 세션 747개의 UUID를 사용했다. 접두어·닉네임·시간대만으로 삭제하지 않았다.
- 탈퇴 뒤 집중 기록의 `user_id`가 NULL이므로 사용자 조건만으로는 찾을 수 없다. 동결한 세션 ID로 기본·상세·구간·정산을 연결했다.
- 일일 통계 60건은 더미의 `user.withdrawn` 이벤트와 동일한 PostgreSQL 트랜잭션 ID(`xmin`)로 소유자를 복원했다. 각 행의 날짜별 초·세션 수를 같은 트랜잭션의 동결 집중 기록과 대조했다. 60건 모두 일치했고 총 **1,426초·129회**였다. 다른 익명화 대상 6개 표에서도 같은 탈퇴 트랜잭션의 잔존 행이 없음을 확인했다.
- 이벤트 8,862건은 정확한 더미 `user_id`로 선택했다. 삭제 전에 이벤트 ID와 aggregate 키를 동결해 Chat·Notification 수신 기록도 대조했다. 다른 사용자 이벤트와 공유하는 aggregate 키는 제외하는 조건을 적용했다.
- DB마다 트랜잭션을 사용하고 단계별 완료 증거를 남겼다. FK 자식부터 삭제했으며 실행 전 처리 중인 전달 lease가 0임을 확인했다. 실행 스크립트는 독립 검토와 읽기 전용 예행 검증을 거쳤다.

## 남겨야 했던 6개 종료 섬

현재 배포의 `focus_session_details.island_id`는 **NOT NULL + groups 참조 RESTRICT**다. 추가 부하의 SEA 기록 5건과 사전 시험의 SEA 기록 1건이 서로 다른 시험 섬 총 6개를 목적지로 참조한다. 첫 대조 당시 추가 부하 관련 2건은 진행 중이고 나머지 4건은 완료 상태였다. 운영 코드는 항해 화면에 목적지 이름을 보여 주기 위해 종료된 섬도 조회한다.

따라서 이 섬을 삭제하거나 목적지 ID를 NULL로 바꾸면 정상 사용자 기록과 조회가 깨진다. 해당 섬 6행은 `deleted_at`이 설정된 종료 상태로만 남겼다. 활성 시험 계정·멤버십·섬은 0이다. 추가 부하의 정상 SEA 상세 5행은 삭제 직후와 지연 재조회에서 행 전체 해시가 같았고, 사전 시험의 정상 SEA 상세 1행도 삭제 전후 해시를 대조했다. 운영 DDL·ACL·이미지·컨테이너 설정은 변경하지 않았다.

이 최소 참조 행까지 제거하려면 운영 목적지 참조 계약을 먼저 개선·배포하고 다시 정리해야 한다. 일반 사용자의 기록을 지워 숫자만 0으로 만들지 않는다.

## 재검증과 증거

[cleanup-evidence.json](cleanup-evidence.json)에 삭제 건수, 익명 통계 대조 결과, 즉시 잔존 검사, 약 125초 뒤 재검사, Redis 정리 및 Data DB의 전체 UUID 컬럼 범위 검사를 남겼다. 사용자 UUID·토큰·DB 자격은 포함하지 않았다.

Data DB public 스키마 99개 표의 UUID 219개·식별자 문자열 8개 컬럼을 시험 ID 목록과 정확히 일치하는 조건으로 대조했다. 이 전수 검사는 JSON·배열 내부와 문자열 부분검색을 포함하지 않는다. 그 결과, 400개 추가 부하 범위의 잔존은 정상 SEA 상세 5행과 보호된 종료 섬 5행뿐이었다. 10개 사전 시험의 범위는 별도 증거에서 대조한다. 익명 통계와 복합 aggregate 키는 동결한 별도 목록으로 재검사했다. 검사 대상인 세 DB의 삭제 범위는 모두 0이었다.

이 기록은 서비스 DB·캐시 및 임시 시험 자원의 정리 증거다. 공유 Kafka 로그의 이미 전달된 이벤트, 운영 감사 로그·백업, Jira에 보관한 측정 증거까지 선택적으로 물리 삭제했다는 뜻은 아니다. 공유 로그를 비우거나 정상 운영의 보존 정책을 변경하지 않았다.

## 재발 방지 구현

추가로 필요한 작업은 부하 시험의 종료 절차다. 생성 manifest에 소유 PK·이벤트 ID를 기록하고 익명화 전에 관계를 동결해야 한다. 종료 시 Data·Chat·Notification·Redis를 모두 검사하고, 정상 사용자의 외부 참조가 있으면 보호 목록으로 명시해야 한다. 일반 탈퇴 API 성공만으로 시험 데이터 정리가 끝났다고 판정하는 방식을 바꿔야 한다.
