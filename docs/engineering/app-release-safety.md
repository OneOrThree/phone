# 앱 출시 검증과 운영 오류 감시

## 구현과 실제 활성화 구분

다섯 방어 단계의 코드가 존재한다. API 전체를 실서버에서 테스트했다는 의미는 아니다.
정적 경로 대조는 122개, 런타임 응답 계약은 핵심 8종, dev 시나리오는 기존 15종과 첫 항해 1종이다.
모든 API·권한·실패 조합을 검증한 것으로 집계하지 않는다. [커버리지](../../smoke/contracts/coverage.md)를 참고한다.
운영 계정·Datadog 키·알림 수신처는 코드와 별도이며 활성화 전에 실제 계정으로 검증해야 한다.

## 1. 개발 중 계약 검사

`smoke/contracts/inventory.cjs`는 앱 request 호출과 인증 refresh를 추출하고 서버 경로와 메서드를 대조한다.
`response_contract.py`는 계정·소속·망원경·홈·첫 도착·집중 시작·현재 집중·보상 정산의 성공 응답 필드와 타입을
검증한다. 신규 필드는 허용하고 필수 필드 삭제·타입 변경은 실패시킨다. 정적 경로 일치만으로 응답 호환성을 승인하지 않는다.

## 2. dev 시나리오와 격리 데이터

기존 smoke의 전용 신규 게스트·단독 섬·소유권 검사·요청 예산·정리 절차를 사용한다.
TC019는 실제 무인도 생성·도착·동일 키 재요청·홈을 검사하고 기존 집중·보상·건설 TC014와 함께 실행한다.
별도 fixture의 시나리오들로 구성되므로 하나의 사용자가 모든 앱 기능을 연속 수행하는 UI E2E와는 구분한다.
공유 dev에서 DB 전역 초기화나 일반 사용자 데이터 변경을 수행하지 않는다.
전체 결과는 `compatibility-dev.json`에 앱 커밋·앱 트리·실제 서비스 소스 SHA·image ID·결과 해시와 함께 남긴다.

## 3. 출시할 앱과 운영 서버 대조

앱 출시 스크립트의 기존 `app-server-gate.py` 끝에서 `release_check.py`를 호출한다.
`ALLOW_SERVER_GAP`은 이전 소스 비교의 예외이며 새 호환성·운영 API 검사까지 건너뛰지 않는다.

1. `APP_COMPATIBILITY_RUN_ID`로 특정 main dev smoke 성공 실행을 선택한다.
2. GitHub API로 실행 워크플로·브랜치·성공·head SHA를 확인하고 `smoke-results` 산출물을 받는다.
3. 현재 빌드할 `app/app-dev` Git 트리가 해당 dev 검사 시점의 트리와 일치해야 한다.
4. `deployment-status/prod-V2/app-proof.json`의 네 서비스 소스가 테스트 당시 실제 dev 서비스와 모두 같아야 한다. release merge commit은 SHA가 다를 수 있으므로
   SHA가 다르면 Git에서 해당 서비스 디렉터리 트리가 동일한지도 확인한다.
5. 운영 기록의 실행 URL·재실행 번호가 최신 성공 운영 CD와 일치해야 한다. 검사 뒤에도 다시 확인한다.

서버 소스 버전 일치는 보수적이다. 소스가 다르지만 호환되는 경우에도 재검증 전에는 막는다.
운영·dev의 환경 설정 차이는 동일 소스라는 사실로 보증하지 않으며 다음 실제 응답 검사로 보완한다.
앱만 변경된 main은 서버 배포가 없어 자동 smoke가 안 돌 수 있다. 이 경우 main의 dev smoke를 수동 실행한다.
산출물 보존 기간(현재 7일)이 지나면 재검증한다. 오래된 성공을 영구 승인으로 사용하지 않는다.

## 4. 운영 핵심 검사

전용 운영 계정을 준비하고 기존 소속 섬·홈이 정상 조회되도록 유지한다. 일반 사용자 계정을 사용하지 않는다.
저장소 밖 권한 0600 파일에 다음을 보관한다. `user_id`는 실제 UUID여야 한다.

```json
{"purpose":"phone-production-smoke","user_id":"전용 계정 UUID","access_token":"유효한 토큰"}
```

출시 명령 실행 환경에 다음을 설정한다. 토큰 값은 인자·로그·커밋에 넣지 않는다.

```bash
export APP_COMPATIBILITY_RUN_ID=성공한_dev_실행_ID
export APP_PROD_SMOKE_FIXTURE=/보호된/경로/production-smoke.json
# 그다음 기존 운영 OTA·TestFlight·Android release 명령 실행
```

- `/me`, `/me/islands`, `/me/telescope`, `/screens/home`을 운영 고정 주소에서 실제 호출한다.
- HTTP 200·성공 봉투·핵심 필드 타입과 전용 계정 ID를 확인한다. 인증 실패·404·5xx·리다이렉트·HTML·타임아웃은 차단한다.
- `POST /islands/not-a-uuid/intro-arrivals`는 `400 INVALID_PARAMETER`, `field=islandId`를 요구한다.
  인증과 라우팅을 지나 컨트롤러의 UUID 검증까지 도달했음을 확인한다. 401·404를 성공으로 인정하지 않는다.
  도메인 호출 전에 잘못된 UUID로 중단하므로 무인도·도착 데이터를 만들지 않는다.
- 위 부정 입력 검사는 실제 도착 쓰기 성공을 보장하지 않는다. 쓰기 성공은 dev TC019의 근거와 서버 버전 대조로 확인한다.
- access token 만료 시 전용 계정으로 다시 인증해 파일을 갱신한다. 무한 재시도·자동 계정 생성·서버에 대한 쓰기 부하는 없다.

## 5. 출시 후 감시

기존 business 접근 로그의 `status_code`, `app_version`, `http_route`를 사용한다.
`release-monitoring/manage.py`는 404·5xx 각각 전체 요청 및 앱 버전/경로별 모니터 4개를 생성·갱신한다.
알림은 5분간 5건부터 발생하도록 시작한다. 정상적인 리소스 부재도 404이므로 실제 트래픽에 맞춰 조정한다.
버전 헤더가 없는 오류를 놓치지 않도록 전체 요청 모니터를 함께 둔다.

필요 설정: `DD_API_KEY`, `DD_APP_KEY`, `DD_SITE`, `DD_RELEASE_ALERT_RECIPIENT`.
수신처 예: `@실제팀메일` 또는 실제 Datadog 알림 연동 식별자.
워크플로 「운영 앱 API 오류 모니터 설정」은 기본 계획 출력이며 execute 선택 시 원격 validate 후 적용한다.
동일 관리 태그·이름이면 갱신하며 중복 생성이나 타 팀 모니터 삭제를 하지 않는다.
그룹 집계에는 Datadog에서 앱 버전·경로 facet이 실제 수집되는지도 확인해야 한다.

business까지 도달하지 않은 CDN/nginx 오류는 이 접근 로그 모니터의 범위 밖이다.
해당 구간의 감시는 Infra nginx/CDN 로그 수집 설정과 별도로 연결해야 한다.
정의 추가만으로 모니터가 활성화된 것으로 보고하지 않는다.

## 반영 순서

1. dev CI와 시나리오를 main에 반영하고 실제 16개 TC 성공 산출물을 만든다.
2. 서버 기록 코드를 release로 승격하고 운영 CD를 성공시켜 app-proof.json을 생성한다.
3. 전용 운영 계정과 파일을 출시 환경에 준비하고 실제 검사 통과를 확인한다.
4. 새 앱 출시 게이트를 사용하는 환경에 위 두 변수를 설정한다. 설정이 없으면 출시가 차단된다.
5. Datadog 로그·facet·수신처를 확인해 모니터를 적용하고 알림 수신을 확인한다.

이미 업로드한 앱의 App Store Connect 출시 버튼에는 실행되지 않는다.
심사 제출 후 서버 롤백을 했다면 같은 앱 소스로 다시 검사를 실행한 뒤 수동 출시한다.
구버전 앱 계약은 유지하고 필드·경로 삭제는 실제 구버전 사용 종료를 확인한 뒤 진행한다.
공통 앱 API 목록만으로 과거 모든 앱 버전의 호환성을 자동 보증하지 않는다.
