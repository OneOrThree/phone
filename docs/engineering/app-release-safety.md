# 앱 출시 검증과 운영 오류 감시

## 구현과 실제 활성화 구분

네 방어 단계의 코드가 존재한다. API 전체를 실서버에서 테스트했다는 의미는 아니다.
정적 경로 대조는 122개, 런타임 응답 계약은 핵심 8종, dev 시나리오는 기존 15종과 첫 항해 및 집중 여정 2종이다.
모든 API·권한·실패 조합을 검증한 것으로 집계하지 않는다. [커버리지](../../smoke/contracts/coverage.md)를 참고한다.
운영 적용 전 실제 dev 실행과 운영 테스트 데이터의 생성·정리 검증이 필요하다.

## 1. 개발 중 계약 검사

`smoke/contracts/inventory.cjs`는 앱 request 호출과 인증 refresh를 추출하고 서버 경로와 메서드를 대조한다.
`response_contract.py`는 계정·소속·망원경·홈·첫 도착·집중 시작·현재 집중·보상 정산의 성공 응답 필드와 타입을
검증한다. 신규 필드는 허용하고 필수 필드 삭제·타입 변경은 실패시킨다. 정적 경로 일치만으로 응답 호환성을 승인하지 않는다.

## 2. dev 시나리오와 격리 데이터

기존 smoke의 전용 신규 게스트·단독 섬·소유권 검사·요청 예산·정리 절차를 사용한다.
TC019는 실제 무인도 생성·도착·동일 키 재요청·홈을 검사하고 기존 집중·보상·건설 TC014와 함께 실행한다.
TC020은 첫 항해 사용자의 집중 시작부터 휴식·재개·종료·보상까지 같은 계정으로 실행한다. 실제 모바일 UI 재시작을 수행하는 E2E와는 구분한다.
공유 dev에서 DB 전역 초기화나 일반 사용자 데이터 변경을 수행하지 않는다.
전체 결과는 `compatibility-dev.json`에 앱 커밋·앱 트리·실제 서비스 소스 SHA·image ID·결과 해시와 함께 남긴다.

## 3. 출시할 앱과 운영 서버 대조

앱 출시 스크립트의 기존 `app-server-gate.py` 끝에서 `release_check.py`를 호출한다.
`ALLOW_SERVER_GAP`은 이전 소스 비교의 예외이며 새 호환성·운영 API 검사까지 건너뛰지 않는다.
`app/app-dev`에 Git이 감지하는 미커밋 수정이나 미추적 파일이 있거나 상태 조회에 실패하면
어떤 예외 설정이 있어도 먼저 중단한다. 검증 기준인 HEAD와 빌드할 앱 소스가 달라지는 일을 막기 위함이다.

Android CI의 일회용 서명 AAB와 Play internal은 기존 [경고 정책](../conventions/android-ci-cd.md#서버-선행-게이트)을
따른다. 서버 검사는 별도 CI 잡에서 실행하지만 실패해도 internal 게시를 허용하고 CD 요약에도 표시한다.
Gradle의 CI 빌드는 이 검사를 중복 실행하지 않는다. 아래 차단 규칙은 iOS·OTA·Android 로컬 운영 빌드에
적용되며, internal 게시 성공으로 이를 통과했다고 간주하지 않는다.

1. `APP_COMPATIBILITY_RUN_ID`로 특정 main dev smoke 성공 실행을 선택한다.
2. GitHub API로 실행 워크플로·브랜치·성공·head SHA를 확인하고 `smoke-results` 산출물을 받는다.
3. 현재 빌드할 `app/app-dev` Git 트리가 해당 dev 검사 시점의 트리와 일치해야 한다.
4. `deployment-status/prod-V2/app-proof.json`의 네 서비스 소스가 테스트 당시 실제 dev 서비스와 모두 같아야 한다. release merge commit은 SHA가 다를 수 있으므로
   SHA가 다르면 Git에서 해당 서비스 디렉터리 트리와 공용 JAR·이미지 빌드 입력이 동일한지도 확인한다.
5. 운영 기록의 실행 URL·재실행 번호가 최신 성공 운영 CD와 일치해야 한다. 검사 뒤에도 다시 확인한다.

서버 소스 버전 일치는 보수적이다. 소스가 다르지만 호환되는 경우에도 재검증 전에는 막는다.
운영·dev의 환경 설정 차이는 동일 소스라는 사실로 보증하지 않으며 다음 실제 응답 검사로 보완한다.
앱만 변경된 main은 서버 배포가 없어 자동 smoke가 안 돌 수 있다. 이 경우 main의 dev smoke를 수동 실행한다.
산출물 보존 기간(현재 7일)이 지나면 재검증한다. 오래된 성공을 영구 승인으로 사용하지 않는다.

## 4. 운영 핵심 검사

매 실행 새 기기 UUID로 임시 게스트를 만들고 무소속 상태를 확인한다. 그 계정으로
정원 1명·가입 승인 필수인 테스트 섬을 생성해 타 사용자의 자동 가입을 막는다.
검사가 끝나면 성공·실패·예외·SIGINT/SIGTERM 여부와 관계없이 finally에서 아래를 실행한다.

1. 현재 소속 목록을 다시 읽어 이 실행의 고유 이름과 일치하는 섬만 찾는다.
2. 본인 방장·주민 1명을 확인하고 소속 해제로 섬을 폐쇄한다.
3. 섬 조회가 404이고 소속 목록이 비었는지 확인한다.
4. 계정 탈퇴 API에 `confirmation=DELETE`를 보내고 `deleted=true`를 확인한다.
5. 정리까지 성공해야 실행 기록을 제거하고 출시 검사를 통과시킨다.

섬 정리 실패 시에도 계정 탈퇴를 시도하며, 하나라도 실패하면 출시를 차단한다.
탈퇴·폐쇄는 기존 서버의 삭제 정책이다. 개인정보·자격·공동 데이터는 정리하지만
삭제 표시된 계정/섬 행과 보존 대상 이력까지 물리적으로 모두 제거하지는 않는다.
섬은 잠시 공개 목록에 보일 수 있으나 정원 1명과 승인 필수 설정으로 타인 가입을 막는다.

출시 실행 환경에 다음을 설정한다. 더 이상 사전 계정 토큰 파일을 사용하지 않는다.

```bash
export APP_COMPATIBILITY_RUN_ID=성공한_dev_실행_ID
export APP_PROD_SMOKE_STATE_DIR="$HOME/.local/state/phone-prod-smoke"
# 이후 기존 운영 OTA·TestFlight·Android release 명령 실행
```

정리 기록 디렉터리는 본인 소유 0700, 개별 실행 기록은 처음부터 0600으로 생성한다.
기록에는 생성 응답 유실 복구용 기기 UUID·인증 자격이 있으므로 커밋·로그·일반 CI 산출물로
공유하지 않는다. 재부팅 후에도 유지되는 보호된 경로를 사용하고 RUNNER_TEMP를 사용하지 않는다.
동일 경로에서 동시 실행은 거절하고, 미정리 기록이 있으면 새 검사·출시도 차단한다.

- `/me`, `/me/islands`, `/me/telescope`, `/screens/home`을 운영 고정 주소에서 실제 호출한다.
- HTTP 200·성공 봉투·핵심 필드 타입과 임시 계정 ID를 확인한다.
- `POST /islands/not-a-uuid/intro-arrivals`는 `400 INVALID_PARAMETER`, `field=islandId`를 요구한다.
  이 요청은 섬 생성·도착 쓰기 전에 중단한다. 실제 도착 쓰기 성공 검증은 dev TC019에서 수행한다.
- 게스트 생성 응답을 잃으면 240초 이내에만 동일 기기 UUID로 복구를 시도한다.
  서버의 게스트 IP별 생성 제한을 우회하지 않으며 429나 복구 창 경과는 실패한다.
- 섬 생성 응답을 잃어도 소속 목록에서 고유 이름을 대조해 정리 대상을 찾는다.

SIGKILL·전원 차단·장기 네트워크 단절은 finally 실행을 보장할 수 없다. 보호된 기록을 남겨
새 실행을 막고 정리 전용 명령으로 복구한다. 토큰 만료·복구 창 경과·탈퇴 응답 유실 등
확인할 수 없는 상태는 자동 성공 처리하지 않고 운영자가 기록을 확인해야 한다.

```bash
python3 smoke/contracts/production.py --cleanup "$APP_PROD_SMOKE_STATE_DIR/실행ID.json"
```

이 명령은 유효한 자체 실행 기록에 대해서만 섬·계정 정리를 재시도하고 새 테스트는 실행하지 않는다.
계정 탈퇴는 확인됐으나 섬 폐쇄 근거가 불명확한 기록은 자동 재시도하지 않고 수동 확인을 요구한다.

## 반영 순서

1. dev CI와 시나리오를 main에 반영하고 실제 17개 TC 성공 산출물을 만든다.
2. 서버 기록 코드를 release로 승격하고 운영 CD를 성공시켜 app-proof.json을 생성한다.
3. 보호된 영속 정리 기록 경로를 준비하고 실제 생성·검사·폐쇄·탈퇴까지 통과하는지 확인한다.
4. 새 앱 출시 게이트를 사용하는 환경에 위 두 변수를 설정한다. 설정이 없으면 출시가 차단된다.

이미 업로드한 앱의 App Store Connect 출시 버튼에는 실행되지 않는다.
심사 제출 후 서버 롤백을 했다면 같은 앱 소스로 다시 검사를 실행한 뒤 수동 출시한다.
구버전 앱 계약은 유지하고 필드·경로 삭제는 실제 구버전 사용 종료를 확인한 뒤 진행한다.
공통 앱 API 목록만으로 과거 모든 앱 버전의 호환성을 자동 보증하지 않는다.
