# GROMO-1976 신고·차단 구현 계획

## 범위

- 앱만 변경한다. 서버·배포·CI 계약은 변경하지 않는다.
- 기존 차단 API(`GET/POST/DELETE /blocks`)를 사용한다.
- 신고는 새 서버 API를 만들지 않고, 앱에서 운영 Gmail 수신 주소가 채워진 메일 작성 화면을 연다.
- 운영 수신 주소는 `nappaegonoljima@gmail.com`이다.

## UI 진입로

| 진입로 | 기능 |
| --- | --- |
| 친구 목록 `···` | 신고하기, 차단하기, 기존 친구 삭제 |
| 받은 편지 상세 `···` | 편지 신고, 발신자 차단 |
| 설정 → 안전 | 차단 목록 조회와 차단 해제 |

신고 화면은 사유, 선택 설명, 선택 회신 이메일, `이 사용자도 차단` 토글을 제공한다. `이메일 작성`을 누르면 대상 정보와 입력값을 본문에 채운 `mailto:` 링크로 기기의 메일 앱을 연다. 사용자가 전송 전 내용을 확인하고 직접 보내므로 앱은 메일이 접수됐다고 단정하지 않는다.

## 차단과 클라이언트 필터

1. 차단 성공 직후 로컬 차단 ID 집합을 갱신한다.
2. 친구·요청·검색·받은/보낸 편지·열린 편지·섬 우체통에서 차단 사용자를 숨긴다.
3. 로그인 주체가 바뀌면 이전 계정의 차단 snapshot을 폐기한다.
4. 차단 목록 GET과 차단/해제가 경합하면 오래된 응답이 최신 로컬 상태를 덮지 못하게 revision과 request sequence로 막는다.
5. 최초 차단 목록 로딩 실패 중에는 관련 화면을 fail-closed로 숨기고 재시도를 제공한다.

## 검증

- 신고 메일 링크의 수신자·제목·본문·회신 주소를 단위 테스트한다.
- 신고 UI의 기타 사유 검증, 연타 방지, 메일 앱 실패 복구, 선택 차단을 테스트한다.
- 차단 목록 진입·해제와 각 화면의 클라이언트 필터를 테스트한다.
- 앱 전체 Jest, TypeScript, ESLint, Prettier를 통과시킨다.
- 설정 진입부터 이메일 작성 직전까지 브라우저 캡처를 남긴다.

## 범위 정정 기록

초기 구현에서 신고 메일을 서버 SMTP로 발송하도록 확장했으나 요구 범위를 벗어났다. PR에서는 정정 커밋으로 서버와 서버 CI 변경을 전부 제거하고, 기존 차단 API와 앱의 메일 작성 연결만 남긴다.
