# 목표 아키텍처 — 결정 장부 (A1~A22)

> 팀 공유 정본. `service-architecture.md`·`system-architecture.md` 와 어긋나면 **이 장부가 맞다**. 새 결정은 A 번호를 이어서 추가하고, 뒤집힌 결정은 지우지 말고 취소선 + 후속 번호로 남긴다.
> 결정자: 조재영. 2026-09-09~10 브레인스토밍. 잠정 = `(잠정)`, 보류 = `(보류)`.
> 본문의 숫자만 있는 티켓 번호(1643 · 1658 · 1659 · 1660 · 1661 · 1695 …)는 전부 Jira **GROMO-####** 이다(예: 1658 = GROMO-1658). "후속 논의"는 같은 날 뒤이어 진행된 다른 설계 세션(MQ · 레포 분리)을 뜻한다.
| A22 | **분리가 깨뜨리는 「한 트랜잭션」 목록과 그 대체 계약.** 지금 한 DB·한 트랜잭션이라 공짜로 성립하던 불변식들이 소유권을 나누는 순간 전부 깨진다. 리뷰 6~9라운드가 실제 코드에서 찾아낸 것들이고, **산문에서 사라지면 조용히 회귀하므로 여기에 못 박는다** — 구현 시 이 표의 항목마다 대체 계약이 살아 있는지 확인한다.
| ⓐ **탈퇴 → 위성 정리**: 알림은 `user.withdrawn` + 멱등 삭제 + 새벽 리컨실, 링크는 **Business → withdraw** 이고 미전달분은 **Data relay**. tombstone 은 이후 쓰기만 막으므로 **withdraw 가 기존 `claimed_user_id` 도 같은 트랜잭션에서 익명화**해야 한다(`InviteLinkClick:127` = 최초 1회만 기록이라 되돌릴 길이 없다).
| ⓑ′ **가입 귀속 전달**: `GroupService.publishJoinAttribution` 은 **커밋 후 fire-and-forget** 이라 응답 유실·프로세스 종료 시 보낼 주체가 사라진다 → 멤버십 트랜잭션의 `link.joined` outbox + relay.
| ⓑ″ **발급 ↔ 폐기 순서 역전**: revoke 가 먼저 도착하면 no-op 이 되고 **지연된 발급이 새 active slug 를 만든다** → 링크 서버가 `(groupId, inviterId)` 멤버십 tombstone/버전으로 오래된 발급을 거부. **revoke 는 slug 가 아니라 `(groupId, inviterId, linkVersion, membershipEpoch)` 로 보낸다** — **두 값을 분리해야 한다**: 활성 링크가 epoch N 에서 발급된 뒤 탈퇴가 N+1 을 만들면, **새 값만 실은 revoke 는 「정확히 일치」 조건 때문에 링크 N 을 못 지우고**, 반대로 **옛 값 N 만 실으면 「최대값보다 오래된 명령 거부」 규칙에 걸려** 지연 발급 N 을 못 막는다. 그래서 outbox 에 **폐기 대상 `linkVersion=N` 과 전이 후 `membershipEpoch=N+1` 을 함께** 싣고, 링크 서버는 **`linkVersion` 이 일치하는 링크를 폐기하면서 tombstone 을 `N+1` 로 갱신**한다 — 구 테이블 제거 후 Data 는 slug 를 모른다.
| ⓗ **발송 이력**: `notification_sent_logs` → `deliveries` 를 **상태·사건 키까지** 이관. 빈 채 시작하면 `rescanAndFlush` 가 48시간 회차를 재선점해 **결과 푸시 재발송**(`V45:53-61` 이 같은 위험을 명시), `PENDING`·`DEFERRED` 는 반대로 유실.
| ⓘ **판정 잡의 자리**: ②′ 투영으로 판정되면 알림 서버, **코어 이력을 읽어야 하면 Data API 에 남긴다** — `last_active_at`(D+3/7/14)은 이미 비활성인 유저가 이벤트를 안 만들어 투영으로 복구 불가. 판돈 동결 감지(`GroupBetFreezeMonitor`)도 Data 잔류(빠뜨리면 묶인 참가비 탐지 경로 소멸).
| ⓙ **링크 백필은 폐기 상태를 확정하고 옮긴다** — `group_invite_links` 엔 폐기 컬럼이 없고 만료가 **런타임 코어 조회**라, 그대로 복사하면 죽은 slug 가 되살아난다.
| ⓑ **탈퇴·강퇴 → 링크 폐기**: Business 의 revoke 만 실패하면 예전 slug 가 살아 **비공개 그룹 무단 가입**(그룹 HLD `01-acquisition/high-level-design.md:70·83`). → 멤버십 전이 트랜잭션에서 `link.revoked` outbox, Data relay 재전달.
| ⓒ **기기 토큰 삭제(로그아웃·계정 전환)** — **세대 증가는 여기 결합되지 않는다**(㊼: 유저 공통 `authGeneration` 은 **탈퇴·전 기기 로그아웃**에만. 개별 기기·계정 전환은 `ownershipVersion` 이 담당한다): 앱이 실패를 삼킨다(`App.tsx:528`). → ~~Data `/internal/auth/logout` 트랜잭션의 outbox~~ → **㊲ 로 정정: 「DELETE 를 처리하는 자리」에서 outbox 생성**(로그아웃 요청엔 대상 토큰·소유권 값이 없다) + **등록 시 같은 FCM 토큰의 타 유저 행 제거**(두 번째 방어선) + **로그아웃이 올린 세대는 `auth.generation.bumped` 로 별도 전달**.
| ⓓ **결과 ack ↔ 대기 푸시**: 현행은 `BetResultAckSuppressionListener` 가 **같은 트랜잭션에서** 클레임을 종결한다. 알림 DB 분리 후 Kafka 만 쓰면 5분 flush 가 끼어들어 **이미 본 결과가 다시 간다**. → **prepare(HELD 잠금) → Data ack 커밋 → commit** 2단계. **리스 만료는 fail-closed** — `NEEDS_CONFIRM` 으로 넘겨 flush 가 계속 건너뛰고, 해제는 commit·`abort`·**Data 정본 ack 조회로 자기 수렴**(알림 → Data 조회 3종의 두 번째). 조회 경로가 없으면 **롤백 직후 프로세스가 죽는 구간에서 abort 행이 안 생겨 영구 억제가 실재한다**. 「동기 종결 1회」로는 부족하다 — 순서에 따라 발송이 새거나 **영구 억제**된다.
| ⓔ **내기 승리 발행**: `GroupBetEarlyWinConfirmer.confirmWins` 가 집중 세션 트랜잭션 안에서 발행하고 응답에 안 실린다 → **Business 는 발생 사실을 모른다**. 발행 주체는 Data API.
| ⓕ **이관은 이중 쓰기 → 백필 순서**, 클릭만은 **구 랜딩을 잠깐 세워(302 아님 — 302 는 반대 방향 창을 연다) 마지막 증분을 끝낸 뒤 랜딩·매치를 한 nginx reload 로 함께 전환**(fail-closed: 랜딩 잠깐 닫힘 < 되돌릴 수 없는 `matched:false`). 부트스트랩 컷은 시각이 아니라 **outbox 단조 커서**(또는 선소비-버퍼링 + `eventId` dedup). `LINK_IP_SALT` 는 **기존 값 그대로** 이관(새로 만들면 매치 전멸).
| ⓚ **비공개 가입 검증을 트랜잭션 경계까지**: Data 는 Neon 을 못 읽고 Business 는 링크 확인과 가입을 별도 호출로 조합하므로 그 사이 탈퇴·revoke 를 놓친다 → 링크 서버가 **서명한 자격**(slug·groupId·inviterId·**membershipEpoch**·만료)을 Data 명령에 실어 **커밋 안에서 대조** — **대조만으로 부족하다**: `GroupMember` 에 `@Version` 이 없고 조회가 무락이라, 판독 직후 커밋된 동시 탈퇴를 못 본다. **`membershipEpoch`(탈퇴·강퇴·재가입 때만 증가, 일반 낙관락 `version` 과 분리)** + 공유 락으로 **판독과 커밋을 같은 순서 경계에** 묶는다. 낙관락 `version` 을 쓰면 첫 가입이 버전을 올려 **재사용 링크의 이후 수신자가 전부 실패**한다. 서명 검증 키(`LINK_CAPABILITY_KEY`)는 링크·Data 양쪽 보유.
| ⓛ **클릭 이관은 상태 전이까지**: `invite_link_clicks` 엔 `updated_at` 이 없다 → 커서를 **커밋과 함께 증가하는 change sequence**(또는 클릭 전용 outbox)로 잡고(~~`GREATEST(clicked_at, matched_at, claimed_at)`~~ → ㋖: 시각은 커밋 순서를 보장하지 않는다), 정지 창에서 **랜딩뿐 아니라 match·claim 쓰기도 함께 멈춘다**(안 그러면 이미 복사된 행이 미매치·미귀속으로 남아 재매치·귀속 유실).
| ⓜ **코어 조회로 성립하던 억제**: `FriendNotificationService` 는 발송 직전 `friendships` 를 재조회해 이미 처리된 요청을 거른다 → 분리 후엔 `friend.request.resolved` 투영을 **1차 필터로만** 쓰고 **최종 판정은 발송 직전 `eligibility` 정본 조회**(㊩) — 투영만으로는 지연 소비자가 첫 레코드 시점에 `PENDING` 으로 보아 거짓 푸시를 낸다.
| ⓝ **Data 잔류 잡의 발송 명령도 내구화**: 동기 호출만으로 끝내면 알림 서버 장애 시 그 단계 알림이 영구 소실(`InactiveReturn` 은 그 하루만 조회) → 결정적 키로 outbox + `noti_delivered_at` relay.
| ⓞ **presence 종결 계약**: 완료 소비자가 `ZADD`(절대값)와 presence 제거를 **한 Lua 로 원자 수행**, 취소·자동 종료는 별도 제거 전이. TTL 은 안전망일 뿐 종결 수단이 아니다(안 정하면 이중 계상 또는 점수 실종).
| ⓟ **ZSET 재구축은 이벤트 커서와 함께**: 소비 정지·drain 후 교체(1순위) / Kafka watermark 동시 확정 / 버전 붙은 절대 점수 쓰기. 안 맞추면 미소비 이벤트가 스냅샷 위에 한 번 더 더해진다.
| ⓠ **RT 회전은 서명(Business)과 저장(Data)이 갈린다**: RT 도 `JWT_SECRET` 서명 JWT(`AuthService:424`) → Business 가 후보 서명 → Data 가 **조건부 UPDATE 한 번**으로 대조·저장(동시 refresh 는 한쪽만 성공). ~~0행이면 구 RT 유지~~ → **㉮ 로 뒤집혔다: 0행 = 세션 종료(401·재로그인)**. 이 문구는 현행 `AuthService:430` 의 「끊긴 세션은 되살리지 않는다」와 정반대였다 — **㉮ 만 유효한 결정이다.**
| ⓡ **기기 토큰 삭제에 등록 세대**: 지연된 삭제가 **같은 사용자의 재로그인 등록**을 지운다(「타 유저 행 제거」 방어로는 못 막는다) → 현재 세대보다 오래된 삭제를 거부.
| ⓢ **알림 발송 이력은 읽기 전환부터 roll-forward 전용**: `deliveries` → 구 `notification_sent_logs` 역기록 경로가 없다(§3 금지 · 계정 격리). 롤백하면 `rescanAndFlush` 가 재발송.
| ⓣ **랜딩은 DNS 라 nginx 와 원자 전환 불가**: 컷에서는 랜딩도 nginx 프록시로 붙여 매치·claim 과 함께 넘기고 **DNS 이전은 그 뒤 따로**. claim 은 Business 경유라 reload 로 안 바뀐다.
| ⓤ **판정 잡의 자리는 「투영으로 되는가」로 갈린다**: 리그 알림 5잡(`LeagueNotificationService`)도 리그 결과·실시간 순위·티어 설정을 읽어 **Data 잔류**. ⓘ 와 같은 기준.
| ⓥ **등록 세대는 Data 가 소유한다**(`authGeneration`) — ~~로그인·로그아웃마다 증가~~ → **㊓ 로 뒤집혔다: 로그아웃·탈퇴 때만 증가**(로그인에서 올리면 다른 기기 로그인이 유효한 AT 의 `gen` 을 낡게 만들어 정상 세션의 재등록이 거부된다). **㊓ 만 유효하다** — 알림이 발급하면 Data 가 알 수 없어 outbox 에 실을 수 없다.
| ⓦ **이벤트 스키마는 `schemaVersion` + expand/contract**: additive-only · 소비자 선배포 · 제거는 다음 릴리즈 · 모르는 필드 무시 · 양쪽 CI 계약 테스트. 순서용 `version` 과 다른 값이다.
| ⓧ **관리형 브로커 전환은 컷오버 절차가 필요**: 프로듀서 정지 → 구 브로커 drain(랙 0 · DLQ 처리) → 확정 offset 에서 함께 전환 → relay 재개. 주소만 바꾸면 미소비 로그·DLQ 가 버려진다.
| ⓨ **게스트 레이트리밋은 다중 인스턴스의 선행 조건**: `ratelimit:auth:guest:*`(A19) 로 올리기 전엔 Business 를 늘릴 수 없다(`GuestLoginRateLimiter:32-33` 이 같은 말을 한다).
| ⓩ **발송 직전 상태 재확인은 투영으로 대체되지 않는다**: 지연 소비자는 첫 레코드 처리 시점에 투영이 아직 옛 상태다(`ChallengeCreatedNotificationService:109-113` 은 재조회로 `ACTIVE`·현재 그룹원을 확인한다) → 알림을 **상태 무관형/상태 의존형**으로 나누고 후자는 발송 직전 `POST /internal/notifications/eligibility`(조회 3종의 세 번째).
| ㉮ **RT 회전 0행 = 세션 종료**(현행 `AuthService:430` 의 `InvalidTokenException` 을 유지). 세션을 늘리는 건 `isRefreshRotationDue` 의 「회전 안 함」 경로이고, 둘을 섞지 않는다.
| ㉯ **`score-events` 는 별도 토픽·별도 소비자**: producer = Data 세션 종료 outbox, consumer = 랭킹 컨슈머(알림 서버 아님). 안 그리면 완료 점수가 ZSET 에 안 오르고 presence 도 안 지워진다.
| ㉰ **링크 컷 이후는 엄격한 roll-forward**: 「손실 3시간」은 오산이었다 — 컷 이후의 클릭·상태 전이·귀속 감사가 전부 Neon 에만 쌓인다.
| ㉱ **서비스 토큰은 audience + 경로 허용목록으로 강제**: 이름 분리만으로는 최소 권한이 안 선다(알림 자격으로 `/internal/auth/*`·배치 트리거 호출 가능).
| ㉲ **정본이 자기모순이면 취소선으로 끊는다**: ⓠ 의 「0행이면 구 RT 유지」가 ㉮ 와 정면 충돌한 채 남아 있었다 — 장부가 다른 문서보다 우선하므로 **뒤집힌 문구는 지우지 말고 취소선 + 후속 번호**(장부 머리말 규약)를 반드시 적용한다.
| ㉳ **랭킹 소비 멱등은 Redis 안에서 닫는다**: RDS UNIQUE + Redis Lua 는 한 트랜잭션이 아니다. ~~같은 Lua 에서 `eventId` 검사·기록(`league:seen:*`)~~ → **㊧ 로 해소**: 점수를 절대값+version 으로 통일해 **멱등이 연산 자체에서 나온다**(별도 표시 불필요).
| ㉴ **기기 토큰 세대는 양방향 거부**: 오래된 삭제뿐 아니라 **오래된 등록**도 막아야 한다(삭제 시에도 최대 세대를 tombstone 으로 보존).
| ㉵ **Data 명령 응답은 완성된 봉투**(`version` 포함): Business 는 DB 가 없어 outbox 시퀀스를 다시 읽을 수 없다.
| ㉶ **스케줄러 컷오버는 저장소 전환과 별개 단계**: 두 ShedLock 이 다른 DB 에 있어 서로 배제하지 못한다 → 구 정지 → drain → 신 활성화 → legacy 제거 확인.
| ㉷ **Target-2 판정↔워커 전달도 내구화**: 기본값은 **워커가 `deliveries` 미발송 행을 lease 로 선점**(ⓑ), 폴링이 안 되면 알림 DB outbox(ⓐ).
| ㉸ **외부 `X-User-Id` 는 폐기하고 다시 설정한다**: Data 가 `JwtFilter` 를 떼고 헤더를 신뢰하므로, 앱 헤더가 새어 들어가면 정상 AT 로 **남의 데이터를 읽고 쓴다**. Business 가 무조건 제거 → 검증한 AT subject 로 1회 설정(패스스루·BFF·위성 전부).
| ㉹ **내부 HTTP 도 expand/contract**: 이벤트와 방향이 **반대**다 — **제공자 선배포 · 소비자 후배포**. additive-only · 제거는 다음 릴리즈 · 양방향 계약 테스트. 못 지키면 상호 의존 이미지를 한 매니페스트로 원자 배포.
| ㉺ **스케줄러는 「분리 후 이관분만 정지」**: 현 `NotificationScheduler` 하나에 `@Scheduled` 17개가 모여 Data 잔류 잡까지 같이 있다 — 통째로 끄면 그 잡들이 사라진다.
| ㉻ **`rescanAndFlush` 는 쪼갠다**: Data 가 재훑어 발송 명령(outbox)만 만들고 claim·flush 는 알림 서버가 자기 DB 에서. A18 이 비요청형 유실을 허용할 수 있어 이 복구 경로를 잃으면 결과·환불 푸시가 영구 누락.
| ㉼ **명령 멱등은 `eventId` 가 아니라 idempotency key 로, 키 소유자는 앱**: 호출자는 첫 응답 전엔 `eventId` 를 모르고 Business 는 무상태라 앱 재시도마다 새 키가 생긴다 → 앱이 `Idempotency-Key` 헤더로 보내고 Data 가 UNIQUE 저장 후 **응답을 재생**.
| ㉽ **`authGeneration` 은 AT claim 으로 나른다**: 앱이 로그인과 무관한 시점에 `PUT device-token`·`onTokenRefresh` 를 부르므로(`push.ts:261`) 로그인 응답 전달만으로는 세대를 모른다.
| ㉾ **발송 명령 키에 도메인 사건 식별자 필수**: `userId+단계+날짜` 만이면 같은 날 여러 그룹·챌린지 사건이 한 키로 충돌해 한 건 빼고 누락(현 파이프라인의 `(user_id, kind, subject_id)` 와 같은 이유).
| ㊀ **위성 호출 토큰은 caller 별로 분리**(총 7종): 공유하면 수신 측이 호출자를 구분 못 해 허용목록이 합쳐지고 한쪽 유출이 다른 쪽 명령을 연다.
| ㊁ **DLQ 이름은 `*.DLT`(프레임워크 기본값)로 확정**: `.dlq` 는 커스텀 resolver 를 반드시 함께 설정해야 하고 그 누락이 조용히 새는 실패를 만든다 — 기본값을 택해 그 유형 자체를 없앴다.
| ㊂ **컬렉션 투영은 aggregate 별 version**: 유저 단위 최대 version 하나면 지연된 앞 회차가 「오래된 것」으로 거부돼 참가 행이 영구 누락.
| ㊃ **랭킹 스트림에 탈퇴·직군 변경도 발행**: 세션 종료만 보내면 탈퇴자가 랭킹에 남고 직군 모수가 틀어진다 → `ZREM`·직군 ZSET 이동을 멱등 적용.
| ㊄ **정지 창의 match·claim 은 거절이 아니라 대기**: 앱이 재시도해 주지 않는다(`deferredInvite.ts:93-105` 는 다음 실행, `claimStoredInviteAttribution` 는 다음 로그인).
| ㊅ **prepare 는 부재 클레임도 선점**: ack 가 소비보다 먼저 오면 잠글 행이 없어 no-op → `(userId, BET_RESULT, sessionId)` insert-or-transition(현 구현의 「INSERT 먼저」와 같은 이유).
| ㊆ **이관 전 기기 토큰 중복 정리 + 토큰 단위 유일성 검증**: `device_token` 에 UNIQUE 가 없고 로그아웃 삭제 실패를 앱이 삼킨다.
| ㊇ **drain 뒤 이력 재동기화(④″)**: 두 DB 는 한 트랜잭션이 아니라 ③ 통과 후 생긴 누락을 아무도 못 잡는다 → 중복 푸시.
| ㊈ **FCM 자격 회수는 ④′ 이후 배포에서**: fail-fast 생성자라 조기 회수 시 Data API 가 안 뜨고 전환 기간 알림이 끊긴다.
| ㊉ **④″ 는 이력만이 아니라 이중 쓰기 리소스 전부**를 쓰기 정지·drain 뒤 재동기화·재검증(토큰·설정·이력). ③ 통과 후의 실패는 아무도 못 잡는다.
| ㊊ **링크 명령도 양방향 세대 거부**: 발급만 막으면 지연된 revoke(N)가 재가입 후 발급(N+1)의 새 slug 를 폐기한다 → 오래된 revoke 거부 + 요청 버전과 정확히 일치하는 링크만 폐기.
| ㊋ **`score-events` 는 주차별로 분할**(`(weekStartAt, 절대값, version)`)하고 키도 `league:<weekStartAt>:*`. 자정·주 경계를 걸친 세션은 두 주차를 갱신하므로 **세션당 한 건**으로는 한 주가 틀린다.
| ㊌ **기기 토큰은 「전역 소유권 장벽」까지 필요**: 세대는 유저별이라 A·B 의 순서를 못 가린다 → 토큰 행에 `(ownerUserId, ownerGen, ownershipVersion)`, 소유권 이전 뒤 **이전 소유자의 모든 명령 거부**.
| ㊍ **`gen` claim 활성화는 롤아웃 절차**: 구 AT 에는 `gen` 이 없다(`JwtProvider:228-229`) → Business 선배포 → AT 최대 수명(3600s) 대기 → 세대 검사 필수화. **없는 값을 현재 세대로 채우면 tombstone 우회**.
| ㊎ **새 스케줄러 활성화는 ④″ 뒤(④‴)**: ③ 이후 구 스케줄러가 만든 이력이 신 DB 에 없는 채로 켜면 재훑기가 재선점해 중복 푸시.
| ㊏ **링크 원장도 ④″ 대상**: 구 쪽 발급만 성공한 slug 가 남으면 이미 공유된 초대가 전환 직후 실패.
| ㊐ **오래된 점수는 상태 전이 tombstone/버전으로 거부**: `.DLT` 재처리분은 `eventId` 검사를 통과하므로, 가산 방식이었다면 `ZREM` 뒤에 과거 점수가 얹혀 탈퇴자가 되살아났다 — **㊧ 의 절대값+version 통일로 점수 쪽은 해소**됐고, **탈퇴 tombstone 은 그대로 필요**하다(절대값이라도 탈퇴 후엔 아예 쓰면 안 된다).
| ㊑ **최초 로그인 RT 는 2단계 + 멱등 재개**: Business 는 upsert 전 `userId` 를 모르고 Data 는 미서명 RT 해시를 저장할 수 없다 → ① upsert(멱등 키)로 `userId` → ② 서명 → ③ 조건부 해시 저장.
| ㊒ **소셜 로그인은 「선택적 인증」**: 현 `AuthService.socialLogin` 이 선택적 AT 로 게스트→소셜 승격을 한다(GROMO-585) — 순수 익명으로 구현하면 **집중 기록·지갑·그룹 상태를 잃는다**. 전달값은 헤더가 아니라 **검증한 AT 의 subject**(㉸ 와 충돌 없음).
| ㊓ **`authGeneration` 은 ~~로그아웃~~·탈퇴 때만 증가** → **㊼ 로 좁혀짐: 탈퇴·전 기기 로그아웃에만**(로그인·개별 기기 로그아웃은 안 올림). 로그인 fencing 은 토큰 행의 `ownershipVersion` 담당 — 이중으로 두면 멀쩡한 세션의 재등록이 거부된다.
| ㊔ **기존 사용자 로그인의 RT 교체는 CAS 로**: 재로그인 시 넣을 「기존 해시」가 없다 → ①이 로그인 시도에 묶인 opaque CAS 를 반환하고 ③이 그것으로 조건부 교체.
| ㊕ **백필 충돌은 `DO NOTHING` 금지, 최신값 비교 UPDATE**: 신 DB 에 행이 생긴 뒤의 구 DB opt-out 이 영구히 안 반영된다. 검증도 필드 단위.
| ㊖ **정지 창의 쓰기도 보존**(대기·큐잉 또는 outbox): 앱이 설정·토큰 저장 실패를 삼키고 다음 변경까지 재시도하지 않는다.
| ㊗ **presence 시작 쓰기도 내구화**: 커밋 후 presence 기록만 실패하면 Redis 는 멀쩡해 「복구 시 재적재」가 안 돈다 → outbox·주기 대조·DB 폴백.
| ㊘ **발송은 at-least-once 로 못 박고 `deliveryId` 를 payload 에 실어 앱에서도 dedup**: FCM 수락 직후 크래시 구간은 어떤 순서로도 안 닫힌다 — 유실보다 중복을 택한다.
| ㊙ **CAS 완료 후 응답 유실도 멱등**: ①의 저장 응답에 **RT 서명 재료**(고정 `jti`·발급 시각)를 담아 재시도 시 **같은 RT 를 결정적으로 재생성** — 평문 저장 없이 최종 결과를 재생.
| ㊚ **소유권 값은 요청에도 실어야 순서를 가른다**: 서버 행에만 두면 「지연된 A 등록」과 「정상 B→A 재이관」이 구별되지 않는다 → 등록 응답마다 `ownershipToken` 발급, 다음 요청에 CAS.
| ㊛ **백그라운드 표시 중복은 앱 dedup 으로 못 막는다**: `notification` 블록이라 OS 가 먼저 띄운다 → collapse 키(`tag`/`apns-collapse-id`)로 **교체**시키고, 완전 해소(data-only)는 Target-1 범위 밖으로 명시.
| ㊜ **반복 알림은 사건 키 모양이 다르다**: `CHALLENGE_WINDOW_END`·`CHALLENGE_ENDED` 는 `subject_id` NULL + `target_user_id`+당일 `sent_at` 판정 → 이관 시 KST 판정일로 **변환**해야 전환 당일 재발송을 막는다.
| ㊝ **주 경계 세션은 마지막 이벤트에서만 presence 제거**(`isSessionFinal`): 전주 이벤트가 먼저 지우면 이번 주 라이브 점수가 통째로 빈다.
| ㊞ **구 앱 멱등 키를 요청 본문에서 도출하지 마라**: 종료된 챌린지를 같은 설정으로 다시 만드는 정상 명령이 접힌다 → 매 호출 새 키(Business 재시도만 보호) + 앱 보급 후 필수화.
| ㊟ **`ownershipToken` 도 롤아웃 필요**: 현 앱은 등록에 `{deviceToken}` 만, 삭제엔 본문이 없다 → 앱 배포 → 누락 허용 → 최소 지원 버전 상향 후 필수화. 삭제는 헤더(`X-Device-Ownership`)로.
| ㊠ **`/l/match` 는 붙들 수 없다(5초)**: `MATCH_TIMEOUT_MS=5000` 이고 실패해도 다음 앱 실행까지 재시도가 없다 → 구 앱 잔존 기간엔 **양쪽 저장소 조회**로 처리. 붙들기는 claim 등 여유 있는 경로만.
| ㊡ **로그인 CAS 는 성공 재생 · 충돌 재발급**: 패배한 시도가 같은 키로 재시도하면 무효 nonce 를 재생받아 영영 실패한다.
| ㊢ **fan-out 이벤트는 수신자별 outbox 행으로 펼친다**: 봉투에 `userId` 가 하나뿐이라 `CHALLENGE_CREATED` 를 한 건으로 보내면 수신자를 알 길이 없다 → `<사건키>:<userId>` 로 안정적 `eventId`.
| ㊣ **랭킹 적격성은 하나의 계약**(withdrawn · occupationChanged · **onboarded**)이고 적용은 **주차별 절대 점수 재적재**다 — delta 가산이면 순서·유실에 약하고, 온보딩 완료가 빠지면 나중에 닉네임이 생겨도 넣을 사건이 없다. **탈퇴 거부와 직군 이동을 같은 규칙으로 묶지 않는다**(직군 변경 뒤 온 delta 는 현재 직군에 적용).
| ㊤ **삭제 outbox 를 RT 폐기에 매달지 마라**: 다른 기기 로그인이 해시를 먼저 바꾸면 `logout` 이 유저를 못 찾고 예외로 빠져 outbox 에 도달조차 못 한다 → 검증한 RT subject(또는 AT 인증 별도 명령)로 기록, 새 해시는 건드리지 않음.
| ㊥ **매치는 읽기가 아니라 소진(쓰기)**: 정지 창에도 **쓰기 원장은 Neon 하나**, 구 DB 는 후보 조회만 — 양쪽 소진은 잠금이 공유되지 않아 같은 클릭이 두 기기에 배정된다.
| ㊦ **`ownershipToken` 필수화엔 부트스트랩 예외**: 최소 지원 버전은 코드 존재만 보장한다 → 소유자 증명 시 1회 수락·발급(이전만 토큰 요구).
| ㊧ **점수도 delta 가 아니라 「주차 절대값 + 단조 version」**: 상태 전이의 절대 재적재와 delta 가산을 섞으면 `.DLT` 지연분이 **이중 계상**된다 → 절대값으로 통일해 순서·중복·지연을 한 규칙으로 닫는다.
| ㊨ **삭제 outbox 에 대상 FCM 토큰 + 소유권 값**: 재로그인은 세대를 안 올리므로 세대만으로는 지연된 삭제가 **새 등록을 지운다**.
| ㊩ **친구 요청도 상태 의존형**: 투영은 1차 필터일 뿐 — 지연 소비자는 첫 레코드 시점에 `resolved` 를 아직 적용 안 했다 → 최종 판정은 `eligibility` 정본 조회.
| ㊪ **삭제 요청도 대상 FCM 토큰을 실어야 한다**(`X-Device-Token`) — 현 DELETE 엔 본문이 없어 Business·Data 가 대상 토큰을 알 길이 없고, 그러면 ㊨ 의 outbox 를 계약대로 만들 수 없다.
| ㊫ **정지 창의 구·신 조합 주체는 Business 뿐**: 링크는 코어를 못 부르고 Data→링크는 relay 외 금지 → 정지 창 동안만 nginx 가 `/l/match` 를 Business 한시 핸들러로 보내고 컷오버 후 제거.
| ㊬ **새 주차 ZSET 은 전체 적격 사용자 0점으로 초기화**: 현 쿼리가 `LEFT JOIN` 으로 미집중 사용자도 0점 포함하는데, 초기화가 없으면 월요일 경계 직후 그들이 통째로 사라진다(초기화 전엔 DB 폴백).
| ㊭ **재구축의 점수와 version 은 같은 DB 스냅샷에서**: version 만 따로 붙이면 재구축이 읽은 100점에 더 큰 version 을 달아 동시 커밋된 150점을 영구 거부한다 → 도메인 트랜잭션이 점수와 version 을 함께 저장.
| ㊮ **동점은 Redis 정렬에 맡기지 않는다**: 현 정본은 `user_id ASC`(`:159`)인데 `ZREVRANGE` 는 UUID 내림차순 — 가산 후 재정렬에 `score DESC, uuid ASC` 를 명시 적용하고, 내 순위도 「높은 인원수 + 동점 중 uuid 작은 인원수」로 계산.
| ㊯ **주차 0점 초기화는 최신 점수를 덮지 않게**(version 비교 = 사실상 `NX`, 또는 shadow ZSET 원자 교체) — DB 폴백은 조회만 보호한다.
| ㊰ **종료된 세션의 라이브 값은 고정**: presence 에 `endedAt` 표시 — 안 그러면 소비 지연 동안 끝난 세션이 TTL 까지 계속 가산되고, TTL 뒤엔 완료 점수마저 없다. **단 DB 와 Redis 는 한 트랜잭션이 아니다** — 종료 표시는 **DB outbox 에서 재전달**하고, **미적용 행이 있는 동안 조회는 DB 폴백**(또는 DB 의 종료 상태를 함께 확인).
| ㊱ **소유권 mutation 도 멱등 재생**: version 이 전진하므로 응답 유실 후 재시도가 낡은 값으로 거부된다 → `Idempotency-Key` 로 결과 토큰을 저장·재생(거부가 아니라 성공으로).
| ㊲ **삭제 outbox 는 DELETE 처리 자리에서 만든다**: 앱은 토큰 DELETE 와 logout 을 별개 요청으로 보내고 Business 는 무상태라 값을 이어줄 수 없다 → DELETE 를 받은 Business 가 **먼저 Data outbox 를 기록**하고 그다음 직접 삭제를 시도해 **성공 시 완료 표시**(㊿ — ~~실패 시에야 기록~~이면 그 사이 죽었을 때 둘 다 안 남는다).
| ㊳ **presence 고정값도 주차로 자른다**(`endedAt - max(startedAt, weekStartAt)`): 전체 길이로 고정하면 주 경계 세션의 전주분이 이번 주 랭킹에 중복된다 — 이벤트를 주차별로 쪼갠 것과 같은 규칙.
| ㊴ **`score-events` 도 outbox 강제**(A18 의 유실 수용 대상 아님): 커밋만 되고 이벤트가 사라지면 절대 점수도 안 오르고 presence 도 안 지워진다.
| ㊵ **`version` 비교는 `ZADD` 에만** — `isSessionFinal` presence 종결은 오래된 이벤트에서도 실행(멱등). 안 그러면 `.DLT` 재처리분이 통째로 무시돼 presence 가 남고 이중 계상.
| ㊶ **탈퇴는 모든 주차 ZSET + presence 를 함께 제거**: 후보가 presence 전원을 합치므로 `ZREM` 만으로는 TTL 까지 다시 노출된다.
| ㊷ **알림 설정 변경도 재전달 경로 필요**: 앱이 실패를 삼키고 「다음 변경 때」까지 재시도하지 않아(`NotificationSettingsScreen.tsx:142-148`) **껐는데 계속 오는** 상태가 무기한 간다 → Data outbox 또는 앱 내구 대기열.
| ㊸ **outbox `version` 은 aggregate 행 잠금 아래 발급**: 시퀀스는 할당 순서만 보장하고 커밋 순서를 보장하지 않아, 먼저 번호를 받고 늦게 커밋한 최신 상태가 폐기된다(`User` 엔 `@Version` 도 없다).
| ㊹ **세대 증가는 별도 전달**(`auth.generation.bumped`): 앱이 DELETE 를 logout 보다 먼저 부르므로 삭제 outbox 엔 증가 전 세대만 담긴다 → 지연 등록이 「같은 세대」로 수락돼 토큰이 되살아난다. **단 세대를 올리는 사건은 탈퇴·전 기기 로그아웃뿐**(㊼) — 개별 기기 로그아웃의 장벽은 `ownershipVersion` 이다.
| ㊺ **claim 붙들기도 15초 한계**(`api.ts:215-218`): 정지 창 목표를 15초 미만으로, 넘길 위험이 있으면 `202` + 서버 내구 큐.
| ㊻ **GA4 4종은 링크 서버에도 배포**: 발급·랜딩·매치가 넘어가면 `invite_link_created`·`invite_link_clicked`·`invite_match_resolved` 발행도 넘어간다 — 안 주면 클릭·매치 퍼널이 조용히 끊긴다(링크→코어 전달은 단방향 위반).
| ㊼ **세대는 유저 축, 소유권은 기기 축 — 섞지 않는다**: 유저 공통 `authGeneration` 을 **개별 기기 로그아웃**에 올리면 로그인 중인 다른 기기의 `onTokenRefresh` 등록이 거부돼 푸시가 끊긴다 → 유저 축은 **탈퇴·전 기기 로그아웃**만, 기기 축은 `ownershipVersion`.
| ㊽ **동점자는 자르기 전에 전부 가져온다**: 컷오프 점수 동점자가 N 보다 많으면 `ZREVRANGE` 가 UUID 내림차순 쪽만 줘 정본상 앞선 사용자가 후보에서 탈락한다(새 주차 0점에서 대량 발생) → 경계 점수 구간을 통째로 조회 후 절단.
| ㊾ **Cloudflare 뒤의 원본 IP 는 검증해서 재작성**: `$remote_addr` 는 CF 엣지 IP 라 매치가 전멸하고, `CF-Connecting-IP` 를 그대로 믿으면 오리진 직접 호출자가 위조한다 → `set_real_ip_from` = CF CIDR + 오리진 방화벽.
| ㊿ **삭제 outbox 는 시도 「전에」 기록**하고 직접 전달 성공 시 완료 표시 — 실패 후 기록이면 그 사이 죽었을 때 둘 다 안 남고 앱은 실패를 삼킨다.
| ㋐ **presence 종결은 `sessionId` compare-and-delete**: 유저 단위로 지우면 `.DLT` 재처리분이 그 사이 시작된 새 세션의 presence 를 지운다.
| ㋑ **revoke 는 `linkVersion`(폐기 대상)과 `membershipEpoch`(전이 후)를 분리해 싣는다**: 한 값만 쓰면 「정확 일치」로 못 지우거나 「오래된 명령 거부」로 지연 발급을 못 막는다.
| ㋒ **인증 시크릿도 병행 배포 후 회수**(FCM ㊈ 과 같은 순서): `JWT_SECRET`·IdP 설정은 현 prod yml 의 필수 placeholder 라 조기 회수·롤백 시 Data 가 기동하지 못해 전체 API 가 멈춘다.
| ㋓ **삭제는 행을 지우지 말고 토큰별 tombstone + 마지막 `ownershipVersion` 보존**: 「행 없음」 부트스트랩 예외를 지연 등록이 통과해 토큰을 되살린다.
| ㋔ **호환 핸들러 인플라이트도 drain 대상**: 그 핸들러가 Neon 을 직접 소진하므로 최종 동기화와 겹치면 구 미매치 상태가 새 상태를 덮거나 검증이 안 닫힌다.
| ㋕ **알림 설정에도 단조 `version`**(또는 사용자별 최신 상태로 outbox 병합): 완료 표시만 실패한 「끔」이 나중에 적용돼 사용자가 켠 설정을 도로 끈다.
| ㋖ **시각 기반 증분 커서 금지**(클릭 이관): 상태 변경 시각은 커밋 순서를 보장하지 않아 늦게 커밋된 전이를 영구히 건너뛴다 → change sequence/outbox, 최종 단계는 전체 스캔.
| ㋗ **기기 토큰 DELETE 는 AT 만으로 인증하지 않는다**: bare axios + 만료 AT 로 401 이면 outbox 조차 안 남고 뒤의 logout 엔 대상 값이 없다 → RT 나 별도 기기 자격.
| ㋘ **DB↔Redis 는 한 트랜잭션이 아니다**: 종료 표시도 DB outbox 에서 재전달하고 미적용 행이 있는 동안 조회는 DB 폴백 — 어느 쪽을 먼저 써도 한쪽이 틀린다.
| ㋙ **폐기는 그 사이 수락된 claim 까지 되돌린다**: relay 지연 중 링크는 active 로 보여 claim 을 기록하는데, 그룹 HLD 는 폐기 후 claim 을 no-op 으로 둔다 → 유효하지 않은 초대가 귀속·전환에 영구 집계.
| ⓖ **위성 쓰기 전 활성 검사** — 위성 직행 쓰기는 Data 의 `X-User-Id` 검사를 안 거친다. | PR #731 codex 6~9라운드 (실코드 대조로 확인) | 09-10 |
