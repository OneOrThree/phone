# Apple Watch 컴패니언 — 정책 정본

이 문서가 **정본**이다. `prd.md`와 그 뒤에 올 `information-architecture.md`·`high-level-design.md`·`low-level-design.md`와 어긋나면 **이 문서가 맞다.**

결정은 `D<번호> · <결정 한 문장>` 형식의 플랫 로그다 (`docs/prd/inquiry/policy.md`와 같은 스타일). 번호는 재사용하지 않는다 — 뒤집힌 결정은 지우지 말고 `~~취소선~~` + 대체 조항 번호를 적는다.

확정일: 2026-08-18 · 리뷰 근거: CEO 리뷰 3라운드(독립 리뷰어 최종 9.0/10) + codex 교차 리뷰

## D1 · 구현 접근은 「폰 릴레이 리모컨」이다 — 워치는 리모컨 + 디스플레이, SoT는 폰

워치 자체는 서버와 통신하지 않고, 모든 서버 호출·실드·정산은 폰 엔진이 대행한다. 1차 릴리즈의 백엔드 변경은 0이다.

**근거.** 두 must-have(미러링·워치 발 시작)를 서버 변경 0으로 충족하는 유일한 안이고, 카테고리 표준 방식이다(Flow·Be Focused 등 경쟁 제품이 전부 폰 페어링 컴패니언). 대안 B(표시 전용)는 핵심 모순의 절반만 풀고, 대안 C(워치 자율 클라이언트)는 자격증명 공유 + 서버 하트비트 공사가 딸려와 1차로 과하다.

**뒤집을 신호.** 워치 세션 완료율이 폰 발 대비 유의미하게 낮으면(폰 깨우기 신뢰성 한계) C안 요소(워치 직접 통신)를 v2에서 재검토한다 — D9 참조.

## D2 · 선행 리팩토링은 「화면 탈출」이 아니라 4요소 공사다

① 버전 붙은 **영속 세션 상태 머신**(모드·목표·페이즈·정지 포함) ② **정산 저널** ③ 그 위의 **헤드리스 엔진**(백그라운드 콜드 스타트에서 UI 없이 부팅) ④ **네이티브 명령 인박스**(WCSession 명령을 JS 부팅 전에 영속화). 별도 티켓·별도 PR로 먼저 나가고, 착수 전에 현행 동작 특성화 테스트를 잡는다.

**근거.** 현재 SoT는 `FocusSessionScreen`(1,792줄) 안의 React ref들이다. 영속 레코드에는 모드·정지 상태가 없고, `OrphanFocusSettler`는 세션을 재개하는 게 아니라 마지막 체크포인트에서 종료 정산한다 — 재연결한 워치에 보낼 권위 상태 자체가 없다(codex 교차 리뷰로 확인). 기존 모듈(`blockPause`·`uploadFocusBlock`·`pendingFocusUploads`)은 복제하지 않고 그대로 오케스트레이션한다.

## D3 · 출시 순서 — 실기기 스파이크와 LA 정확도 수리를 맨 앞에 둔다

페이즈 0 = ⓐ WCSession wake SLO 실기기 스파이크(suspended/terminated/force-quit별) ⓑ Live Activity `ContentState` 확장(정지 중에도 증가하는 현행 부정확도 수리) ⓒ 페어링 보급률 계측 ⓓ 특성화 테스트 + 헤드리스화. 이 넷이 끝나야 페이즈 1(워치 코어)에 들어간다.

**근거.** codex의 「순서가 거꾸로다」 지적(보급률을 재기 전에 최대 리팩토링부터 시작)의 절충안이다. 가장 싼 검증(스파이크·계측·LA 수리)을 앞으로 당기면, 워치 코어에 들어가기 전에 ① 폰 깨우기가 실제로 성립하는지 ② 보급률이 투자를 정당화하는지를 실측으로 안다. 범위 확정 자체는 유지한다 — 검증이 실패하면 그때 범위를 다시 연다.

**뒤집을 신호.** ⓐ에서 wake 성립률·지연이 수용 불가로 나오면 페이즈 1 착수 전에 D1을 재검토한다.

## D4 · 홈스크린 위젯·Siri/App Intents는 별도 PRD로 분리한다

R14(홈 위젯)·R15(App Intents)는 `docs/prd/entry-points/`로 이관한다. 이 PRD는 워치(+ 워치 소속인 컴플리케이션)만 다룬다.

**근거.** 둘은 워치와 무관한 폰 표면이고, 이 PRD의 문제 정의(§1)는 전부 워치다. 리뷰 단위·문서 응집도가 낫고, 페이즈 2 시점에 어차피 별도 티켓이다. 공통 기반(헤드리스 엔진, D2)은 두 PRD가 같이 딛는다.

## D5 · 워치 발 시작은 카운트업만, 미러링은 3모드 전부

워치 시작 UI에는 모드 선택이 없다 — 과목 선택 → 카운트업 시작. 폰에서 시작한 카운트다운·뽀모도로 세션은 워치에 온전히 미러링된다(상태 스냅샷에 모드가 실리므로 증분 비용이 작다).

**근거.** 워치 화면에서 모드·목표 시간까지 고르게 하면 시작 마찰이 폰만큼 커져 「손목 시작」의 존재 이유가 죽는다. 카운트다운·뽀모도로가 필요한 사용자는 어차피 목표 설정을 위해 폰을 연다.

**뒤집을 신호.** 워치 발 시작 사용자가 세션 중 폰으로 모드를 바꾸는 패턴이 관측되면 워치 시작 UI에 모드를 추가한다.

## D6 · 일시정지·재개를 워치에 노출한다

**근거.** 「잠깐 자리 뜨기」(S-4)는 실사용 빈도가 가장 높은 세션 중 조작이고, 이걸 폰으로 하게 만들면 세션 중 폰 픽업 제거라는 목표 1이 깨진다. 정지는 현행 로컬 의미론(`totalDistractionSeconds` 차감)을 그대로 쓰므로 서버 영향 0.

## D7 · 폰 미도달 시 워치 로컬 임시 시작은 하지 않는다 — 즉시 실패 + 안내

폰이 안 닿으면 워치는 큐잉·로컬 타이머 없이 「iPhone과 연결한 뒤 시작할 수 있어요」를 표시한다. S-3(로컬 임시 시작)은 1차 미구현으로 확정.

**근거.** 임시 시작을 허용하는 순간 워치가 임시 SoT가 되어 D1과 충돌하고, 소급 반영은 서버 `startedAt` 클램프([-5분, 0], `FocusController.java:137`)와 정면 충돌한다. 소급·중복·계정 전환 정책 3종이 딸려오는 것에 비해, "폰을 가까이 두는" 사용자가 대다수인 1차에서 얻는 게 작다.

**뒤집을 신호.** 워치 시작 실패 사유 중 「폰 미도달」 비중이 높게 관측되면 v2에서 재검토 — 그때는 서버 소급 API(R11 포기)가 전제다.

## D8 · watchOS 최소 버전은 잠정 11+ — 페이즈 0 보급률 데이터로 확정한다

**근거.** watchOS 11+(iOS 18 페어링)은 Smart Stack의 Live Activity 자동 미러링을 근거 자산으로 쓸 수 있어 워치 앱이 커버 못 하는 표시 공백을 OS가 메꾼다. 다만 이건 가설이고, 분모(페어링 기기의 OS 분포)는 페이즈 0 계측이 준다 — 확정을 데이터 도착 뒤로 미루는 비용이 0이다(타겟 버전은 개발 착수 시점에만 필요).

## D9 · 워치 직접 API 호출(자격증명 공유)은 v2다

**근거.** PR #647로 토큰이 Keychain으로 옮겨져도 Keychain access group은 같은 기기 앱 간 공유라 워치에는 닿지 않는다 — 전달 경로는 WCSession뿐이고, 워치가 직접 통신하려면 서버 하트비트/리스(미발행 신뢰성 계획)까지 선행돼야 12h `AUTO_CLOSED` 유실을 막는다. 1차 릴레이 모델(D1)이 이 전부를 회피한다.

## D10 · App Intents 과목 미지정 시작의 기본값은 「최근 과목」이다

(기능 자체는 D4로 entry-points PRD 소관 — 결정만 여기 기록한다.) 인텐트로 과목 없이 시작하면 최근 사용 과목으로 시작하고, 완료 후 변경을 허용한다.

**근거.** 음성·단축어 시작의 가치는 마찰 0인데 매번 과목을 묻으면 그 가치가 죽는다. 잘못 붙은 과목은 완료 후 수정이 싸다.

## D11 · 워치 발 시작 시 Live Activity는 폰의 다음 포그라운드에서 표시한다

백그라운드 즉시 표시를 시도하지 않는다. 로컬 알림 대체 고지(안 ②)·push-to-start(안 ③)를 쓰지 않는다.

**근거.** `Activity.request`는 포그라운드 전용이고, push-to-start(iOS 17.2+)는 APNs 서버 발송이 필요해 「백엔드 변경 0」(D1)과 충돌한다. 결정적으로, 워치 발 시작 사용자는 그 순간 **워치를 보고 있다** — 폰 잠금화면 LA의 한계 가치가 낮다.

**뒤집을 신호.** 워치 발 세션의 이탈률이 폰 발보다 유의미하게 높고 원인이 "폰에 타이머가 안 보여서"로 좁혀지면 안 ②(로컬 알림)부터 재검토한다.

## D12 · 완료 시 워치에는 집중 시간 + 햅틱만 — 코인·결과 상세는 보류

**근거.** 서버 저장이 fire-and-forget(`sessionSaveVerdict.ts`)이라 코인 확정값이 완료 순간보다 늦게 도착한다. 지연 처리 UX(대기·재시도)가 까다롭고, 틀린 코인 숫자를 잠깐이라도 보여주면 금융성 숫자에 대한 신뢰가 깨진다. v1.1 후보로 남긴다.

## D13 · 워치 명령 킬스위치는 페이즈 1 필수다 (R16)

OTA 배포 가능한 폰 쪽 JS 플래그로 워치 명령 처리를 차단할 수 있어야 한다. 꺼진 동안 워치는 안내 화면만 표시한다.

**근거.** 워치 앱 바이너리는 OTA 회수가 불가능하다 — 사고 시 유일한 대응 수단이 폰 쪽 차단이다. hot-updater가 이미 붙어 있어(`@hot-updater/react-native`) 구현 비용이 플래그 하나 수준.

## D14 · QA는 실물 Apple Watch로 한다 — 착수 전 기기 확보

**근거.** Maestro는 watchOS를 지원하지 않고, 시뮬레이터는 WCSession wake·force-quit 거동을 실기기와 다르게 재현한다. D3의 스파이크ⓐ 자체가 실기기 없이는 무의미하다. **오너 액션: 테스트용 Apple Watch 확보(페어링 iPhone 포함).**

## D15 · 완료 화면에 캐릭터 스냅샷을 재사용한다 — 페이즈 1 스트레치

App Group에 이미 저장되는 캐릭터 스냅샷(Live Activity용)을 워치 완료 화면에 표시한다. 일정에 걸리면 잘라도 되는 스트레치 항목.

**근거.** 제네릭 타이머 얼굴은 gromo다움이 없다. 자산이 이미 App Group에 있어 비용이 작고, 완료 순간(보상 감정의 정점)에 캐릭터가 있는 것이 리텐션 루프와 정합한다.
