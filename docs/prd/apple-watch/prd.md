# Apple Watch 컴패니언 — PRD

> 정책 충돌 시 `policy.md`가 정본이다 (D1~D15). 이 문서는 「왜 · 무엇을」을 다룬다.
> 코드 사실은 2026-08-17 `main` 기준 전수 조사 결과다 (파일:라인 인용).

## 1. 배경과 문제

gromo의 핵심 루프는 집중 세션인데, **세션 중 유일한 조작·확인 수단이 폰이다.** 여기엔 구조적 모순이 있다:

- 집중 세션의 목적은 **폰을 내려놓게 하는 것**이다. 실드(`ManagedSettingsStore`)가 다른 앱을 차단하는 이유도 그것이다.
- 그런데 남은 시간을 확인하려면, 세션을 끝내려면, 잠깐 정지하려면 **폰을 다시 집어야 한다.** 폰을 집는 순간 알림·홈 화면이 보이고, 차단이 막아주지 못하는 이탈(그냥 폰을 만지작거리는 행위)이 시작된다.
- 세션을 시작할 때도 마찬가지다 — 책상에 앉아 "이제 집중하자"는 순간 폰을 열어 앱을 찾고 과목을 고르고 시작을 눌러야 한다.

Apple Watch는 **폰을 집지 않고 세션을 확인·제어할 수 있는 유일한 표면**이다. 그리고 우리는 이미 절반쯤 와 있다: 폰 앱은 세션 시작 시 Live Activity를 띄우고 있고(`app/ios/Widget/WidgetLiveActivity.swift`, `GromoFocusAttributes`), watchOS 11+ 기기는 iOS Live Activity를 **Smart Stack에 자동 미러링**한다. 즉 최신 워치 사용자는 이미 손목에서 타이머를 *볼 수는* 있다 — 하지만 시작·정지·종료는 전혀 못 한다.

### 1.1 용어

| 용어 | 뜻 |

## 2. 목표 / 비목표

### 2.1 목표

1. **세션 중 폰을 집을 이유를 없앤다.** 경과/남은 시간 확인·일시정지·종료가 손목에서 된다.
2. **세션 시작도 손목에서 된다.** 과목을 고르고 시작하면, 폰은 주머니 속에서 실드를 걸고 마커를 연다.
3. **세션의 단일 진실 원천(SoT)은 폰에 남긴다.** 워치는 리모컨 + 디스플레이다. 서버 계약·저장 로직·실드 로직은 폰 앱이 계속 소유한다 → 1차 릴리즈의 **백엔드 변경 0**을 노린다.
4. **Live Activity의 「앵커 + 자체 갱신」 원리를 재사용한다.** 앵커 시각만 주면 OS/수신자가 스스로 튀는 모델을 워치 표시에 적용해 폰→워치 갱신 트래픽을 최소화한다. 단, 현행 LA 구현(`ContentState`가 `startedAt` 하나)은 그대로 못 쓰고 R4 스키마로 확장한다 (§4.2).
5. **시작 표면을 넓힌다 (확장 채택분, 2026-08-17).** 헤드리스 엔진 위에 컴플리케이션(페이즈 2)을 얹어 손목에서의 진입 장벽을 없앤다. 같은 엔진을 딛는 홈스크린 위젯·Siri/App Intents는 별도 PRD로 진행한다 (`docs/prd/entry-points/`, policy D4).

## 3. 사용자와 시나리오

### 3.1 핵심 시나리오

**S-1. 폰으로 시작하고 손목으로 산다 (주 시나리오)**
폰에서 평소처럼 세션 시작 → 폰을 엎어둠 → 워치를 들면 현재 과목·경과(또는 남은) 시간·정지 버튼이 보임 → 공부 끝, 워치에서 「종료」 → 폰 앱이 정산·마커 종료를 수행 → 워치에 완료 요약(집중 시간)과 햅틱.

**S-2. 손목에서 시작한다**
책상에 앉음, 폰은 가방 속 → 워치에서 gromo 열기 → 최근 과목 목록에서 선택 → 시작 → WCSession이 폰 앱을 (백그라운드) 깨움 → 폰이 실드 적용 + 마커 시작 → 워치는 타이머 표시로 전환. Live Activity는 iOS 제약상 이 시점에 못 뜨고 **폰이 다음 포그라운드가 될 때 표시**된다 (§4.3).

**S-3. 폰이 안 닿는다 (경계 시나리오 — 1차 미구현 확정, policy D7)**
S-2에서 폰이 꺼져 있거나 통신 불가 → 워치는 **즉시 실패**하고 「iPhone과 연결한 뒤 시작할 수 있어요」를 표시한다. 로컬 임시 시작·큐잉·소급 반영은 하지 않는다 — 워치가 임시 SoT가 되어 D1과 충돌하고 서버 `startedAt` 클램프와 정면 충돌하기 때문 (근거·뒤집을 신호는 D7).

**S-4. 세션 중 잠깐 자리를 뜬다**
워치에서 「일시정지」 → 폰의 정지 상태와 동기화(정지 누적은 현행 로직대로 `totalDistractionSeconds` 차감 — `app/src/screens/focus/blockPause.ts`) → 돌아와서 워치로 재개.

### 3.2 유저 스토리

- 사용자로서, **손목에서 남은 시간을 봐야** 시간 확인을 핑계로 폰을 열지 않는다.
- 사용자로서, **폰을 꺼내지 않고 세션을 시작해야** "시작 장벽" 때문에 세션을 안 여는 일이 줄어든다.
- 사용자로서, **워치로 종료해도 폰으로 종료한 것과 똑같이 기록·코인이 처리돼야** 어느 쪽으로 조작할지 고민하지 않는다.
- 팀으로서, **워치 발 세션의 비중과 완료율을 알아야** 페이즈 2 우선순위 등 Apple Watch 후속 투자를 정한다. (Wear OS 투자는 iOS 계측으로 판단할 수 없다 — §5의 Android 별도 계측·조사)

## 4. 기능 요구사항

### 4.0 한눈에

| # | 요구사항 | 비고 |
|---|---|---|
| R1 | watchOS 앱 타겟(SwiftUI)이 기존 `ios/` 프로젝트에 추가된다. 번들 ID `com.oneorthree.gromo.watchkitapp` | 서명은 §6.1 규칙: **Debug = Automatic**(개발·실기기 스파이크용, 수동 development 프로파일 없음), **Release = 수동**으로 fastlane `DIST_PROFILES`에 편입 |
| R2 | 워치는 진행 중 세션의 과목·모드·상태(집중/휴식/정지)·시간을 표시한다 | 틱은 워치 로컬 렌더 — 폰은 상태 변화 시에만 전송 (R4) |
| R3 | 워치에서 일시정지·재개·종료가 가능하고, **기록·코인·통계 결과가 폰 조작과 동일**하다. 결과 화면·모달은 폰이 다음 포그라운드가 될 때 표시 | 정지는 현행 로컬 정지 의미론 유지 (서버 API 없음). 종료 명령 미도달 시 워치는 "종료됨"을 단정하지 않고 「종료 대기」를 표시한다 (§4.2). **지연 종료는 명령의 `issuedAt`을 종료 시각으로 보존**한다 — 서버 PATCH는 `endedAt`을 수신 시각 기준으로 클램프하므로(`FocusService.java:833-835`, 5분 창) 늦게 재생된 종료를 그대로 PATCH하면 미연결 구간까지 적립된다. 클램프 창을 넘긴 종료는 **PATCH 대신 마커 취소 + 정확 구간 POST 저장**으로 처리 — `uploadFocusBlock`의 기존 클램프 창 판정·`onMarkerStillOpen` 취소 경로를 그대로 재사용한다. **미확인 종료 명령은 워치의 계정·세션별 영속 아웃박스에 보존**한다 — 메모리 큐면 재연결 전 워치 프로세스 종료 시 issuedAt과 함께 유실돼 폰 세션이 계속 적립된다. 폰 ack 수신까지 보존하고 재기동·재연결 시 재전송(commandId 멱등이 중복을 막는다) |
| R4 | 폰↔워치 동기화는 WCSession으로 하고, 전달하는 것은 틱이 아니라 **상태 스냅샷**이다 — 최소 필드: 세션 id·**`accountId`**·과목·모드·목표 시간·현재 페이즈와 페이즈 anchor 시각·**뽀모도로는 집중·휴식 페이즈 길이와 세트 구성(현재 세트 포함)**·`pausedAt`·정지 누적·revision | 「앵커 시각 + 수신자 자체 갱신」 원리는 Live Activity와 같되, **현행 LA 구현은 재사용 불가** (§4.2). 페이즈 길이가 없으면 목표 시간·anchor만으로는 **휴식 스냅샷의 남은 시간을 워치가 계산할 수 없다**(폰은 `pomodoro.focusMin/breakMin`을 따로 쓴다 — `FocusSessionScreen.tsx:155`). 스냅샷에는 **이탈 크레딧 상한 도달 예정 시각도 포함**한다 — 폰 의미론은 세션당 8시간 상한(`AWAY_CREDIT_CAP_S`)에서 전진을 멈추는데 워치 앵커 렌더가 이를 모르면 8시간 넘는 단절에서 워치 표시가 폰 SoT보다 앞서 달리다 재연결 순간 뒤로 점프한다. 워치는 그 시각에 진행 표시를 동결하고 낡음(연결 필요)을 표시한다(상한 자체는 현행 유지 — 특성화로 고정된 의미론) |

### 4.1 전제 리팩토링 — 세션 로직의 화면 탈출 (가장 큰 공사)

현재 세션 로직 전체(타이머 틱·정산·마커 회전·실드 토글·업로드)는 **1,792줄짜리 화면 컴포넌트가 소유한다** (`app/src/screens/focus/FocusSessionScreen.tsx` — 틱 `:490-503`, 실드 `:542-556`, 정산 `:645`). 별도 훅·스토어가 없다. 더 정확히 말하면 **현재 SoT는 화면 안의 React ref들**이다 — 5초 주기 영속 레코드에는 모드·목표·뽀모도로 설정·페이즈·정지 상태가 없고(`app/src/screens/focus/types.ts:22`), 프로세스가 죽으면 `OrphanFocusSettler`는 세션을 **재개하는 게 아니라 마지막 체크포인트에서 종료 정산**한다. 이 구조에서는:

- 워치가 보낸 「시작」 「종료」를 **화면이 떠 있지 않으면 처리할 주체가 없다.**
- 폰 앱이 백그라운드로 깨어나도 RN 화면은 마운트되지 않는다.
- 재연결한 워치에 보낼 **권위 있는 상태 자체가 존재하지 않는다.**

따라서 워치 연동의 선행 조건은 단순한 "화면 탈출"이 아니라: **① 버전이 붙은 영속 세션 상태 머신**(모드·목표·페이즈·정지 포함, 죽었다 살아나도 재구성 가능) + **② 정산 저널** + **③ 그 위의 헤드리스 엔진**(백그라운드 콜드 스타트에서 UI 없이 부팅 가능) + **④ 네이티브 명령 인박스**(WCSession delegate가 받은 명령을 JS 부팅 전에 영속화)다. 화면은 그 엔진의 뷰가 된다. 이 리팩토링은 워치 기능과 별개 티켓·별개 PR로 먼저 나가야 하고, 기존 동작의 회귀 없음을 특성화 테스트로 먼저 잡은 뒤 자체 검증해야 한다. *규모 산정과 설계는 HLD/LLD에서.*

### 4.2 미러링 (R2·R4)

경과시간은 서버에 없다 — 서버가 아는 것은 마커의 `startedAt`뿐이고 그마저 정지·휴식이 반영되지 않은 벽시계 값이다(`back/…/focus/service/FocusLiveInfoLookup.java:46-69`). 진실은 폰 로컬 틱(`setInterval` 1초 + `Date.now()` 델타 보정, `FocusSessionScreen.tsx:269-290`)에 있다.

그래서 미러링은 **서버 경유가 아니라 폰→워치 직접 전달**이고, 전달 단위는 틱이 아니라 상태 스냅샷이다: 세션 시작·정지·재개·휴식 전환·종료 시에만 WCSession으로 스냅샷을 보내고, 워치는 받은 앵커 시각 기준으로 스스로 튄다. 「앵커 + 수신자 자체 갱신」 원리는 기존 Live Activity와 같지만, **현행 LA 구현을 그대로 재사용할 수는 없다** — 지금 LA는 항상 `Date()`부터 증가하고(`ScreenTimeModule.swift:831`) `ContentState`가 `startedAt` 하나뿐이라(`WidgetLiveActivity.swift:17`) 일시정지·카운트다운·뽀모도로 휴식을 표현하지 못한다. 스냅샷 스키마는 R4의 필드 목록대로 신설하고, LA의 `ContentState`를 같은 스키마로 확장하는 것은 **페이즈 0 작업**이다 (D3-ⓑ · §2.3 — 정지 중 LA가 계속 증가하는 현행 부정확도를 워치 코어 착수 전에 해소).

**신선도·수렴 규칙**: 스냅샷에는 revision이 붙는다. ⚠️ **단순히 오래됐다는 이유로 타이머를 숨기지 않는다** — 스냅샷은 상태 변화 시에만 오므로, 상태 변화 없이 오래 도는 정상 세션은 반드시 "낡은" 스냅샷을 갖는다. 앵커 기반 표시는 그 자체로 계속 정확하므로 유지하고, 「동기화 중」으로 바꾸는 것은 **재연결 검증에서 revision 불일치가 확인됐을 때뿐**이다(도달 불가 구간에는 기존 타이머 유지 + 필요 시 연결 끊김 배지). 재연결 시 **진실은 항상 폰의 영속 상태 머신**(§4.1)이다 — 폰 쪽 세션이 이미 죽어 정산됐다면 워치는 그 결과(종료됨)로 수렴한다. 종료 명령이 폰에 닿지 못한 경우 워치는 「종료 대기」를 유지하고, 로컬로 "종료됨"을 단정하지 않는다 (R3).

### 4.3 워치 단독 시작과 실드 (R5~R7)

실드는 RN 브릿지를 경유해 **메인 앱 프로세스 안에서만** 걸린다(`ScreenTimeModule.swift:595`, 호출부 `FocusSessionScreen.tsx:542-548`). 워치는 폰의 Screen Time 설정을 직접 만질 수 없다. 그러므로 워치 발 시작의 성립 조건은 "폰 앱을 깨워 실드를 걸게 하는 것"이고, 실패 경로가 반드시 남는다 (폰 전원 꺼짐·통신 두절·FamilyControls 권한 미승인 `ScreenTimeModule.swift:604-607`).

현행 구조에서 실드 적용 여부(`shieldedRef`)는 세션 이탈 정책까지 가른다(`FocusSessionScreen.tsx:537-545`). 워치 발 세션이 실드 없이 돌면 같은 규칙의 "실드 실패 경로"로 떨어지는 것이므로 **새 정책을 만들지 않는다** — 다만 사용자가 몰라서는 안 되므로 R7이 워치 표시를 요구한다. 폰 도달 불가 시는 **즉시 실패 + 안내**로 확정 (D7, S-3).

**명령 멱등성과 순서.** 현행 종료 가드는 메모리의 `finishedRef`뿐이고(`FocusSessionScreen.tsx:793`) `POST /focus-session/start`에 클라이언트 멱등키도 없다(`focusApi.ts:130`) — R11(서버 무변경)을 지키는 한 **중복·역순 방어는 전적으로 폰 엔진의 몫**이다. 워치↔폰 명령에는 `commandId`(멱등)·`focusSessionId`·`expectedRevision`·**`issuedAt`/`expiresAt`(처리 기한)**이 붙고 — **`focusSessionId`는 서버 마커 id가 아니라 폰 엔진이 부작용 전에 생성·저널링하는 로컬 세션 ID다**(비어 있지 않음 보장). 서버 마커 id는 별개의 nullable 필드로, 마커 실패·응답 유실 세션에서도 스냅샷·명령·계측(`focus_session_id`)이 끊기지 않는다, 종료된 세션에는 tombstone을 남겨 늦게 도착한 정지/시작 명령을 거절한다. **시작은 원자적이어야 한다**: ⓪ 실드 적용 **전에** 저널에 `starting` 의도를 write-ahead 기록 → ① 실드 적용 → ② 마커 시작·세션 커밋·응답 `sessionId` 저널 기록. 실드 성공 직후 프로세스가 죽으면 실드는 남는데 롤백 코드는 못 돌므로, **다음 부팅에서 저널의 미완료 `starting`을 발견하면 실드를 해제**하고 워치에 실패를 통지한다. 마커 시작의 **응답 유실**(서버 커밋 후 id 미기록)은 재시도로 복구할 수 없다 — 같은 `startedAt` 재시도에 현행 서버는 기존 마커를 유지한 채 `sessionId=null`을 반환한다(`FocusService.java:781-786`). 이 경우 재시도하지 않고 해당 세션은 마커 없이 진행하며(종료는 POST 저장), 잔여 마커는 12시간 스윕이 한계다(서버 무변경 v1의 수용 리스크 — v2에서 멱등키 서버 지원과 함께 재검토). 만료 폐기는 **명령별 정책**이다 — **`start`만 만료 폐기 대상**이고, **`end`는 만료 없이 영속 재생**한다(늦은 종료는 R3의 issuedAt 보존 경로로 정확히 정산되므로 폐기하면 오히려 세션이 계속 적립된다). `pause`/`resume`은 만료 대신 `expectedRevision` 불일치로 거절된다. **특히 `start`는 만료가 필수다** — 네이티브 인박스가 명령을 받았는데 JS 콜드 스타트가 늦으면, 워치가 이미 타임아웃 실패를 표시한 뒤에 폰이 영속 명령을 뒤늦게 처리해 사용자 모르게 세션·실드가 켜지는 "유령 시작"이 생긴다. 엔진은 처리 시점에 만료된 명령을 폐기한다. **응답 유실은 실패 확정이 아니다** — 명령이 커밋된 뒤 마지막 WCSession 응답만 유실되면 워치의 타임아웃과 폰의 활성 세션이 어긋난다. 워치는 타임아웃을 「실패」로 단정하지 않고 **「확인 중」 미확정 상태**로 표시하며, 폰의 다음 권위 스냅샷으로 수렴한다(세션 활성 → 타이머 전환, 비활성 → 그때 실패 확정). 보상 취소는 하지 않는다 — 커밋된 시작을 응답 유실을 이유로 되돌리면 폰 SoT(D1)와 충돌한다. 동시 조작(워치 정지 vs 폰 종료)은 엔진이 revision으로 중재한다. 상세는 LLD.

**이미 세션이 활성일 때의 워치 「시작」**은 새 세션 생성이 아니라 **현재 세션의 미러로 전환**이다 (서버 마커 유저당 1개·엔진 단일 세션 원칙의 귀결).

**실드 실패 세션의 이탈 정책은 엔진이 소유한다.** 현행 이탈 정책은 마운트된 화면이 `AppState`의 background 전환을 관측해야 발동하는데(`FocusSessionScreen.tsx:931-950`), 워치 발 세션은 백그라운드에서 화면 없이 시작되므로 그 관측 자체가 존재하지 않는다 — R7의 표시만으로는 「실드 없는 무감시 세션」을 막지 못한다. 따라서 이탈 정책 관측(AppState·타임아웃)은 D2 헤드리스화에서 **화면이 아니라 엔진의 책임으로 이관**하고, 이관 전까지 워치 발 시작은 **실드 적용 실패 시 시작을 거절**한다(워치에 실패 사유 표시). 상세 정책은 policy D2 보강분·LLD.

### 4.4 인증 (R11의 근거)

토큰은 현재 AsyncStorage 평문(`gromo:accessToken`, `app/src/types/storage.ts:7-8`)이고 App Group·Keychain에 없다. **단, 열린 PR #647(GROMO-965)이 토큰을 expo-secure-store(Keychain, `AFTER_FIRST_UNLOCK_THIS_DEVICE_ONLY`)로 이전 중**이라 이 서술은 곧 낡는다. 그래도 결론은 바뀌지 않는다 — Keychain access group 공유는 **같은 기기의 앱 간** 메커니즘이라 별개 기기인 워치에는 닿지 않고, 워치로 자격증명을 보내는 길은 WCSession 전달뿐이며 이는 보안 검토가 따르는 별도 과제다. 1차는 **모든 서버 통신을 폰이 대행**하는 릴레이 모델로 이 문제를 통째로 회피한다. 워치 단독 통신은 v2로 확정 (D9).

## 5. 성공 지표

모든 지표는 GA4 이벤트에서 나온다 (서버 변경 없음 — R11). **이벤트 계약**: 발원지만으로는 시작↔완료를 이을 수 없으므로(현행 이벤트에 세션 식별자 없음 — `analyticsEvents.ts:109`), 세션 관련 전 이벤트에 **익명 `focus_session_id` + `start_origin`('phone'|'watch'|'intent'|'widget') + `command_origin`**을 싣는다. `isPaired`는 "워치 앱 설치·지원 watchOS·도달 가능"을 뜻하지 않으므로 **보급률의 상한 근사치**로만 해석한다 — 워치 앱 출시 후에는 `isWatchAppInstalled`를 함께 계측해 분모를 정교화한다.

**워치 로컬 실패의 전송 경로.** 폰 미도달·타임아웃 실패는 정의상 폰이 관측할 수 없다 — 그 순간의 관측자는 워치뿐이다. 워치에 분석 SDK를 넣지 않는 대신, **워치가 실패 이벤트를 로컬에 영속화했다가 다음 WCSession 연결 때 폰으로 전달하고 폰이 GA4로 대리 발행**한다(재수렴 큐). 이 경로가 없으면 위 「실드 실패 시작률」·wake 실패 분포에서 가장 중요한 미도달 표본이 통째로 빠진다. **큐 레코드는 발생 당시의 `accountId`·`occurredAt`을 보존**한다 — GA4 발행이 전송 시점 로그인 계정으로 귀속되므로(`UserContext.tsx:86` `setUserId`), 재연결 전에 계정 전환·날짜 경과가 끼면 실패가 엉뚱한 계정·날짜로 잡힌다. 대리 발행 시 이벤트 파라미터에 `occurredAt`을 싣고, **계정 불일치 건은 발행하지 않고 폐기**한다(교차 계정 오귀속보다 표본 손실이 낫다 — 폐기 건수는 별도 카운트). 큐 상세(중복 방지 이벤트 id 포함)는 LLD.

| ~~사용자가 폰 앱을 스와이프 강제종료해 두면 WCSession이 앱을 재기동하지 못함~~ → **실측으로 반박됨** (2026-08-18 스파이크 GROMO-1596, SE 2·watchOS 10.6.2 + iPhone 16 Pro Max): 포그라운드·suspended·**강제종료 3상태 모두 성공 100%, RTT ~200ms** — 강제종료도 OS가 백그라운드 재기동해 응답. suspended는 기존 프로세스가 그대로 응답(재기동 불필요) | 리스크 강도를 하향하되 계측(§5 성립률)은 유지 — 표본이 기기 1대·1회차라 저전력 모드·저장공간 부족 등 변수는 남는다. **JS 부팅 시간은 미측정**(스파이크의 로드 알림이 브리지리스 RN에서 미발화) — D2-④ 인박스 설계는 유지하되, **측정은 페이즈 1로 미루지 않고 페이즈 0 종료 게이트(§2.3-ⓔ)로 남는다**: 헤드리스 엔진(ⓓ) 완성 직후 「명령 발신→JS 엔진 처리 완료」를 실측하고 합격 SLO를 확인해야 워치 코어에 착수한다 |
| **백그라운드로 깨어난 폰의 RN/JS 엔진 기동 지연·시간 제약** — iOS엔 Headless JS가 없어 콜드 스타트 수 초 + 제한된 실행 시간 안에 부팅·처리 완료 보장 없음 | §4.1 ④ 네이티브 명령 인박스로 명령을 먼저 영속화(유실 방지) + wake 소요 계측(§5) + 예산 초과 시 「네이티브 선(先)실드 → JS 후처리」 최적화. 착수 전 실기기 스파이크 필수 |
| **워치 앱 바이너리는 OTA 회수 불가** — 사고 시 되돌릴 수단 없음 | 폰 쪽 **워치 명령 처리 킬스위치**(App Group 네이티브 영속 플래그, 인박스 수신 시점 평가 — R16·D13 2차 개정)를 페이즈 1에 포함 — 끄면 워치는 안내 화면만 표시. OTA는 플래그 갱신 수단일 뿐, JS 부팅 전 네이티브 게이트가 필수 계약 |
| 실드 없는 워치 발 세션이 "차단 안 되는 집중"의 뒷문이 됨 | 이탈 관측 엔진 이관 전까지 워치 발 시작은 실드 실패 시 **거절** (§4.3·D2) + R7 사유 표시 + 실드 실패 시작률 계측 (§5) |
| 워치 보급률이 낮아 투자 대비 효과 미달 | 계측 먼저 (§5 워치 발 비중). 이 수치의 용도는 **Apple Watch 후속 투자(페이즈 2 우선순위 등)로 한정** — iOS 모집단만 관측하므로 **Wear OS 판단에는 못 쓰고**, 그건 §5의 Android 사용자 대상 별도 계측·조사로 (컴플리케이션은 페이즈 2 확정) |
| 수동 서명 타겟 7→8개 관리 부담 | 기존 체계에 1개 추가일 뿐 새 체계는 아님. testflight.sh·Fastfile 매핑 갱신을 체크리스트화 |
| **백그라운드 페이즈 경계에 폰 실행 주체 없음** — suspend 중 카운트다운 목표·뽀모도로 경계 도달 시 정산·다음 페이즈·완료 햅틱이 지연 | R8의 2층 모델로 대응: ① 권한 의존 **워치 로컬 알림 전 경계 선예약**(사용자 신호) ② 최선 노력 wake + **관측 시점의 경계 벽시계 소급 리플레이**(SoT 수렴 — 지연돼도 틀리지 않음). 워치 wake는 스파이크(1596)로 3상태 검증, 남는 변수는 JS 기동(§2.3-ⓔ 게이트) |
