# 섬 상점 API — PRD

GROMO-1780 · 2026-09-12 · 상태: **설계 초안, 제품 정책 결정 대기**.

[정책](policy.md) · [구성 설계](high-level-design.md) · [상세 계약](low-level-design.md)

## 문제와 목표

개인 물고기로 내 꾸미기 상품을 사고, 섬 마을 포인트로 공동 테마와 음원을 산다. 같은 화면에 보여도
소유자와 차감 지갑이 다르다. 구매를 여러 서버 쓰기로 나누면 돈만 빠지거나 소유권만 생길 수 있다.
이번 설계는 다섯 조회·구매 계약과 Data의 원자 주문 경계를 정의한다. 기존 코인을 물고기로 이름만
바꿔 노출하거나 현재 물고기/공동 포인트가 구현됐다고 주장하지 않는다.

## 범위 — 5개 계약

|ID|method/path|사용자 행동|
|---|---|---|
|wallet|GET `/islands/{islandId}/shop/wallets`|본인 물고기와 현재 섬 포인트 확인|
|catalog|GET `/islands/{islandId}/shop/products`|내 꾸미기/섬/소리 탭 상품 탐색|
|product|GET `/islands/{islandId}/shop/products/{productId}`|가격·보유·선행 조건 확인, 개인 미리듣기|
|buy|POST `/islands/{islandId}/shop/orders`|가격 확인 후 하나의 상품 구매|
|orders|GET `/islands/{islandId}/shop/orders`|본인 또는 현재 섬 공동 구매 내역|

요구사항:

- 지갑 주인은 개인=`userId`, 공동=`islandId`다. 요청자는 검증 JWT subject이며 앱이 owner/가격/통화를 고르지 않는다.
- 상품의 정본 정의가 종류·소유자·통화·선행 상품/시설을 정한다. 개인은 fish, 공동은 village_points만 사용한다.
- 현재 섬 context와 membership을 정본으로 확인한다. 앱의 선택 섬 문자열이나 이전 BFF 응답만 믿지 않는다.
- 구매는 자동 착용·테마 적용·음악 재생을 하지 않는다. [외양 설계](../island-appearance/prd.md)와 재생 도메인이 별도 요청을 받는다.
- 주문·차감·원장·소유권·목록 버전·receipt·outbox는 Data 한 트랜잭션이다. 이미 산 상품은 새 키로 다시 요청해도 다시 차감하지 않는다.
- 개인 wallet/inventory 이벤트는 본인만, 공동은 해당 섬 주민만 받는다. 개인 잔액이나 다른 사람의 구매 목록이 섬 토픽으로 나가지 않는다.
- 방송기 없는 음원 구매, 선행 선체 미보유 구매, 다른 섬 자산에 대한 소비를 거절한다.
- 가격은 배포 코드의 목업 상수가 아닌 서버 설정의 버전으로 관리한다. 아직 승인되지 않은 경제 설정은 운영에서 활성화하지 않는다.

## 제외와 선행 결정

기존 코인/보유품 승계, 환전율, 신규 초기 잔액·상품 가격·무료 음원, 공동 소비 권한은 미결이다.
무료 지급·새 경제 초기화·기존 자산 삭제·운영 활성화를 이번 문서로 승인하지 않는다.
물고기 획득·초기건설 기여·퀘스트 지급은 해당 정산 도메인에서 같은 지갑/원장 경계를 사용한다.
실물 결제·환불·소모품 수량·상품 선물·음원 직접 업로드는 이 다섯 계약에 없다.

## 출처와 현재 상태

원본은 1739의 화면별 API 스펙 v0.3-proposed, 2026-09-11 13:41:45 KST, wallet/catalog/product/buy/orders.
사용자 결정에 따라 `/v1`을 제거했다. 원본 숫자500/1500/20/30은 응답 형태 설명용 목업이며 운영값이 아니다.

기존 [재화 문서](../currency/prd.md), [아키텍처 결정](../../architecture/decisions.md) A4/A9/㉼를 대조했다.
1750 공통 봉투·receipt·cursor와 1754 이벤트 계약은 별도 설계 브랜치의 선행 문서다. 아직 이 기준
브랜치에 없는 문서의 상대 링크를 만들지 않는다. 상세 동기화 항목은 LLD에 명시한다.

## 완료 판정과 검증

설계 산출물 네 파일을 갖추는 것과 티켓의 제품 정책을 확정하는 것은 다르다. 공동소비 권한·경제승계/
활성화 가 결정되기 전에는 설계 완료나 구현 ready로 표시하지 않는다.
구현 검증은 LLD의 동시 주문·다른 키 중복구매·가격변경·회원탈퇴·원장/receipt rollback·개인정보
수신 범위 시나리오가 기준이다. 이 문서 작업에서 코드·DB 변경이나 테스트 실행은 하지 않는다.
