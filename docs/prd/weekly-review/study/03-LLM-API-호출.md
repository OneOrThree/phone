# 3편 — "LLM을 호출한다"는 게 물리적으로 무슨 뜻인가

> 다이어그램: **`03-LLM-API-호출.drawio`** (페이지 2장: ① 호출 해부도 ② 왜 계산을 안 맡기나)

## 결론부터: 그냥 HTTP POST다

"AI를 붙인다"는 말이 거창하게 들리지만, 코드 관점에서는
**외부 REST API 하나를 호출하는 것**과 완전히 같다. 카카오 API나 FCM을
호출해 본 적 있다면 이미 아는 모양이다:

```
POST https://api.anthropic.com/v1/messages
Header: x-api-key: (발급받은 API 키)
        anthropic-version: 2023-06-01   ← API 버전 고정 (필수)
        content-type: application/json  (필수)
Body:   JSON (모델명 + 보낼 메시지 + 옵션)
  ↓ 수 초 후
응답:   JSON (모델이 생성한 텍스트 + 사용한 토큰 수)
```

모델은 우리 서버에 설치되는 게 아니다. Anthropic 서버에 있고, 우리는
요청을 보내고 결과를 받을 뿐이다. GPU도, 모델 파일도, ML 지식도 필요 없다.
Spring에서는 `RestClient`(또는 공식 Java SDK)로 다른 외부 API와 똑같이 부른다.

## 요청 해부도

우리 기능의 실제 요청은 이렇게 생겼다 (다이어그램 페이지 1과 대조하며 볼 것):

```json
{
  "model": "claude-sonnet-5",
  "max_tokens": 600,
  "system": "너는 몰입 습관 코치다. 아래 규칙을 지켜라:
    - 입력 JSON에 있는 숫자만 언급한다. 새 숫자를 만들거나 계산하지 않는다.
    - 비난하지 않는다. 잘한 점 하나를 먼저 짚는다.
    - 반드시 아래 JSON 스키마로만 응답한다: {\"interpretation\": string, \"actions\": [string, string]}",
  "messages": [
    {
      "role": "user",
      "content": "{ \"weekTotalMin\": 1163, \"deltaPct\": 27, \"goalMetDays\": 6,
                   \"dailyMin\": {\"월\":145, \"화\":190, \"수\":120, \"목\":205,
                                 \"금\":168, \"토\":240, \"일\":95},
                   \"longestSessionMin\": 98, \"prevRecordMin\": 82,
                   \"finishRate\": 0.73, \"badges\": [\"record\", \"goal5\", ...],
                   \"suggestionSeeds\": {\"rebalanceFromDay\": \"토\",
                                        \"rebalanceMin\": 60,
                                        \"longestGoalMin\": 100} }"
    }
  ]
}
```

(예시는 읽기 좋게 줄바꿈했지만, 실제 JSON 문자열 안에는 리터럴 줄바꿈이 못 들어간다 —
코드에서는 `\n` 이스케이프이거나, 자바 텍스트 블록으로 만든 문자열을 직렬화한 결과다.)

`suggestionSeeds`가 중요하다: "다음 주 행동 제안"에 들어갈 숫자(토요일에서 옮길
60분, 최장 세션 목표 100분)까지 **서버가 미리 계산해 입력에 담는다.** LLM이
제안 문장을 쓰다가 스스로 숫자를 지어내면 아래 검증 그물 ③에 걸리기 때문에,
제안에 쓸 숫자 재료도 전부 입력 쪽에 놓아 주는 것이다.

각 필드의 뜻:

| 필드 | 뜻 | 우리 기능에서 |
|---|---|---|
| `model` | 어떤 모델을 쓸지 | 품질/비용 균형으로 선택. 해석 한 문단이면 중간급이면 충분 |
| `system` | 모델의 역할·규칙 (개발자가 박는 지시) | **"계산 금지, 입력에 있는 숫자만, JSON으로만"** — 안전장치의 절반이 이 문장 |
| `messages` | 실제 입력 | 4단계에서 만든 **집계 JSON 그 자체**. 원본 세션 로그가 아니다 |
| `max_tokens` | 응답 길이 상한 | 폭주 방지 + 비용 상한. 해석+제안 2개면 600이면 충분 |

**토큰**은 LLM이 텍스트를 세는 단위다(대략 한국어 1글자 ≈ 1~2토큰, 영어 1단어 ≈ 1.3토큰).
요청과 응답의 토큰 수만큼 과금된다 — 그래서 "원본 로그 전체"가 아니라
"집계 JSON"을 보내는 게 비용에서도 이득이다(5편에서 계산).

## 응답 해부도

```json
{
  "content": [{ "type": "text", "text": "{\"interpretation\": \"목요일에 세 시간 가까이…\", \"actions\": [\"토요일 240분 중 60분을 일요일로 옮겨보기\", \"최장 98분, 다음 주 100분 한 번만\"] }" }],
  "usage": { "input_tokens": 812, "output_tokens": 236 },
  "stop_reason": "end_turn"
}
```

- `content[0].text` — 모델이 생성한 **텍스트**. 우리가 JSON으로 답하라고
  시켰으니 JSON *모양의 문자열*이 온다. 하지만 이건 어디까지나 모델이 쓴
  글이지 보장된 JSON이 아니다 → 그래서 검증이 필요하다(아래).
- `usage` — 이번 호출에 쓴 토큰. **비용 로그로 반드시 저장**한다.

## 왜 계산을 안 맡기나 (다이어그램 페이지 2)

LLM은 "다음에 올 가장 그럴듯한 단어"를 확률적으로 뽑는 기계다. 그 결과:

1. **산수를 틀린다.** "1163분 = 19시간 23분" 같은 변환을 시키면 가끔 틀린다.
   백 번 중 한 번이라도, 리포트에 틀린 숫자가 찍히는 순간 기능 전체의 신뢰가 죽는다.
2. **없는 사실을 지어낸다(할루시네이션).** "지난달보다도 늘었네요" 같은,
   주지도 않은 데이터에 대한 문장을 만들 수 있다.
3. **매번 다르게 답한다.** 같은 입력에도 문장이 달라진다 — 해석에는 장점(자연스러움),
   숫자에는 치명적.

그래서 역할을 자른다: **숫자가 들어가는 문장은 100% 서버 템플릿**(4단계에서 이미 완성),
**LLM은 확정된 숫자를 재료로 한 해석·제안만**. 정확히 말하면 보장 범위가 갈린다 —
**서버 템플릿 문장의 숫자는 틀릴 수 없다**(그냥 값 대입이니까). LLM 해석 문단은
"산수할 기회를 안 줌 + 아래 검증 그물"로 틀릴 **확률을 구조적으로 낮춘 것**이지
수학적 보장이 아니다. 그 잔여 위험을 받아주는 게 다음 절의 검증과 폴백이다.

## 응답 검증 4중 그물

모델의 응답은 "외부 입력"으로 취급하고 서버 검증을 통과해야만 저장한다:

1. **JSON 파싱** — 깨진 JSON이면 실패
2. **스키마 검증** — `interpretation`(문자열), `actions`(1~2개 배열) 있는지, 길이 상한
3. **숫자 대조** — 응답의 아라비아 숫자를 정규식으로 뽑아 **입력 JSON에 없는
   숫자가 있으면 실패**. 할루시네이션 숫자를 기계적으로 잡는 가장 싼 방법.
   솔직한 한계: "205분"을 "세 시간 가까이"로 풀어 쓰면 이 그물은 못 잡는다
   (한글 수사는 정규식 밖). 그래서 이 그물은 아라비아 숫자만 보고, 서버가
   시간 변환 파생값("3시간 25분")까지 집계 JSON에 미리 담아 허용 집합을 넓힌다.
   완전한 보장은 아니고 **안전장치의 한 층**이다 — 완전성은 층을 쌓아서 얻는다
4. **금칙 검사** — "폰 전체" 같은 금지 표현(정책상 "관리 중인 앱"만 허용) 필터

참고로 요즘 API에는 응답을 JSON 스키마로 강제하는 옵션(Structured Outputs)이
있어서 그물 ①·②를 크게 덜어준다 — 써도 되고, 그래도 ③·④ 검증은 유지한다
(스키마는 "모양"만 보장하지 내용은 보장하지 않는다).

실패하면 재시도 1회 → 또 실패하면 **폴백**: 해석 자리에 템플릿 문장
("이번 주 목표를 6일 지켰어요. 꾸준함이 기록을 만듭니다" 류)을 넣고 리포트는
정상 발행한다. `weekly_review.llm_status` 컬럼에 `ok / fallback`을 남겨
폴백률을 모니터링한다(5편).

## API 키는 어디에 두나

API 키 = 돈이 나가는 비밀번호. 코드·git에 절대 넣지 않고, 기존 gromo 방식대로
**시크릿 저장소(AWS Secrets Manager / 환경변수)** 에 두고 서버가 기동 시 주입받는다.
dev와 prod 키를 분리해 dev에서 폭주해도 prod 예산에 영향 없게 한다.
