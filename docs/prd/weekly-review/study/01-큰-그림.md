# 1편 — 큰 그림: 등장인물과 데이터가 흐르는 길

> 다이어그램: **`01-큰-그림.drawio`** (페이지 2장: ① 구성요소와 흐름 ② 한 주의 타임라인)

## 등장인물 5명

| 등장인물 | 정체 | 이 기능에서 하는 일 |
|---|---|---|
| **앱** | React Native (gromo) | 평소엔 몰입 세션을 기록해 서버로 보냄. 월요일엔 푸시를 받고 리포트 화면을 띄움 |
| **백엔드** | Spring Boot (기존 gromo 서버) | 이 기능의 주인공. 집계·채점·LLM 호출·저장·푸시 발송 전부 여기서 |
| **DB** | PostgreSQL | 원재료(`focus_session` 등 기존 테이블)와 완제품(새 `weekly_review` 테이블) 보관 |
| **LLM API** | Claude API (Anthropic, 외부 서비스) | 계산이 끝난 집계 결과를 받아 "해석 문단 + 다음 주 제안"만 생성 |
| **FCM** | Firebase 푸시 (이미 프로젝트에서 사용 중) | "주간 리포트 도착" 푸시를 앱으로 배달 |

핵심: **새로 등장하는 외부 서비스는 LLM API 하나뿐이다.** 나머지는 전부
지금 gromo에 이미 있는 것들이고, 우리가 새로 만드는 건 백엔드 안의 모듈 몇 개
(스케줄러 → 집계 → 채점 → LLM 클라이언트 → 저장 → 푸시)와 앱 화면 하나다.

## 데이터가 흐르는 두 개의 길

이 기능의 데이터 흐름은 시점이 다른 두 갈래로 나뉜다. 다이어그램 페이지 1에서
색으로 구분해 놨다.

### 길 A — 평소 (월~일, 이미 존재하는 흐름)

```
앱 (몰입 세션 시작/종료) ──> 백엔드 REST API ──> DB (focus_session 적재)
앱 (관리 중인 앱 사용량)  ──> 백엔드 REST API ──> DB (스크린타임 적재)
```

우리가 **손댈 게 없는** 길이다. 재료는 이미 매일 쌓이고 있다.
두 번째 줄(스크린타임)은 "폰 사용 감소" 뱃지·점수의 원천이다 — 이 데이터가
없는 사용자(권한 미허용 등)에게 그 축을 어떻게 처리할지는 prd.md 확정 대상.

### 길 B — 월요일 아침 (새로 만드는 흐름)

```
스케줄러(월 08:00) ─> 집계(SQL) ─> 채점(규칙) ─> LLM 호출(해석) ─> 저장 ─> FCM 푸시 ─> 앱
                        │            │              │
                        DB에서       점수·뱃지·      Claude API
                        지난 2주     한 줄 판정      (외부, 유일한
                        SELECT       (숫자 확정)      새 등장인물)
```

사용자가 푸시를 누르면 앱은 `GET /weekly-review/latest` 같은 API로
**저장돼 있는 완제품을 읽기만** 한다. 화면을 열 때 LLM을 부르는 게 아니라,
월요일 아침에 미리 만들어 둔 걸 꺼내 보여준다.

## 왜 "미리 만들어 저장"인가 (조회 시점 생성이 아니라)

처음엔 "화면 열 때 LLM 부르면 되지 않나?"라고 생각하기 쉽다. 안 되는 이유:

1. **속도** — LLM 응답은 수 초 걸린다. 화면 열 때마다 3~5초 로딩은 못 쓴다.
2. **비용** — 같은 주 리포트를 열 때마다 다시 생성하면 호출 수 = 열람 수.
   미리 만들면 호출 수 = 사용자 수 × 주 1회로 고정된다.
3. **일관성** — LLM은 같은 입력에도 매번 다른 문장을 낸다. 아침에 본 리포트와
   저녁에 본 리포트의 문장이 다르면 이상하다. 한 번 만들어 박제해야 한다.
4. **실패 격리** — LLM API가 장애여도 월요일 배치에서 폴백 처리하면 되고,
   사용자가 화면을 여는 순간에는 이미 완성본이 있다.

이 "미리 계산해서 저장해 두고, 조회는 읽기만" 패턴은 이름이 있다 —
**배치(batch) + 사전 계산(precompute)**. 주간 단위 기능이라 자연스럽게 이 패턴이 된다.

## 새로 생기는 것 목록

| 층 | 새로 만드는 것 |
|---|---|
| DB | `weekly_review` 테이블 (user_id, 주차, 점수, 뱃지, 템플릿 문장, LLM 해석, 상태) — Flyway 마이그레이션 1개 |
| 백엔드 | 스케줄러 1개, 집계/채점 서비스, LLM 클라이언트, 조회 API 1~2개 |
| 앱 | 리포트 화면 1개 (ui.html이 시안), 푸시 딥링크 라우팅 |
| 외부 | Anthropic API 키 발급 + 시크릿 보관 |

## 타임라인으로 보면 (다이어그램 페이지 2)

```
      월  화  수  목  금  토  일   │  다음주 월 08:00        월 09:12 (예시)
      ─────────────────────────   │  ───────────────        ─────────────
      세션 기록이 매일 쌓임         │  배치가 지난주를          사용자가 푸시를
      (길 A, 기존 기능)            │  집계→채점→LLM→저장       눌러 리포트 열람
                                  │  →푸시 발송               (읽기만, 즉시 뜸)
```

"지난주"의 경계는 KST 기준 **반개구간 `[월 00:00, 다음 월 00:00)`** — 구현에서는
이걸 UTC 타임스탬프로 변환해 조회한다("일 24:00"이라는 시각은 DB에 없다).
자정을 걸친 세션을 시작일에 줄지 날짜별로 쪼갤지는 prd.md 확정 대상.

발행 시각 08:00은 일요일 밤 세션이 들어올 **여유**이지 보장이 아니다 —
오프라인 기기의 늦은 업로드는 8시간을 넘길 수 있다. 마감 후 도착한 데이터를
무시할지(이번 안: 무시, 리포트는 박제) 별도 정책을 둘지도 prd.md에서 확정한다.
