# 1:1 문의 (Inquiry) — PRD

> 정책 충돌 시 `policy.md`가 정본이다. 이 문서는 「왜 · 무엇을」을 다룬다.

## 1. 배경과 문제

gromo에는 **사용자가 팀에 말을 걸 수 있는 창구가 하나도 없다.**

`app/src/` 전수 검색 결과 `문의` · `고객센터` · `FAQ` · `support` · `inquiry` · `mailto` · 카카오 채널 — **전부 0건**이다. 앱 안의 외부 링크는 `MenuScreen.tsx`의 개인정보 처리방침 · 서비스 이용약관 두 개뿐이고, 둘 다 팀 사이트의 정적 문서로 나간다. 백엔드에도 문의 관련 도메인이 없다.

그래서 지금 벌어지는 일:

- **사용자 쪽** — 타이머가 안 멈추거나 스크린타임 수치가 이상해도 알릴 데가 없다. 앱을 지우는 것 말고 할 수 있는 게 없다.
- **팀 쪽** — 버그 리포트가 들어오는 경로가 스토어 리뷰뿐이다. 리뷰는 재현 정보가 없고, 되묻기도 어렵고, 공개된 자리에 남는다.

### 1.1 용어

| 용어 | 뜻 |
|---|---|
| **문의** | 사용자가 팀에 보내는 질문 · 오류 신고 · 제안 |
| **담당자** | 문의를 받는 개발자 3명. 카드에 적히는 건 담당 영역(소유권)이 아니라 **어떤 문의에 어울리는지에 대한 성격 설명**이다 (D6) |
| **카테고리** | 문의 영역 3분할 — 집중·스크린타임 / 그룹·챌린지 / 계정·기타 |
| **오픈채팅방** | 담당자별 카카오톡 1:1 오픈채팅방. 실제 대화가 일어나는 곳 |
| **링크아웃** | 앱이 대화를 처리하지 않고 외부 채널로 내보내는 방식 |

## 2. 목표 / 비목표

### 2.1 목표

1. **사용자가 5초 안에 「어디에 말하면 되는지」를 안다.** 앱 안에서 창구를 찾을 수 있어야 한다.
2. **잘못된 사람에게 가지 않는다.** 각자의 성격 설명이 화면에 보여 사용자가 어울리는 담당자를 고른다.
3. **팀이 재현 가능한 버그 리포트를 받는다.** 되물을 수 있는 1:1 채널이면 충분하다.
4. **백엔드를 건드리지 않는다.** 서버 변경 0, 신규 테이블 0으로 출시한다.
5. **기대치를 미리 맞춘다.** 24시간 응대가 아님을 화면에서 먼저 알린다.

### 2.2 비목표 (명시적 범위 밖)

| 안 하는 것 | 이유 |
|---|---|
| 앱 내 실시간 메신저 | `policy.md` D1 — 반대편 화면이 필요하고 실시간 인프라가 없다 |
| 담당자 자동 배정 | D2 — 배정 상태를 소유할 서버가 없다 |
| 문의 상태 표시 (접수·확인중·답변완료) | D4 — 서버가 대화를 모르므로 진짜 상태를 만들 수 없다 |
| 관리자(어드민) 화면 | D1 — 답변은 카카오톡에서 한다 |
| 푸시 알림 | 알릴 상태 변화가 서버에 없다 (D4의 귀결) |
| 이미지 첨부 | 업로드 인프라가 아예 없다 (S3/presigned URL 0건). 스크린샷은 카톡방에서 붙인다 |
| FAQ · 도움말 문서 | 별도 기능. 이번 범위 밖 |
| 문의 이력 조회 | D4 — 카카오톡 대화방이 이력이다 |

## 3. 사용자와 시나리오

### 3.1 역할

| 역할 | 하는 일 |
|---|---|
| 사용자 | 문의 화면에서 카테고리와 담당자를 고르고 카카오톡으로 이동한다 |
| 담당자 (개발자 3명) | 자기 오픈채팅방에서 답한다. **앱에서는 아무것도 하지 않는다** |

### 3.2 핵심 시나리오

**S-1. 타이머가 안 멈춘다 (주 시나리오)**
집중 세션이 끝났는데 타이머가 계속 돈다 → 「전체」 탭 → 「계정 · 정보」의 `1:1 문의` → 「집중 · 스크린타임」 칩 선택 → 그 영역 담당자가 맨 위로 올라오고 「추천」 배지가 붙음 → 「카카오톡으로 문의하기」 → 확인 모달에서 목적지·대화 저장 위치 확인 → 카카오톡 오픈채팅방 열림 → 증상을 쓰고 스크린샷을 붙임.

**S-2. 어디에 물어야 할지 모르겠다**
친구 초대가 안 붙는데 이게 그룹 문제인지 계정 문제인지 모른다 → 문의 화면 진입 → 카테고리를 안 고르고 담당자 카드 3장을 훑음 → 「계정 · 결제 · 그 밖의 모든 것」 소개를 보고 3번 담당자 선택. **카테고리 선택은 필수가 아니다** (`policy.md` D6).

> ⚠️ **로그인 자체가 안 되는 사용자는 이 창구에 도달할 수 없다.** `App.tsx`는 `user`가 없으면
> `LoginScreen`이나 온보딩만 렌더하고 `RootNavigator`는 인증된 분기에서만 마운트되므로,
> 유일한 진입점인 「전체」 탭이 존재하지 않는다. **가장 도움이 필요한 사용자가 가장 확실하게
> 막히는 구조**다. 이 상태로 1차를 내기로 정했다 — `policy.md` **D14**(검토한 대안 B·C와
> 보류 근거 포함). 「문제가 없다」가 아니라 **「알고 미룬다」**는 뜻이고, 재검토 조건은
> policy.md 「뒤집을 때의 신호」에 걸어 뒀다.

**S-3. 카카오톡이 없다**
「카카오톡으로 문의하기」 → https 오픈채팅 URL이라 OS가 브라우저로 연다 → 카카오톡 웹 오픈채팅 화면 (D7).

### 3.3 유저 스토리

- 사용자로서, **앱 설정에서 문의 창구를 찾을 수 있어야** 오류를 만났을 때 앱을 지우지 않는다.
- 사용자로서, **누가 무엇을 담당하는지 보여야** 엉뚱한 사람에게 물어 시간을 버리지 않는다.
- 사용자로서, **외부로 나간다는 것과 대화가 어디 남는지 미리 알아야** 안심하고 누른다.
- 사용자로서, **응답이 즉시가 아님을 미리 알아야** 답이 늦어도 버려졌다고 느끼지 않는다.
- 팀으로서, **어느 영역 문의가 많은지 알아야** 다음에 무엇을 고칠지 정한다.

### 4.1 진입점 (R1)

`MenuScreen.tsx`의 「계정 · 정보」 섹션에 `SettingsRow`를 하나 추가한다. 기존 컴포넌트를 그대로 쓰므로 신규 UI 부품이 없다.

- 라벨 `1:1 문의`, 보조 텍스트 `궁금한 점 · 오류 신고`
- 아이콘 `chatbubble-ellipses-outline` (Ionicons)
- 위치: `계정 설정` 아래, `개인정보 처리방침` 위

### 4.2 문의 화면 (R2~R5, R10)

세로 순서: 안내 문단 → 카테고리 칩 → 담당자 카드 3장 → 하단 안내 박스.

`SettingsScaffold`(제목 `1:1 문의`)를 그대로 쓴다. 담당자 카드와 카테고리 칩은 이 화면 전용이므로 설정 feature 폴더인 `screens/settings/components/`에 콜로케이션한다 — 2곳 이상에서 쓰이면 그때 전역 `components/`로 승격한다 (`app/.claude/CLAUDE.md` 배치 규칙).

**카테고리 선택 동작 (R4).** 선택된 카테고리의 담당자 카드가 목록 맨 위로 이동하고 「추천」 배지가 붙는다. 나머지 카드는 사라지지 않는다 — 「직접 지목」(D2)이 유지돼야 하므로 항상 3장 다 보인다. 같은 칩을 다시 누르면 선택이 해제되고 원래 순서로 돌아간다.

### 4.3 이동 확인 (R6~R9)

`ConfirmCardModal`을 쓴다. 제목 `카카오톡으로 이동할까요?`, 본문에 담당자 이름 · 「1:1 오픈채팅방이 열려요」 · 「대화 내용은 카카오톡에 저장되고, gromo 서버에는 남지 않아요」. 주 버튼 `이동하기`, 보조 `취소`.

실패 처리는 2단이다. `Linking.canOpenURL`을 신뢰하지 않고 곧장 `openURL`을 호출한 뒤 예외를 잡는다 — iOS에서 `canOpenURL`은 스킴 화이트리스트에 걸려 false를 뱉는 일이 있어 멀쩡한 링크를 막을 수 있다.

### 4.4 계측 (R11)

`policy.md` D11의 3개 이벤트. `contact_id`는 닉네임조차 아닌 고정 슬러그를 보낸다 (PII 금지).

## 5. 성공 지표

D4대로 서버에 아무것도 남지 않으므로 **모든 지표는 GA4 이벤트에서 나온다.**

**모든 비율은 이벤트 건수가 아니라 세션 단위 distinct로 센다.** 한 세션에서 담당자를 바꿔 가며
여러 번 누르거나(재선택) 실패 후 「다시 시도」를 누르면 `inquiry_contact_opened`가 여러 번 발화한다.
건수로 나누면 전환율이 100%를 넘고, D11의 「주 30건」 임계도 부풀어 정책 재검토 신호가 오작동한다.

| 지표 | 정의 | 첫 릴리즈 기준선 |
|---|---|---|
| 창구 도달 | `inquiry_screen_viewed`의 **주간 distinct 세션 수** (비율 아님 — 아래 참조) | 관측 (목표 미설정) |
| 이동 전환율 | `inquiry_contact_opened` / `inquiry_screen_viewed` — 둘 다 distinct 세션 | **40% 이상** — 화면까지 왔는데 절반 넘게 나간다면 카드가 답을 안 주고 있다는 뜻 |
| 카테고리 사용률 | `inquiry_category_selected` / `inquiry_screen_viewed` — 둘 다 distinct 세션 | 관측. 20% 미만이면 칩이 안 보인다는 신호 |
| 추천 일치율 | `is_recommended='true'` / `inquiry_contact_opened` — **이것만 이벤트 단위** (카테고리 선택자 한정, 아래 참조) | 관측. 낮으면 D6 카테고리↔담당자 매핑이 틀린 것 |
| 미분류 비중 | `category='etc'` / 전체 선택 — **이것도 이벤트 단위** (아래 참조) | **50% 미만** — 넘으면 카테고리 축 재설계 (D6) |

**「추천 일치율」과 「미분류 비중」은 이벤트 단위다.** 이 둘이 세는 것은 *세션*이 아니라 *선택*
하나하나이기 때문이다. 한 세션에서 추천/비추천을(또는 `etc`/다른 카테고리를) 각각 한 번씩 고르면
실제 비중은 50%인데, 세션 distinct로 세면 분자에도 1·분모에도 1이 잡혀 **100%로 기록된다.**
문서가 같은 세션의 복수 선택을 명시적으로 허용하므로(위 문단) 이 왜곡은 예외가 아니라 기본값이 되고,
그 값으로 판단하면 **D6 매핑이 틀렸는데도 맞다고 나오거나, 반대로 축 재설계가 잘못 발동한다.**

**가르는 기준은 「무엇을 한 단위로 보는가」다.** 「이 세션에서 일어났나」를 묻는 지표(창구 도달 ·
이동 전환율 · 카테고리 사용률)는 distinct, **선택끼리 비율을 내는 지표**(추천 일치율 · 미분류 비중)는
이벤트 단위다. 지표를 추가할 때 이 기준으로 먼저 분류한다.

**재시도는 이벤트 단위 지표에서도 1건이다** — `low-level-design.md` §5.4가 「다시 시도」에서
`inquiry_contact_opened`를 재발화하지 않게 막는다. 안 그러면 실패가 잦은 링크·기기 쪽이 과대표집된다.

> **파라미터 값은 문자열로 조회한다.** `services/analytics.ts`의 `sanitizeParams`가 boolean을
> `'true' | 'false'` 문자열로 변환해 보낸다. GA4 대시보드에서 `is_recommended = true`(boolean)로
> 필터를 걸면 0건이 나온다.

**「창구 도달률」을 비율로 만들지 못한다.** 분모가 될 「전체」 탭 진입 이벤트가 없기 때문이다 —
`analyticsEvents.ts`에 `home_viewed` · `league_viewed` · `group_viewed` · `stats_viewed`는 있어도
메뉴(전체) 탭에 해당하는 것이 없고, D11은 이 기능의 이벤트를 3개로 못 박았다.
그래서 1차 릴리즈에서는 **절대 건수만 본다.** 비율이 필요해지면 `menu_viewed`를 추가하는 것이
선행 조건이고, 그건 이 기능이 아니라 계측 공통 작업이다 (`policy.md` 미결 참조).

첫 2주는 목표를 걸지 않고 기준선만 잡는다. 문의량 자체가 적을 것이므로 비율 지표는 표본이 쌓인 뒤 해석한다.
