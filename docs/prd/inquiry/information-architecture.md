# 1:1 문의 — 정보 구조 (Information Architecture)

> 정책 충돌 시 `policy.md`가 정본이다.

## 1. 전체 지도

```
탭바 「전체」 (MenuScreen)
└── 계정 · 정보
    ├── 계정 설정               → SettingsAccount
    ├── 1:1 문의  ★신규         → SettingsInquiry ─┐
    ├── 개인정보 처리방침        → 외부 URL         │
    ├── 서비스 이용약관          → 외부 URL         │
    └── 버전 정보               → SettingsVersion  │
                                                   │
                    ┌──────────────────────────────┘
                    ▼
            InquiryScreen (SettingsScaffold「1:1 문의」)
            ├── 안내 문단
            ├── 카테고리 칩 ×3        ─ 선택 시 담당자 재정렬(로컬 상태)
            ├── 담당자 카드 ×3        ─ 각 카드에 「카카오톡으로 문의하기」
            └── 하단 안내 박스
                    │
                    │ 카드 버튼 탭
                    ▼
            ConfirmCardModal「카카오톡으로 이동할까요?」
                    │ 이동하기
                    ▼
            Linking.openURL(https://open.kakao.com/o/…)
                    │
                    ├─ 카카오톡 설치됨 → 앱의 1:1 오픈채팅방
                    ├─ 미설치        → 브라우저의 웹 오픈채팅
                    └─ 실패          → 모달이 실패 상태로 전환 (복사 가능한 URL 노출)
```

**앱의 경계는 `openURL`에서 끝난다.** 그 뒤로는 gromo가 관여하지 않는다 (`policy.md` D1).

## 2. 화면 계층

### 2.1 화면 목록

| 화면 | 라우트 | 골격 | 신규 |
|---|---|---|---|
| 「전체」 탭 | `Main` › `전체` | 기존 | 행 1개 추가 |
| 1:1 문의 | `SettingsInquiry` | `SettingsScaffold` | ✅ |
| 이동 확인 | (모달) | `ConfirmCardModal` | 기존 컴포넌트 |

**화면은 1개만 늘어난다.** 이력·상세·목록 화면이 없다 (`policy.md` D4).

### 2.2 문의 화면의 정보 순서

위에서 아래로 **「무엇을 할 수 있는가 → 어떤 문제인가 → 누구에게 → 무엇을 알아야 하는가」** 순이다.

| 순서 | 블록 | 담는 것 |
|---|---|---|
| 1 | 안내 문단 | `무엇을 도와드릴까요?` + 「담당 개발자에게 카카오톡으로 직접 물어보실 수 있어요」 |
| 2 | 카테고리 칩 | `집중 · 스크린타임` / `그룹 · 챌린지` / `계정 · 기타` |
| 3 | 담당자 카드 ×3 | 아바타 · 닉네임 · 성격 설명 · 한 줄 소개 · 응답 시간 · CTA |
| 4 | 하단 안내 | 외부 이동 · 응답 지연 가능성 |

**「담당자」가 화면의 주인공이다.** 카테고리는 담당자를 고르기 위한 길잡이지 그 자체가 목적이 아니다 (D6). 그래서 칩이 카드보다 위에 있되 시각적 무게는 카드가 훨씬 크다.

### 2.3 담당자 카드 안의 정보 순서

```
┌────────────────────────────────────────┐
│ (아바타)  닉네임                [추천]   │  ← 누구인가
│           성격 설명                     │  ← 어떤 쪽 사람인가
│                                        │
│  "한 줄 소개 — 어떤 증상일 때 나에게"    │  ← 내 문제가 여기 맞나
│                                        │
│  🕐 응답 가능 시간                       │  ← 언제 답이 오나
│  ┌──────────────────────────────────┐  │
│  │  💬 카카오톡으로 문의하기          │  │  ← 행동
│  └──────────────────────────────────┘  │
└────────────────────────────────────────┘
```

한 줄 소개는 **성격 설명을 사용자 언어로 옮긴 문장**이다. 「집중 · 스크린타임 · 통계」는 우리 말이고, 「타이머가 안 멈추거나 사용 시간이 이상하면」이 사용자 말이다. 둘 다 있어야 매칭이 된다.

둘 다 **소유권 주장이 아니다.** 「이 사람이 이 기능을 책임진다」가 아니라 「이런 문의면 이 사람이 어울린다」이며, 사용자는 무시하고 아무나 고를 수 있다 (D2 · D6).

### 2.4 상태 분기

| 상태 | 화면 |
|---|---|
| 기본 | 카테고리 미선택, 담당자 3장이 상수 순서대로 |
| 카테고리 선택 | 해당 담당자가 1번 자리로, 「추천」 배지 부착. 나머지 2장은 남는다 |
| 카테고리 재탭 | 선택 해제, 기본 순서 복귀 |
| 확인 모달 열림 | 배경 딤 + 카드 (담당자명 · 목적지 · 저장 위치 고지) |
| 링크 실패 | **같은 모달**이 실패 문구 + 복사 가능한 URL + 「다시 시도」로 전환. 닫히지 않는다 |

**로딩 상태가 없다.** 데이터가 전부 앱 상수라 네트워크를 타지 않는다 (D5). 그래서 스켈레톤·에러·리트라이 분기가 전부 불필요하다.

## 3. 데이터 구조 (Content Model)

### 3.1 엔티티

서버 엔티티가 없다. 앱 상수 2종뿐이다.

```
InquiryCategory (상수 3개)
  id       : 'focus' | 'group' | 'etc'
  label    : 표시 문구
  scope    : 이 카테고리가 포함하는 것 (도움말 문구용)

InquiryContact (상수 3개)
  id            : 슬러그 — 분석 이벤트용 안정 키 (닉네임조차 아님, D11)
  name          : 닉네임 · 활동명 (실명 아님, D10)
  initial       : 아바타 이니셜 1글자
  avatarColor   : T.avatarPalette 중 하나
  scopeLabel    : 성격 설명 — 어떤 쪽 문의에 어울리는지 (우리 말, 소유권 아님)
  intro         : 한 줄 소개 (사용자 말)
  availability  : 응답 가능 시간
  categoryId    : 이 담당자가 추천되는 카테고리 (1:1)
  openChatUrl   : https 오픈채팅 URL
```

`categoryId`가 카테고리 ↔ 담당자를 잇는 유일한 연결이며 **1:1**이다 (`policy.md` D6의 표). 한 담당자가 두 카테고리를 맡거나 한 카테고리에 두 담당자가 붙는 경우는 이번 범위에 없다.

이 1:1은 **추천 순서를 정하는 장치**일 뿐 업무 분장의 기록이 아니다 (D6). 실제 분장과 어긋나도 화면은 정상 동작한다 — 추천이 덜 맞을 뿐이다.

### 3.2 카테고리 축

| id | label | 포함 | 추천 담당자 |
|---|---|---|---|
| `focus` | 집중 · 스크린타임 | 집중 세션, 타이머, 스크린타임 권한·사용량, 통계 | 담당자 1 |
| `group` | 그룹 · 챌린지 | 그룹, 초대, 챌린지, 내기, 리그 | 담당자 2 |
| `etc` | 계정 · 기타 | 로그인, 탈퇴, 시간조각, 캐릭터·상점, 그 밖 전부 | 담당자 3 |

`etc`가 **미분류 흡수 칸**이다. 갈 곳 없는 문의가 있으면 사용자는 아무 칩이나 고르고, 그러면 계측이 오염된다.

## 4. 진입 경로 (Navigation & Entry Points)

### 4.1 도달 경로

| 경로 | 비고 |
|---|---|
| 「전체」 탭 → 계정 · 정보 → `1:1 문의` | **유일한 진입점** |

딥링크(`gromo://…`)를 만들지 않는다. `navigationRef.ts`의 딥링크 매핑에 추가하지 않는다 — 푸시도 이메일도 이 화면으로 사람을 보내지 않으므로 받을 트래픽이 없다.

홈 플로팅 버튼, 에러 화면의 「문의하기」 링크, 온보딩 안내 — 전부 이번 범위 밖이다 (D12).

### 4.2 이탈 경로

| 지점 | 다음 |
|---|---|
| 뒤로 가기 | 「전체」 탭 |
| 「이동하기」 | **앱 밖** — 카카오톡 또는 브라우저 |
| 링크 실패 | **모달이 닫히지 않는다** — 같은 모달이 실패 상태로 전환(복사 가능한 URL + 「다시 시도」). §2.4와 `policy.md` D7 |

**실패 시 Toast를 띄우지 않는다.** Toast는 모달을 닫는 처리와 짝을 이루는데, 모달이 닫히면 URL이 화면에서 사라져 유일한 수동 폴백이 없어진다.

「이동하기」 뒤에 앱이 하는 일은 없다 — 돌아왔을 때 **화면에 보여줄 변화가 없다.** 상태를 새로 불러올
것도, 되돌릴 것도 없으므로 복귀 시 UI를 갱신하지 않는다.

**다만 `AppState` 자체는 계측 때문에 구독한다.** 사용자를 앱 밖으로 내보내는 화면이라 「떠났다 돌아온다」가
정상 경로이고, 그 사이 GA4 세션이 새로 시작되면 `inquiry_screen_viewed` 없이 `inquiry_contact_opened`만
남아 전환율이 100%를 넘는다. 화면 갱신은 안 하되 노출 이벤트는 다시 쏜다 — `low-level-design.md` §6.

## 5. API 표면 (Endpoint Map)

**없다.** (`policy.md` D13)

이 절은 비워두지 않고 명시한다 — 나중에 「IA에 API 절이 없으니 빠뜨린 것 아닌가」라는 오해를 막기 위해서다. 이 기능은 네트워크 호출을 하지 않는다.

## 6. 정보 우선순위 (Priority Model)

화면 예산이 부족할 때 (작은 기기 · 큰 글씨 설정) 지키는 순서:

1. **담당자 닉네임 + 성격 설명** — 이게 없으면 화면이 존재할 이유가 없다
2. **CTA 버튼** — 행동 경로
3. **한 줄 소개** — 매칭 정확도. **줄 수를 제한하지 않는다**(`numberOfLines` 없음). 길면 카드가 세로로 늘어난다
4. **응답 가능 시간** — 기대치 관리
5. **카테고리 칩** — 없어도 직접 지목이 가능하다
6. **하단 안내 박스** — 스크롤 아래로 밀려도 무방

글자 배율을 키워도 1~4는 잘리지 않아야 한다. **그래서 3번에 `numberOfLines`를 두지 않는다** —
「2줄까지 허용하고 넘치면 말줄임」과 이 문장은 동시에 만족할 수 없고, 잘리는 쪽을 택하면 담당자를
고르는 **유일한 근거**가 접근성 배율을 키운 사용자에게만 사라진다. 카드 3장짜리 스크롤 화면이라
세로로 길어져도 잃는 게 없다(`low-level-design.md` §8.4 Q8이 iPhone SE 도달 가능성을 확인한다). 고정 폭 칸이 없는 레이아웃이므로 `maxFontSizeMultiplier`를 걸지 않는다 — 줄바꿈으로 풀리는 칸에 상한을 걸면 접근성만 깎인다 (`theme.ts`의 `FIXED_BOX_FONT_SCALE_MAX` 주석 참조).

## 7. 상태 소유권 (State Ownership)

| 상태 | 소유자 | 수명 |
|---|---|---|
| 담당자 · 카테고리 목록 | **앱 상수** (`inquiryContacts.ts`) | 빌드/OTA 시점 고정 |
| 선택된 카테고리 | `InquiryScreen`의 `useState` | 화면 언마운트 시 소멸 |
| 확인 모달 대상 담당자 | `InquiryScreen`의 `useState` | 모달 닫히면 소멸 — **아래 셋은 한 몸** |
| 모달의 실패 여부 | `InquiryScreen`의 `useState` | 〃 |
| 링크 요청 진행 중 | `InquiryScreen`의 `useState` | 〃 |
| 문의 내용 · 진행 상태 | **카카오톡** | gromo 밖 |

**모달 상태 셋은 반드시 같은 닫기 경로에서 함께 리셋된다.** 대상 담당자만 비우고 실패 여부를
남기면, 다음에 누른 담당자의 모달이 **링크를 시도하기도 전에** 실패 화면으로 열린다. 이 계약은
`low-level-design.md` §5.4의 `closeModal()` 한 곳에만 산다 — 여기서 상태를 행 단위로 나눠 적었다고
해서 각각 따로 관리해도 된다는 뜻이 아니다.

**Context에 아무것도 올리지 않는다.** 이 화면 밖에서 읽는 상태가 없다.

## 8. 저장소 (Local Storage)

**없다.** `STORAGE_KEYS`에 키를 추가하지 않는다.

선택한 카테고리를 기억하지 않는다 — 다음 문의가 같은 영역이라는 보장이 없고, 기억하면 오히려 잘못된 담당자로 유도한다.
