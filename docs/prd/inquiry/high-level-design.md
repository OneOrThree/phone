# 1:1 문의 — 상위 설계 (High Level Design)

> 정책 충돌 시 `policy.md`가 정본이다.

## 1. 시스템 컨텍스트

```
┌─────────────────────────── gromo 앱 ────────────────────────────┐
│                                                                │
│   MenuScreen ──navigate──▶ InquiryScreen                       │
│                                │                               │
│                    ┌───────────┼───────────┐                   │
│                    ▼           ▼           ▼                   │
│            inquiryContacts  ConfirmCard  analyticsEvents        │
│              (앱 상수)        Modal         (GA4)               │
│                                │             │                 │
│                                ▼             │                 │
│                        Linking.openURL       │                 │
└────────────────────────────────┼─────────────┼─────────────────┘
                                 │             │
                                 ▼             ▼
                    ┌────────────────────┐  ┌──────────┐
                    │  카카오톡           │  │  GA4     │
                    │  1:1 오픈채팅방 ×3  │  │          │
                    └────────────────────┘  └──────────┘
                             │
                             ▼
                    담당자 (개발자 3명)

  gromo 백엔드 ─────── 관여하지 않음 (policy.md D13) ───────
```

### 1.1 구성 요소의 책임

| 요소 | 책임 | 책임이 **아닌** 것 |
|---|---|---|
| `InquiryScreen` | 담당자·카테고리를 보여주고, 선택을 로컬 상태로 관리하고, 확인 모달을 띄운다 | 문의 내용을 받거나 보내는 일 |
| `inquiryContacts.ts` | 담당자 3명과 카테고리 3개의 **단일 진실 원천** | 원격 갱신 (OTA가 담당) |
| `ConfirmCardModal` | 외부 이동 고지와 최종 확인 | 이 기능 전용 로직 (기존 공용 컴포넌트) |
| `Linking` | 앱 경계를 넘기는 유일한 통로 | 성공 보장 |
| `analyticsEvents` | 이 기능의 **유일한 계측 수단** | PII 전송 |
| 카카오톡 | 대화, 이력, 사실상의 상태 | — |
| gromo 백엔드 | **없음** | — |

## 2. 레이어 구조

```
screens/settings/InquiryScreen.tsx          ← 화면 (상태·조립)
  ├── components/InquiryContactCard.tsx     ← 표시 전용 (props in, onPress out)
  ├── components/InquiryCategoryChips.tsx   ← 표시 전용
  └── inquiryLink.ts                        ← 링크 열기 + 실패 폴백 (부수효과 격리)
constants/inquiryContacts.ts                ← 데이터 (순수 상수, import 없음)
services/analyticsEvents.ts                 ← 계측 (기존 파일에 함수 3개 추가)
```

**세 겹으로 나누는 이유는 테스트 가능성이다.** `inquiryContacts.ts`는 순수 상수라 「카테고리마다 담당자가 정확히 1명인가」를 단위 테스트로 잠글 수 있고, `inquiryLink.ts`는 `Linking`을 모킹해 실패 폴백을 검증할 수 있다. 화면에 전부 인라인하면 둘 다 못 한다.

`inquiryContacts.ts`가 `constants/`에 가는 이유: `theme.ts`와 같은 「import 없는 순수 상수 모듈」 규약을 따른다. 색상값은 `T.avatarPalette`에서 **인덱스로** 참조한다 (`theme.ts`를 import하지 않기 위해).

`services/inquiryApi.ts`를 **만들지 않는다** — 호출할 API가 없다.

## 3. 주요 흐름

### 3.1 정상 — 카테고리를 고르고 문의한다

```
사용자            InquiryScreen        analytics      ConfirmModal      OS
  │                    │                   │              │            │
  ├─ 화면 진입 ────────▶│                   │              │            │
  │                    ├─ viewed ─────────▶│              │            │
  │                    │                   │              │            │
  ├─ 「집중」 칩 탭 ────▶│                   │              │            │
  │                    ├─ category_sel ───▶│              │            │
  │                    │                   │              │            │
  │◀── 담당자1이 1번 자리로 + 「추천」 배지   │              │            │
  │                    │                   │              │            │
  ├─ 「카카오톡으로」 ──▶│                   │              │            │
  │                    ├─ 모달 열기 ────────────────────▶ │            │
  │◀─────────────────── 담당자명·목적지·저장 위치 고지 ──── │            │
  │                    │                   │              │            │
  ├─ 「이동하기」 ─────────────────────────────────────▶  │            │
  │                    │◀─ onPrimary ──────────────────── │            │
  │                    ├─ contact_opened ─▶│              │            │
  │                    ├─ openURL(https 오픈채팅) ──────────────────▶ │
  │                    │                   │              │            ├─▶ 카카오톡
```

**분석 이벤트는 `openURL` 앞에서 쏜다.** 뒤에서 쏘면 앱이 백그라운드로 넘어가는 타이밍과 겹쳐 유실될 수 있다. 「이동하기를 눌렀다」가 우리가 아는 마지막 사실이고, 그게 지표의 정의다 (`prd.md` §5).

### 3.2 카카오톡 미설치

`policy.md` D7대로 https URL만 넘기므로 **앱이 분기하지 않는다.** OS가 판단해서 브라우저로 연다. 우리 코드에 미설치 분기가 없다는 것이 이 설계의 핵심이다.

### 3.3 링크 열기 실패

```
openURL ──▶ throw
   │
   ▼
catch ─▶ 모달을 닫지 않고 실패 상태로 전환
      ─▶ 본문: '카카오톡을 열 수 없어요. 아래 주소를 길게 눌러 복사해 주세요.'
      ─▶ <Text selectable>{openChatUrl}</Text>
```

`Linking.canOpenURL`로 **사전 검사하지 않는다.** iOS에서 `canOpenURL`은 `Info.plist`의 `LSApplicationQueriesSchemes` 화이트리스트에 걸려 멀쩡한 링크에도 false를 뱉을 수 있다. 그러면 우리가 정상 링크를 스스로 막는 꼴이 된다. 곧장 열고 예외를 잡는 편이 안전하다.

**클립보드 API를 쓰지 않는다** (`policy.md` D7). `expo-clipboard`가 미설치이고 RN 코어 `Clipboard`는 0.86에서 제거됐다 — 넣는 순간 네이티브 모듈이 추가돼 §4의 OTA 갱신 모델이 무너진다. `Text`의 `selectable`은 코어 기능이라 공짜다.

**모달을 닫지 않는 것**이 핵심이다. 닫고 Toast를 띄우면 URL이 3초 뒤 사라지고 사용자는 다시 빈손이 된다.

## 4. 데이터 흐름과 갱신 모델

```
빌드/OTA 시점                     런타임
─────────────                    ──────
inquiryContacts.ts  ──고정──▶  InquiryScreen이 그대로 읽음
      ▲
      │ 담당자·링크 교체
      │
   JS 번들 갱신 ──── hot-updater OTA ────▶ 앱 심사 없이 반영
```

담당자 교체·링크 변경·소개 문구 수정이 전부 **JS 상수 변경**이므로 OTA 경로를 탄다 (`policy.md` D5). 네이티브 변경이 없어 스토어 심사를 기다리지 않는다.

이 성질 때문에 원격 설정 엔드포인트가 불필요해졌고, 그 결과 백엔드 변경이 0이 됐다.

## 5. 신뢰성

이 기능에는 동시성도, 일관성도, 트랜잭션도 없다. 서버 상태가 없기 때문이다. 실패할 수 있는 지점은 하나뿐이다.

| 실패 지점 | 영향 | 대응 |
|---|---|---|
| `openURL` 예외 | 사용자가 이동 못 함 | §3.3 — 모달을 실패 상태로 전환 + 복사 가능한 URL 노출 |
| 오픈채팅방 폐쇄 / URL 만료 | 링크는 열리지만 방이 없음 | **앱이 감지할 수 없다.** 운영 점검 사항 — 방 3개를 유지하는 책임은 담당자에게 있다 |
| GA4 전송 실패 | 지표만 결손 | 무시 (사용자 경험 무영향) |

두 번째가 이 설계의 **가장 큰 구조적 약점**이다. 링크가 죽어도 앱은 정상 동작하는 것처럼 보이고, 사용자는 빈 방으로 들어간다. 서버가 없으니 헬스체크할 방법도 없다.

### 5.1 오픈채팅 링크 운영 런북

「릴리즈 전 수동 확인」만으로는 부족하다. **방은 릴리즈 사이에도 죽는다.** 릴리즈 간격이 몇 주면
그동안 들어온 사용자는 전부 빈 방을 만나고, 우리는 그 사실 자체를 모른다. 감지할 수 없는 실패이므로
**감지 대신 주기와 책임으로 막는다.**

| 항목 | 규칙 |
|---|---|
| 방별 책임자 | 그 방의 담당자 본인이 소유자다 — 방을 만든 사람이 유지 책임을 진다 (D3) |
| 정기 점검 | **주 1회**, 담당자가 자기 방 링크를 시크릿 창에서 직접 연다. 방 3개면 3명이 각자 1개씩이라 부담이 분산된다 |
| 배포 게이트 | **스토어 릴리즈뿐 아니라 OTA 배포 전에도** 링크 3개를 확인한다. 링크 교체가 OTA로 나가므로(D5) 스토어 심사만 게이트로 잡으면 정작 링크를 바꾸는 경로가 무검증으로 빠진다 |
| 사용자 신고 경로 | 스토어 리뷰와 담당자 개인 채널이 전부다 — **문의 창구가 죽었을 때 그걸 알릴 창구가 이 기능 자신이라는 순환**이 남는다. 받아들이는 대신, 최소한 세 방이 동시에 죽지 않도록 방을 각자 다른 계정으로 만든다 |
| 복구 SLA | 죽은 방을 확인하면 **당일 새 방 개설 + OTA 배포**. 상수 1줄 교체라 심사가 없어 몇 시간 안에 나간다 — 이 설계가 감지에서 잃은 것을 복구 속도에서 되찾는 유일한 지점이다 |

이 런북이 이 기능의 **유일한 운영 부채**다. 지키지 못할 것 같으면 그건 D1(링크아웃)을 재검토해야 한다는 신호지, 런북을 느슨하게 할 이유가 아니다.

## 6. 관측 (Operability)

| 알고 싶은 것 | 수단 |
|---|---|
| 창구가 쓰이는가 | `inquiry_screen_viewed` 추이 |
| 어느 영역 문의가 많은가 | `inquiry_category_selected` 분포 |
| 어느 담당자에게 몰리는가 | `inquiry_contact_opened`의 `contact_id` 분포 |
| 카테고리 매핑이 맞는가 | `is_recommended` 비율 |
| 화면까지 왔다가 그냥 나가는가 | viewed 대비 opened 전환율 |

서버 로그도, DB 조회도, 대시보드도 없다. **GA4가 유일한 창이다.** 그래서 D11의 이벤트 3개는 부가 기능이 아니라 이 설계의 필수 부품이다 — 빼면 이 기능은 영영 측정 불가가 된다.

## 7. 확장 경로

지금 구조에서 다음 단계로 가는 길을 미리 적어 둔다 (지금 만들지 않는다).

| 필요가 생기면 | 바꾸는 곳 | 규모 |
|---|---|---|
| 담당자 4명 이상 | `inquiryContacts.ts` 배열에 추가 | 상수 1줄. 화면은 세로로 길어질 뿐 안 깨진다 |
| 한 카테고리에 담당자 2명 | `categoryId` 1:1 → N:1로 완화, 추천 정렬 로직 수정 | 소 |
| 원격 담당자 목록 | 상수 → API. 로딩·에러 분기 신설 | 중 (백엔드 발생) |
| 진짜 문의 상태 | `policy.md` S3 — 신규 도메인 + 어드민 | 대 |

**1·2번은 지금 구조가 그대로 흡수한다.** 3·4번은 policy.md의 「뒤집을 때의 신호」에 걸렸을 때만 검토한다.
