# 섬 이동 · 서버 확정 좌표

작성: 2026-09-23 · 상태: **구현 전 설계 제안** · 작업: [GROMO-2110](https://romance.atlassian.net/browse/GROMO-2110)

사용자가 탭하면 앱이 먼저 움직임을 예측하고, 별도 이동 서버가 확정한 경로·좌표에 맞춰 표시를 보정한다. 서버는 맵을 소유하고 50ms 간격으로 이동을 계산한다. 좌표는 암호화된 UDP 기반 연결로 전송한다.

이 문서 PR은 서버·앱 구현이나 TestFlight 배포를 포함하지 않는다. 기존 TestFlight의 로컬 이동과 구분한다. 여기서 제시하는 API, 메시지, 서비스명은 **신설 제안**이다.

## 핵심 설계

- **좌표:** `x,y ∈ [0,100]`. 화면 픽셀·그림 타일·길찾기 격자는 별개다.
- **서버 권한:** 출발점·속도·도착 판정은 서버가 소유한다. 앱은 목적지를 요청한다.
- **A*:** 서버는 확정 경로, 앱은 입력 반응을 위한 예측 경로를 계산한다. 매 틱 A*를 반복하지 않는다.
- **전송:** QUIC의 신뢰성 있는 스트림으로 명령·경로를, DATAGRAM으로 20Hz 좌표를 보낸다. 양방향 암호화한다.
- **구현:** Java 이동 코어 + Netty QUIC 어댑터를 POC 출발안으로 삼는다. 직접 연결에 C++ 서비스가 필수인 것은 아니다.
- **분리:** 이동 서비스는 `gameId + roomId` 기준으로 방을 관리한다. 재화·시설 권한은 기존 Business/Data에 남는다.
- **장애:** 한 방에 확정 상태를 쓰는 서버는 하나다. 소유권 세대가 바뀌면 이전 좌표를 버리고 재동기화한다.

Plannotator의 Java·Kafka·Realtime 질문과 추천 근거는 [아키텍처 §7](architecture.md#7-java--kafka--realtime-선택-검토)에서 비교한다.

## 구현 전에 닫을 항목

1. 100×100이 좌표 범위인지 **정확히 100×100개의 통행 셀**인지 최종 확인한다. 이 초안은 전자다.
2. 앱의 이동 서버 직접 연결에 대한 기존 아키텍처 예외를 정식 결정 장부에 반영한다.
3. iOS·Android에서 QUIC 연결, 전환·복귀, 20Hz 처리량과 배터리를 검증한다.
4. 동시 접속 목표와 장애 시 입구 복귀 정책을 확정한다. 문서의 부하 수치는 초기 검증 목표다.

## 용어

| 용어 | 의미 |
| --- | --- |
| 기본 지형 / `mapId + mapVersion` | 섬들이 공유하는 불변 지형·통행 재료 |
| 섬 배치 / `layoutRevision` | 특정 섬의 완공 시설·충돌체 배치 버전. Data 소유 |
| 통행 맵 / `navRevision` | 지형·배치·캐릭터 반경·탐색 규칙을 합성한 불변 산출물. Movement가 생성 |
| 방 / `gameId + roomId` | 동일한 이동 상태를 공유하는 단위. Fishcat은 섬 하나에 방 하나 |
| 서버 확정 위치 | 해당 방 소유자가 시뮬레이션한 위치 |
| 표시 위치 | 예측·보간·보정을 거쳐 화면에 그리는 위치 |
| 목적지 / 도착 지점 | 사용자가 탭한 점 / 서버가 통행 가능성까지 검사해 정한 점 |
| `roomEpoch` | 방 소유권 세대. 장애 이전 패킷을 구분하는 fencing token |
| `actorId` | 방 세대 안에서 유일한 이동 객체 식별자. 계정 ID를 직접 노출하지 않음 |
