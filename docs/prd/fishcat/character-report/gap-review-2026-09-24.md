## 하나씩 닫을 간극

### 1. 차단 정책의 정본 충돌 — 피드백 반영·최소 조건 검증

- `origin/main`의 결정 로그 `차단-도입`과 친구 편지 LLD §1.18은 차단을 친구 목록·검색·받은 편지함의 **표시 필터**로 정의한다. GROMO-1975로 `GET·POST /blocks`, `DELETE /blocks/{blockedUserId}` 및 해당 필터가 구현됐다.
- 이 브랜치의 RP-차단은 **양방향 편지 발송·친구 요청 차단**과 차단자가 보는 **채팅·댓글·공지 숨김**을 확정 정책으로 적었다. `policy.md`는 결정 로그를 우선한다고 명시하므로, 병합 시 두 확정 행을 모순 없이 연결해야 한다.
- **Plannotator 피드백:** “지금 구현된 백엔드 정책이 출시 최소 조건을 만족했는가? 그렇다면 현재 백엔드 정책을 따라간다.”
- **검증 결과: 현재 구현만으로는 최소 조건 충족을 판정할 수 없다.** 병합한 `main`에서도 `FriendService.createRequest`와 `InternalLetterService.send`는 차단 관계를 검사하지 않아 차단된 상대에게도 친구 요청·편지 쓰기를 시도할 수 있다. `LetterRepository.findReceivedByCursor`는 받은 편지함 목록에서만 차단 발신자를 거른다. 앱 `src`에는 `/blocks` 소비나 차단 조작 UI가 확인되지 않았다. 서버 API가 있어도 사용자가 앱 안에서 차단할 수 없다.
- [Apple App Review Guideline 1.2](https://developer.apple.com/app-store/review/guidelines/#user-generated-content)는 UGC의 신고·대응과 악성 사용자 차단 수단을 요구한다. [Google Play UGC 정책](https://support.google.com/googleplay/android-developer/answer/9876937?hl=en)은 1:1 상호작용에서 **앱 내** 사용자 차단, 공개 UGC에서 사용자·콘텐츠 신고와 차단을 요구한다. 두 문서 모두 “목록 한 곳의 표시 필터면 충분하다”는 보증을 주지 않는다. 스토어 심사 통과 자체도 이 문서로 확정할 수 없다.
- **정리 결과:** GROMO-1975의 API·필터는 재사용한다. RP-차단의 직접 연락 차단과 공개 콘텐츠 숨김은 아직 구현되지 않은 후속 범위로 유지한다. 기존 `차단-도입` 행과 친구 편지 LLD §1.18은 당시 구현 범위인 “표시 필터 1단계”로 설명하고, RP-차단이 최종 2.0 정책임을 문서에서 일치시켰다.
- **사용자 후속 지시:** 앱의 신고·차단 UI는 **별도 Jira 티켓으로 만들어 1670에 연결할 예정**이다. 현재 티켓 번호는 없으며, 이 문서는 티켓을 생성했다고 기록하지 않는다. 1670 자체의 완료 판정에는 UI 구현을 넣지 않되, 2.0 출시 게이트에는 해당 티켓의 구현·검증 완료가 필요하다.
- 완료 증거: 결정 로그·친구 편지 LLD·신고 정책이 같은 규칙을 가리키고, 현재 구현/남은 구현이 분리되어 있다.

### 2. 신고 대상·진입점·사유 확정

- Jira 댓글의 대상은 공지·댓글·섬 채팅·친구 편지·닉네임·섬 이름/소개다. `policy.md` D1은 화면별 진입점, 사유, 권한 규칙을 제안했지만 확정 정책으로 승격하지 않았다.
- 검토할 결정: 사용자/콘텐츠 신고 단위, 화면별 진입점, 신고 사유와 설명 필수 조건, 이미 삭제·수정된 대상과 권한 없는 대상의 처리.
- 완료 증거: 후속 앱/API 작업이 대상별 입력과 접근 권한을 추가 제품 판단 없이 구현할 수 있다.

### 3. 증거 획득·보존 계약 확정

- RP-메일정본이 자체 신고 DB 대신 운영 메일함을 기록·증거 정본으로 정했다. D2·D6의 자체 저장소 가정은 개정해야 한다. 서비스별 원문 조회, 편지 닫기 경합, 수정 버전, 메일 실패·중복·반송, 만료·백업·탈퇴 경계가 남았다.
- 검토할 결정: [이메일 접수 계약](email-intake-contract.md)이 정한 서버 원문·권한·메일함 접수 확인·재시도·편지 닫기 직렬화를 각 서비스의 API와 메일 제공자로 실현 가능한지 검증한다. 결과 답장 또는 무연락 종결의 30일 기산점과 보존 예외를 메일함에서 집행한다.
- 완료 증거: 후속 티켓이 메일 증거 없는 접수 성공, 원문 바꿔치기, 권한 밖 원문 전송을 막는 계약과 검증 항목을 갖는다. 메일 제공자 접근·개인정보 고지·파기 작업이 명시된다.

- 완료 증거: 접수에서 종결·재심·파기까지 책임 주체와 상태 전이가 문서로 추적된다. 운영 실명·연락처와 수신 시험은 출시 운영 작업으로 분리한다.

### 5. CSAM·법적 적용 사실 확인

- `legal-response.md`는 공식 자료와 대응 절차 **초안**을 작성했다. 법률 멘토링 결과는 아직 없고 회사별 적용 사실을 문서가 추정하지 않는다.
- 검토할 결정: 실제 사업자 지위·출시국·앱 분류에 따른 의무, 제3자 기관 신고 경로, 기관 요청 검증, 신고 원문과 제재 이력의 개인정보 처리 근거·보존 예외.
- 완료 증거: 정책 문서에서 확정된 제품 절차와 법적 확인 대상을 구분하고, 확인 책임자와 출시 전 점검 항목을 지정한다. 확인 전에는 법적 의무를 단정하지 않는다.

### 6. 최신 `main` 반영과 후속 작업 분할

- `follow-up-scope.md`의 2026-09-22 코드 대조는 차단 스키마만 있는 상태를 전제로 한다. 최신 `main`에는 GROMO-1975 차단 API·일부 표시 필터가 들어왔다. 앱 신고 진입점과 신고 접수·증거 API는 확인되지 않았다.
- 검토할 작업: 문서의 구현 현황 갱신, F1~F6에서 이미 구현한 차단 부분 표시, 남은 기능을 선행 조건·완료 증거가 있는 후속 티켓으로 분할, 최신 `main`과 문서 브랜치의 정합성 확인. 앱 UI는 사용자가 별도 Jira 티켓으로 발행해 1670에 연결할 예정이며, 발행 전에는 번호를 추정하지 않는다.
- 완료 증거: 1670 산출물을 병합할 수 있고, 후속 티켓이 정책 문서만으로 착수 가능하다. 문서 완료와 2.0 출시 게이트 충족은 별개로 표시한다.
