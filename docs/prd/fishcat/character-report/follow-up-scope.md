# 신고센터 후속 구현 범위와 검증 기준

[정책](policy.md) · [이메일 접수 계약](email-intake-contract.md) · [법적 근거·긴급 대응](legal-response.md) · [결정 로그](../decision-log.md)

이 문서는 GROMO-1670에서 정한 정책의 부수 작업과 향후 구현 범위를 기록한다. **이 문서를 완성하는 데 신규 Jira 티켓 발행·기존 티켓 수정·연결은 필요하지 않다.** 차단 API·일부 표시 필터는 GROMO-1975, 여섯 텍스트 입력의 금칙어 검증은 GROMO-1986으로 구현됐지만 신고센터 전체 구현은 완료되지 않았다. 확정 RP 정책을 기준으로 구현하고, 정책의 D 초안 항목은 설계 검토에서 확정한다. 2026-09-24 RP-메일정본에 따라 자체 신고 사건·원문 DB는 범위에서 제외한다.

## 현재 코드 대조 — 2026-09-24, main 250a13f5

- `UserBlockRepository`와 `UserBlock`에 더해 GROMO-1975의 차단 생성·해제·목록 API가 있다. 친구 목록·검색과 받은 편지함 목록에는 차단자 관점 표시 필터가 붙었다. `FriendService.createRequest`와 `InternalLetterService.send`에는 차단 판정이 없고, 앱에는 차단 조작 UI가 확인되지 않았다. RP-차단의 양방향 직접 연락 제한과 채팅·댓글·공지 숨김은 남은 범위다.
- `InternalLetterService.close`는 수신자 권한 확인 후 `softDeleteIfActive`로 편지를 닫는다. 조회와 닫기 경합은 처리하지만 신고 증거 확보와의 경합 처리는 새로 연결해야 한다.
- GROMO-1986의 `BannedWords`는 공지·댓글·편지·닉네임·섬 이름·소개 입력을 서버에서 검증한다. 기존 `CharacterModerationService`는 누끼 이미지 검사다. 섬 채팅·방장이 작성하는 퀘스트 제목과 링크 정책, 작성 전 동의까지 완료됐다는 근거는 아니다. 현재 방문자 응답에 나가는 개인 집중 주제는 타인에게 정형 문구로 대체해야 한다.
- 채팅 정본은 realtime의 `gromo_chat`이며 기존 [우체통 정책](../island-mailbox/policy.md)을 따른다. 신고 때문에 전체 채팅 이력을 Data로 복제하지 않는다.
- 최신 `main`에는 사용자 이미지·파일의 영구 저장→타인 조회 경로가 확인되지 않는다. 그러나 `POST /api/v1/character/moderation`은 최대 약 10MiB의 base64 PNG를 입력받아 OpenAI 이미지 검사 API로 전송하고 결과만 반환한다. `character_generation`은 이미지가 아닌 생성 이력만 저장한다. 기존 이미지 입력·외부 전송의 개인정보·안전 검증은 F6에 포함하고, 새로운 공유·증거 저장 파이프라인 구축과 구분한다.

## 2.0 실행 순서

1. **텍스트 신고·차단 계약 확정:** 공지·댓글·채팅·편지·이름/소개와 공개 퀘스트 제목을 신고 대상으로 고정하고, 개인 집중 주제는 타인에게 정형 문구로만 보여 주며, 기존 앱 UI 티켓 GROMO-1673·1976을 현 정책으로 갱신한다. 이미지·파일 첨부와 타인에게 보이는 미디어 화면은 범위에서 뺀다.
2. **서버 구현:** F1의 텍스트 원문 확인·메일 접수, F2의 직접 연락 거절·서버 전송 제외, F3의 운영 조치 경로를 구현한다. GROMO-1975·1986의 완료분을 재사용한다.
3. **앱·운영 연결:** F4의 신고·차단 UI를 서버 계약에 연결하고, F5에서 남은 텍스트 채팅·링크·동의/공개 고지 범위를 확정한다. F6에서 실제 메일함·긴급 알림·담당자·파기 흐름을 시험한다.
4. **향후 미디어 기능은 별도 게이트:** 이미지·파일의 영구 저장 또는 타인 조회·공유를 새로 열 때 별도 티켓에서 파일 검사, 저장·삭제, 신고 증거, CSAM 대응과 운영 경로를 설계·검증한다. 이번 2.0 티켓의 선행 구현으로 두지 않는다.

GROMO-1670은 정책·범위 정의 티켓이다. 위 기존 티켓들은 별도로 이미 발행됐지만 현재 Jira에서 1670과의 연결이나 설명 갱신은 확인되지 않았다. **그 연결·갱신이나 신규 티켓 발행은 1670의 완료조건이 아니다.** 앱 UI는 GROMO-1673과 GROMO-1976에서 분리해 진행할 수 있다. F1 서버 메일 접수, F2 서버 차단, F3 운영, F5 잔여 필터·규범은 실제 2.0 출시 준비에서 처리한다.

원문 조회·메일 발송·제재 소유권은 기존 Data/Business/realtime 경계에 맞춰 상세 설계한다. 다른 서비스의 DB를 직접 조회해 신고 원문을 가져오는 방식은 채택하지 않는다. 채팅 증거 확보를 포함해 성공 기준을 먼저 정하고, 부분 실패에서 메일 증거 없는 ‘접수 완료’를 반환하지 않는다. 메일함의 접근 권한·상태·결과 통지·파기·백업과 개인정보 고지를 검증한다.

## 필수 검증 시나리오

1. 공지·댓글·채팅·친구 편지·닉네임·섬 이름/소개·퀘스트 제목 각각 신고 가능. 집중 주제 원문은 타인에게 보이지 않고 정형 문구만 전달. 읽을 수 없는 비공개 콘텐츠 ID를 직접 보내면 접수·원문 열람 불가.
2. 편지 신고가 먼저 확정되면 이후 닫아도 증거 유지. 닫기가 먼저 확정되면 신규 신고 거절. 중복 요청과 응답 유실 재시도도 한 건으로 귀결. 수정·하드 삭제된 공지 등은 조회 당시의 유효한 서버 스냅샷 토큰으로 원문·열람 권한 검증. 새 요청 ID의 동일 리비전 신고가 긴급 사유를 추가하면 기존 사건을 승격하고 멱등 알림; 원문 파기 뒤 새 위해 정황은 별도 우선 제보로 평가.
3. 신고 시점의 작성자·원문 버전을 고정. 이후 수정·삭제·탈퇴로 증거를 다른 내용으로 바꾸지 않음. 미확보한 과거 원문을 추정하지 않음.
4. 신고한 콘텐츠만 개인 숨김. ‘함께 차단’ 미선택이면 상대의 모든 글을 숨기거나 친구 관계를 변경하지 않음.
5. 차단 시 양방향 편지/친구 요청 차단. 차단자가 보는 채팅·댓글·사용자 공지, 알림·목록 미리보기·재접속 캐시에서 상대 콘텐츠가 새어 나오지 않음. 타인이 쓴 공지의 현재 리비전을 차단 대상이 수정하거나 수정자가 탈퇴해도 숨김 유지. 닉네임·사용자 소개와 차단 대상이 현재 수정한 섬 이름·소개도 서버에서 중립 대체하고 섬 기능은 유지.
6. 커뮤니티 제한은 집중·기록을 보존하면서 모든 UGC 쓰기 우회를 막음. 전체 정지는 기존 세션·실시간 연결까지 반영하되 이의제기·탈퇴 접근은 보존.
7. 운영자가 확인한 재위반만 경고→7일→30일→영구 단계로 상승. 동시 신고는 대상·필드·리비전 고유 표지를 원자 예약해 위반 판단 ID 하나로 묶고, 원문 파기 뒤 늦은 신고도 중복 상승하지 않음. keyed digest 키 교체 전후 동일 입력·파기 표지 조회 검증.
8. 7일/30일 만료 경계·6개월 무위반 초기화·영구 정지 제외·경고의 기산점·검토 중 신고 경계를 검증. 오래된 초기화 예약 작업이 새 위반/상위 제재 확정 직후 실행돼도 마지막 위반 시각·제재 세대 비교로 무효화.
9. 확인된 답장 주소가 있는 사건은 최초 결과 답장 발송, 답장 주소가 없는 사건은 종결부터 원문 30일 파기. 미확인 주소는 종결 후 7일에 폐기·무연락 전환하고 그때부터 30일 파기. 답장 재시도로 기한 연장 안 됨. 직접 수신 메일은 수신 후 24시간 분류·7일 내 전환/파기/근거 있는 예외를 검증. 제재 최소 이력, 법적 보존 예외가 분리되고 백업 복원 시 파기 대상이 다시 노출되지 않음.
10. 긴급 선택만으로 자동 계정 정지하지 않음. 담당 알림 실패/부재 시 대체 경로, 임시 정지 최초 24시간·7일 상한과 예외 재검토, 오판 복구, 신고자 신원 비노출 확인.
11. 정지된 방장 때문에 섬 운영이나 주민 탈퇴가 막히지 않음. 방문자가 신고/차단해도 원래 게시판 접근 권한을 넘어선 정보가 노출되지 않음.
12. 외부 CSAM 의심 자료를 가리키는 텍스트 신고 훈련은 합성된 무해한 텍스트·사건 메타데이터로 수행. 실제 이미지·영상을 업로드하거나 테스트 자료로 사용하지 않음.
13. 기존 이미지 검사 API에 정상 합성 PNG만 보내 인가·속도 제한·외부 전송·로그 민감정보 배제·오류 시 처리와 개인정보 고지 일치를 확인. 불법 자료로 시험하지 않음.

## 티켓 완료와 출시의 구분

1670은 정책과 부수 작업 범위를 문서로 확정하는 티켓이다. [완료조건 판정](gap-review-2026-09-24.md#2026-09-24-완료-판정)에 따라 네 문서 완료조건은 충족했다. **새 티켓을 지금 만들지 않아도 1670의 문서 작업은 완료다.** D 상세안의 조정, 메일 제공자 검증과 회사별 사실 확인은 실제 구현·출시 작업에서 추적한다. 2.0 출시 전에는 신고·차단·필터·운영·선택적 결과 이메일이 동작해야 하며, 이 문서나 API 단위 테스트만으로 출시 조건 충족을 주장하지 않는다.
