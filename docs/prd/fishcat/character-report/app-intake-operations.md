# 앱 내 신고 접수와 운영 처리

2026-11-12 Play 재검토 보완. 서버·앱 PR을 준비한 상태이며 배포 완료를 뜻하지 않는다.

## 접수 계약

- `POST /reports`: 로그인 세션의 사용자(게스트 포함)가 `requestId` UUID, `targetType`, `targetId`, 선택 `targetUserId`, `reason`, `details`(1~2,000자), 선택 `submittedText`(5,000자 이하)를 제출한다. 일반 신고는 `OTHER`와 상황 설명을 쓴다.
- Business가 검증한 AT의 `sessionId`·`authGeneration`을 신고 본문과 분리해 내부 요청에 전달한다. Data는 users → auth_sessions 순으로 잠근 같은 트랜잭션에서 현재 세션을 확인한 뒤 신규 접수·재시도를 처리한다. 로그아웃 뒤에는 Redis 거부목록 상태와 무관하게 둘 다 거절한다. 앱이 세션 증거를 직접 지정할 수 없다.
- `targetType`: USER, LETTER, ISLAND_MESSAGE, NOTICE, NOTICE_COMMENT, GUESTBOOK, ISLAND, OTHER. OTHER 외에는 대상 UUID가 필요하다.
- 대상 ID·복사한 텍스트는 **신고자의 진술**이다. 접수는 대상의 존재·작성자·원본 일치·위반 확정을 증명하지 않는다. 클라이언트가 남의 비공개 원문을 서버에서 가져오는 기능은 제공하지 않는다. 운영자는 실제 대상·열람 문맥·작성 시점을 따로 대조하고 진술만으로 제재하지 않는다.
- 저장 성공 뒤 `reportId`와 `receivedAt`만 반환한다. 일반 사용자에게 사건 목록·상대 신고 내역은 공개하지 않는다. 같은 사용자·동일 요청 키·동일 본문 재시도는 같은 번호, 다른 본문은 409다. 계정당 1시간 20건이며 이미 접수한 요청의 재시도는 한도를 소비하지 않는다.
- 신고는 자동 차단·자동 전체 숨김을 실행하지 않는다. 앱의 사용자 차단은 별도 선택이다. 이미지/영상 첨부와 외부 URL 자동 다운로드는 하지 않는다.

## 운영자가 조회하고 처리하기

기존 console-member 개인별 서비스 자격과 `X-Backoffice-Environment: dev|prod`를 사용한다. 토큰은 기존 비밀 저장소에서 가져오고 문서·터미널 기록·스크린샷에 남기지 않는다. 사용자 JWT와 Business 서비스 토큰으로는 아래 경로에 접근할 수 없다.

1. `GET /internal/admin/content/reports?cursor=<마지막 id>`로 미종결 신고를 오래된 순으로 100건씩 읽는다. 처음에는 cursor를 생략한다. 조회 결과는 민감 자료이며 일반 로그·이슈·채팅방에 본문을 복사하지 않는다.
2. `CHILD_SAFETY`, `THREAT`는 긴급 대응 절차(`legal-response.md`)에 따라 우선 판단한다. 위험한 링크·파일을 자동으로 열거나 내려받지 않는다.
3. 대상 식별자와 신고 진술을 실제 기록에 대조한다. 원본이 없거나 확인이 부족하면 그 사실을 판단에 남긴다. 권한이 확인된 기존 콘텐츠 삭제/계정 조치 절차로 처리하며, 이 신고 API는 조치를 대신 실행하지 않는다. 운영 DB 변경은 기존 소유자 승인·백업·복구 규칙을 따른다.
4. 실제 조치를 끝낸 경우에만 `POST /internal/admin/content/reports/{reportId}/close`에 `{ "status": "RESOLVED", "resolution": "조치 기록 위치와 판단 근거" }`를 보낸다. 위반 확인이 어려우면 DISMISSED로 종결한다. 처리자·최초 종결 시각은 서버가 기록한다. 재종결은 409로 막아 파기 시점을 연장하지 않는다.
5. 앱은 접수 확인만 제공한다. 별도 결과 수신함과 이메일 자동 발송은 제공하지 않는다. 지원 문의는 접수 번호로 대조하되 번호만으로 신고자 인증을 대체하지 않는다.

개발·운영 프로파일은 P6Spy 바인딩 로깅을 끈다(`application-dev.yml`, `application-prod.yml`). 신고 DTO를 요청/오류 로그에 추가하지 않는다.

운영 담당자는 기존 신고 창구 운영팀이다. 앱 배포 전 개인별 자격으로 위 목록 조회·종결을 로컬/개발 환경에서 확인하고 일일 미종결 검토 담당자를 지정한다. 자동 알림을 연결했다고 주장하지 않는다.

## 보존과 파기

- 일반 사건 전체(진술·신고자/대상 ID·사유·처리 기록)는 최초 종결 후 30일이 지나면 매시간 파기 작업이 삭제한다. 미종결은 검토에 필요한 기간만 보존하고 운영팀이 매일 검토한다. 과거 메일 저장소는 별도의 기존 파기 절차를 따른다.
- 적법한 보존 요청이 있는 경우에만 운영자가 해당 사건 행을 잠근 트랜잭션에서 `legal_hold=true`, `hold_reason`에 근거·범위·재검토일·담당자를 기록한다. 사유 없는 hold는 DB 제약으로 거절한다. 만료 전에 기록해야 하며 이미 파기된 자료가 복원된다고 약속하지 않는다. 사유가 끝나면 같은 절차로 hold를 해제하고 다음 파기 주기에 삭제한다.
- 파기 이후 같은 요청 키를 다시 보내면 새 접수가 될 수 있다. 앱의 동일 시도 재전송용 키이며 영구 사건 보존 수단이 아니다.
- 백업의 보존·복원 접근과 외부 처리자 삭제는 별도 개인정보 운영 절차를 따른다. 운영 저장소 삭제를 모든 백업 삭제로 표현하지 않는다.

## 배포 순서

Data V16 → Data/Business 서버 및 nginx `/reports` 전달 설정 → 앱 순서다. 개발·위성 nginx 정본에도 `/reports`를 추가하며, 실제 운영 프록시 반영 전에는 앱을 배포하지 않는다. 서버 선행 배포가 없는 앱에서는 접수가 실패하므로 앱 배포를 먼저 하지 않는다. 운영 배포·Play 심사 제출은 이번 구현에 포함하지 않는다.
