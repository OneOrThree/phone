# 공통 API 계약 — PRD

GROMO-1750 · 2026-09-12 · [문서 색인](README.md) · [정책 정본](policy.md)

## 문제

화면별 스펙은 69개 화면의 66개 도메인 계약과 14개 이벤트를 제안한다. 각 기능이 독자적으로 응답·재시도·오류를 만들면 같은 앱에서 빈 데이터, 중복 결제, 오래된 상태 수정, 일부 데이터 실패를 서로 다르게 처리하게 된다. 화면 집계가 이 차이를 숨기면 원자 작업이 여러 서버 호출로 찢어지는 문제도 생긴다.

기준 main의 Business `ApiExceptionHandler`와 인증 필터는 평면 `{code,message}`를 쓴다. Data의 `ErrorResponse`와 chat의 오류도 기본 JSON은 같은 평면 두 필드다. '오류 봉투 세 갈래'는 서로 다른 소유·변환 지점이 존재한다는 뜻이며 이미 세 가지 JSON 구조가 있다는 뜻은 아니다. 새 앱 계약은 `{error:{code,message,field,retryable},requestId}`이므로 명시적인 외부 경계가 필요하다.

## 목표

1. 앱이 신규 Business API를 `/focus-sessions`, `/screens/home`처럼 호출한다.
2. 데이터 없음·빈 목록·마지막 페이지·오류를 한 규칙으로 읽는다.
3. 응답 유실 후 같은 명령을 재시도하면 원래 결과를 복구하고 중복 보상·차감·소유권 생성이 없다.
4. 동시에 변경한 자원은 `expectedVersion` 충돌로 드러내고 최신 상태를 재확인한다.
5. 검증한 사용자와 현재 섬이 모든 내부 조각에 일관되게 전달된다.
6. 화면 첫 조회는 BFF 1회로 제공하되 도메인 내부 API와 원자 쓰기는 독립적으로 유지한다.
7. 요청·내부 호출·비동기 이벤트를 추적할 수 있고 민감한 원문을 로그에 남기지 않는다.

## 범위와 호환

- 신규 Business JSON 라우팅·봉투·오류·키·버전·커서·BFF 계약을 설계한다. 실제 구현은 1751~1753 및 후속 도메인 티켓이다.
- 신규 `/link-previews`도 JSON 규약을 적용한다. PNG 썸네일은 바이너리 응답을 유지하며 인증·오류·추적 헤더는 공통 규약을 따른다. 기존 Business 미리보기 경로의 전환·별칭 여부는 1751 계약 테스트로 명시한다.
- 기존 Data `/api/v1`과 chat `/api/v1/chat`은 기존 경로·상태·봉투를 보존한다. 이 문서의 범용 response advice로 기존 서비스를 일괄 감싸지 않는다.
- private Drive, 직접 업로드, 원본 영구 보관, 실제 운영 배포, 13개 화면별 필수/선택 필드 최종표는 이번 문서 티켓 범위가 아니다.
- 값이 결정되지 않은 보상율·가격·권한·기여 배분·자산 승계·우체통 정책을 공통 규약으로 확정하지 않는다.

## 수용 시나리오

- 현재 집중이 없으면 `200 {"data":null}`이며 '없음'을 404로 오인하지 않는다. 존재를 요구한 다른 사용자의 세션 ID가 없거나 보이지 않으면 해당 도메인 접근 규칙을 따른다.
- 종료를 커밋한 직후 네트워크가 끊겨도 앱은 같은 키·본문으로 재전송해 같은 종료 결과를 받는다. 두 HTTP 시도의 `X-Request-Id`는 서로 다르고 해당 시도 오류 본문과 일치한다.
- 유효한 선택적 게스트 AT로 소셜 로그인하면 검증한 기존 subject를 승계해 집중 기록·지갑·그룹이 유지된다. 제시한 AT 오류를 익명 신규 가입으로 처리하지 않는다.
- 구버전 receipt는 저장 contractVersion별 안전한 응답 변환 또는 명시 거절로 처리하며 원 명령을 다시 실행하지 않는다. 자원 권한 소멸 뒤 재생은 활성 본인의 도메인 명시 최소 완료 증거로 제한한다.
- 이미 저장된 동일 키에 다른 구매 본문을 보내면 409 `IDEMPOTENCY_KEY_REUSED`이고 새 차감은 없다.
- 다른 사용자가 버전을 올린 뒤 낡은 버전으로 변경하면 409 `VERSION_CONFLICT`와 인가된 최신 상태를 받는다. UI는 자동으로 새 버전을 덮어 재구매하지 않고 재확인한다.
- 전체 예산이 남아 있는 동안 홈의 선택 조각만 일시 실패하면 해당 필드 null이다. 전체 deadline 소진은504가 우선이며, 사용자/섬 권한 실패를 포함해 화면 조기 종료가 확정되면 남은 실제 HTTP I/O를 취소한다.
- 앱이 `X-User-Id`에 타인 UUID를 넣어도 내부 Data가 받는 사용자 ID는 검증한 JWT subject 하나다.
- 오류 발생 시 로그에서 requestId로 경계를 따라갈 수 있다. Authorization·토큰·미리보기 URL·요청 본문은 로그에서 찾을 수 없어야 한다.

## 완료 조건과 남은 일

이 문서 티켓은 FR01~FR11의 설계와 원본 보존이 완료되면 리뷰할 수 있다. 실제 실행 증거는 구현 티켓이 남긴다. DB 유일성·동시성·상류 실패·PNG/auth 회귀 테스트를 이 문서 작성으로 통과한 것으로 표시하지 않는다.

배치 전체가 완료된 뒤에는 구현된 코드·트랜잭션·폴백·패킷 이동·로그 추적을 연결한 ELI5 학습 가이드가 추가로 필요하다. 아직 없는 코드의 파일 경로를 구현 정본처럼 제시하지 않는다.
