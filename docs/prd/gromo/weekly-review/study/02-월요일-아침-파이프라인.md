# 2편 — 월요일 아침 파이프라인: 배치 안에서 벌어지는 일

> 다이어그램: **`02-월요일-아침-파이프라인.drawio`** (한 사용자 기준 전체 플로우차트)

1편의 "길 B"를 확대한다. 월요일 08:00, 서버 안에서 사용자 한 명당
아래 7단계가 순서대로 돈다. **LLM이 등장하는 건 5단계 딱 한 곳**이고,
그 앞 4단계가 전부 "LLM에게 계산을 안 시키기 위한" 준비다.

## 0단계 — 스케줄러가 깨어난다

Spring의 `@Scheduled(cron = "0 0 8 * * MON", zone = "Asia/Seoul")` 한 줄이면
매주 월요일 08:00에 메서드가 자동 실행된다. 새로 배울 인프라가 아니라
Spring 내장 기능이다.

단, `@Scheduled`는 **놓친 실행을 복구해 주지 않는다** — 월요일 08:00에 서버가
내려가 있었다면 그 주 배치는 그냥 사라진다. 그래서 서버 기동 시(또는 매시간)
"이번 주 리포트가 아직 없는 사용자가 있나"를 확인해 이어서 처리하는 캐치업
로직을 함께 둔다. 멱등성(1단계) 덕에 캐치업이 몇 번 겹쳐 돌아도 안전하다.

깨어나면 대상 사용자 목록을 페이지 단위로 끊어 가져온다(한 번에 전부 메모리에
올리지 않기 — 사용자가 늘어도 터지지 않게). 이후 단계는 **사용자별로 독립**
실행이라, 한 명이 실패해도 나머지에 영향이 없다.

함정 하나: 서버가 여러 대로 늘어나면 `@Scheduled`는 **인스턴스마다** 깨어난다.
1단계의 멱등성이 이중 발행은 막아주지만, 같은 배치를 여러 대가 나눠 도는 건
낭비라서 정석은 분산 잠금(ShedLock 등)으로 한 대만 돌게 하는 것이다.
지금 gromo dev는 단일 인스턴스라 당장은 문제 없다 — 스케일아웃 때 기억할 것.

## 1단계 — 멱등성 체크: 이미 만들었으면 건너뛴다

`weekly_review`에 `(user_id, week_start)` 유니크 제약을 걸고, 이미 그 주
리포트가 있으면 skip. 이게 있어야 배치가 중간에 죽어서 **재실행해도**
같은 사용자에게 리포트가 두 번 생기지 않는다.
"같은 작업을 두 번 돌려도 결과가 한 번 돈 것과 같다"를 **멱등성(idempotency)**
이라 하고, 모든 배치의 기본 안전장치다.

디테일 두 개가 중요하다:

- **skip 판정은 "행이 있나"가 아니라 상태로.** 행에 `status`
  (`PUBLISHED / INSUFFICIENT / …`)를 두고, **PUBLISHED만 skip**한다.
  "데이터 부족" 행까지 행 존재만 보고 건너뛰면, 일요일 데이터가 뒤늦게 동기화된
  사용자가 영영 발행으로 승격되지 못한다(캐치업이 재평가할 길이 막힘).
- **푸시 여부도 행에 기록**(`push_sent` 플래그). 저장 직후·푸시 직전에 서버가
  죽으면, 이 플래그가 없을 때 재실행이 "리포트 있네" 하고 푸시를 영영 건너뛴다.
  재실행은 `PUBLISHED && !push_sent`인 행의 푸시를 회수한다.

## 2단계 — 발행 게이트: 침묵할지 먼저 결정한다

지난주 데이터로 유효일(그날 세션이 1개라도 있는 날)을 센다.
"세션 1개라도"의 정확한 정의 — 완료된 세션만 세나, 최소 몇 분 이상이어야 하나,
중도 포기 세션은 어느 쪽인가 — 는 완주율의 분모 정의와 함께 prd.md 확정 대상이다.
느슨하게 잡으면 3분짜리 테스트 세션으로도 발행 자격이 생긴다.

| 판정 | 조건 | 결과 |
|---|---|---|
| `publishable` | 이번 주 유효일 ≥ 3 | 리포트 발행 |
| `comparable` | publishable **그리고** 지난주 유효일 ≥ 5 **그리고** 짝맞춤일 ≥ 3 | "지난주 대비" 문장·점수까지 포함 |
| 미달 | 위 조건 실패 | **리포트 없음.** "이번 주는 데이터가 부족했어요" 안내만 저장, LLM 호출도 없음 |

ui.html의 프리셋 "데이터 부족"·"신규 유저"가 이 게이트에 걸린 화면이다.
게이트에서 떨어지면 **여기서 파이프라인이 끝난다** — 비용도 0이다.

## 3단계 — 집계: SQL이 모든 숫자를 만든다

지난 2주 `focus_session`을 SELECT해서 계산한다. 전부 평범한 SQL/자바 산수다.

- 요일별 몰입 분(이번 주 7칸 + 지난주 7칸, **데이터 없는 날은 null** — 0 아님)
- 총 몰입 시간, 목표 달성일 수(일 목표 분 이상인 날), 완주율(완료 세션/전체 세션)
- 최장 세션·평균 세션
- 개인 최고기록 경신 여부 — 이것만은 **지난 2주 조회로 못 구한다**(전 기간과
  비교해야 하니까). 매번 전체 이력을 스캔하는 대신, 사용자별 최고기록 요약
  값(컬럼 또는 테이블)을 유지하며 비교·갱신한다
- 짝맞춤 비교: **양쪽 주 모두 데이터가 있는 날끼리만** 합산해 증감률(Δ%) 계산

## 4단계 — 채점 + 숫자 문장 생성: 규칙이 판정한다

집계값을 규칙에 넣어 확정한다. 여기까지 **LLM은 아직 등장하지 않았다.**

- **성취 뱃지 6종**: 최고기록 / 목표 5일+ / 몰입 증가(+10%↑) / 폰 사용 감소(−10%↓) / 개근(7일) / 완주율 80%
- **"이번 주의 한 줄" 축 선택**: 기록 갱신 > |Δ|≥20% > 목표 5일+ > 총량 순으로
  가장 할 말 있는 축 **하나만** 고른다
- **종합 점수**(점수형 채택 시): 목표 40 + 전주 대비 25 + 완주율 20 + 폰 사용 15
  (⚠️ 가중치는 아직 근거 없는 미확정안)
- **숫자가 들어가는 모든 문장은 여기서 템플릿으로 생성**:
  `"총 몰입 {19시간 23분}, 지난주보다 {4시간 12분} 늘었어요"` 처럼
  자리에 값을 끼워 넣는다. LLM이 이 문장들을 만들지 않는다.

## 5단계 — LLM 호출: 해석과 제안만 받는다

계산이 **끝난** 집계 JSON을 Claude API에 보내고, 두 가지만 돌려받는다:

1. **공감 해석 문단** — "목요일에 세 시간 몰입한 날이 이번 주를 끌어올렸네요…"
2. **다음 주 행동 제안 1~2개** — "토요일 240분 중 60분을 일요일로 옮겨보기"

요청·응답의 정확한 생김새, 검증, 실패 시 폴백은 3편에서 해부한다.
여기서 기억할 것 하나: **LLM이 실패해도 리포트는 나간다.** 해석 자리에
템플릿 문장을 대신 넣는 폴백이 있어서, 5단계는 파이프라인의
단일 장애점(SPOF)이 아니다.

## 6단계 — 저장: 완제품을 박제한다

점수·뱃지·템플릿 문장·LLM 해석을 `weekly_review` 한 행으로 INSERT.
이후 앱이 뭘 하든 이 행은 다시 계산되지 않는다(일관성 — 1편 참고).

## 7단계 — 푸시: FCM으로 알린다

"지난주 몰입 리포트가 도착했어요" + 리포트 화면 딥링크. FCM 발송은
프로젝트에 이미 있는 경로를 그대로 쓴다. 푸시 실패는 리포트 실패가 아니다 —
리포트는 이미 저장돼 있고, 사용자가 앱을 열면 어차피 보인다.

## 실패는 어디서 나고 어떻게 버티나 (요약)

| 단계 | 실패하면 | 대응 |
|---|---|---|
| 집계 SQL | 그 사용자만 실패 | try/catch로 격리, 로그 남기고 다음 사용자 진행 |
| LLM 호출 | 타임아웃·429·5xx | 재시도 1회 → 그래도 실패면 폴백 템플릿 (3편) |
| 저장 | 유니크 충돌 = 이미 있음 | 멱등 skip (1단계와 같은 원리) |
| 푸시 | 토큰 만료 등 | 리포트엔 영향 없음, 발송 실패만 기록 |
| 배치 전체 | 서버 재시작 등 | 재실행하면 멱등성 덕에 안 만든 사용자만 이어서 처리 |

상세한 운영 이야기(비용·레이트리밋·모니터링)는 5편.
