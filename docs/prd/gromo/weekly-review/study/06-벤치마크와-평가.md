# 6편 — 벤치마크와 평가: "잘 만들어졌다"를 숫자로 증명하는 법

> 다이어그램: **`06-벤치마크와-평가.drawio`** (평가 루프 전체 — 시험지 → 채점 → 회귀 → 실지표)

앞의 다섯 편으로 "돌아가는" 시스템은 만들 수 있다. 이 편은 마지막 질문을 다룬다:
**"이게 잘 만들어졌다는 걸 어떻게 증명하나?"**

요즘 AI 기능의 승부처는 모델을 만드는 게 아니라 **API를 얼마나 잘 쓰느냐**다.
그리고 "잘 쓴다"는 감이 아니라 채점으로 증명한다 — 구현을 시작하기 전에
**시험지와 채점지부터 만든다.** 순서가 핵심이다: 목표 → 검수 기준 → 시험지 →
채점 → 개선 루프 → 실전 임팩트 측정.

## 0. 목표부터: 이 기능은 뭘 달성하면 성공인가

채점지는 목표에서 역산된다. 목표 없이 만든 벤치마크는 "그럴듯함"을 잰다.

| 층 | 목표(안 — prd.md에서 확정) | 재는 방법 |
|---|---|---|
| 출시 전 품질 | 벤치마크 루브릭 평균 ≥ 8/10, 그물 통과율 ≥ 95% | 이 편의 시험지 |
| 출시 후 행동 | 리포트 열람률, "다음 주에 바꿔볼 것" 담기율 | 앱 계측 |
| 운영 | 폴백률 < 5%, 사용자당 비용 < 10원 | 5편의 모니터링 |

고객 CS 자동화라면 목표가 "운영부담 X% 절감"이겠지만, 우리 기능의 존재 이유는
**몰입 데이터를 다음 주 행동으로 바꾸는 것**이다. 그래서 최종 지표는 "AI가 좋은
문장을 썼나"가 아니라 "사용자가 제안을 담고 다음 주에 실제로 달라졌나"까지 간다.

## 1. 검수 기준: 좋은 해석·제안의 조건을 먼저 적는다

LLM 출력은 자유 텍스트라 "정답 문자열 일치"로 채점할 수 없다. 대신
**좋은 출력이 갖춰야 할 성질**을 루브릭(채점 기준표)으로 박는다. 각 축 0~2점, 10점 만점:

| 축 | 0점 | 2점 |
|---|---|---|
| ① 숫자 정합 | 입력에 없는 숫자 등장 | 모든 숫자가 입력 JSON과 일치 |
| ② 근거 연결 | 아무 주에나 붙는 덕담 | 이번 주 특징(요일·기록)을 구체적으로 짚음 |
| ③ 어조 | 비난·훈계조 | 잘한 점 먼저, 공감 유지 |
| ④ 제안 실행가능성 | "더 열심히 하세요" | 요일+분 단위로 실행 가능 ("토 240분 중 60분을 일로") |
| ⑤ 형식 | 스키마 위반·금칙어·길이 초과 | JSON 스키마·길이·금칙 전부 통과 |

①⑤는 3편의 검증 그물이 **자동 채점**하고, ②③④는 사람이 채점한다.
(LLM에게 채점을 시키는 LLM-as-judge 기법도 있지만, 심판도 LLM이면 같은 편향을
공유할 수 있어 **보조 수단**으로만 — 최종 판정은 사람.)

## 2. 시험지: In → 기대 Out을 미리 만들어 둔다

대표 입력 케이스 20~50개를 모은 게 시험지다. ui.html의 프리셋 5종이 출발점이고,
**경계와 함정 케이스**를 반드시 섞는다:

| 케이스 유형 | 입력 특징 | 기대하는 출력의 성질 (정답 문장이 아니라 성질!) |
|---|---|---|
| 좋은 주 | Δ+27%, 최고기록 경신 | 기록 경신을 해석에 반영, 다음 목표 제안 |
| 무너진 주 | Δ−40%, 목표 1일 | **비난 없이** 회복 가능한 첫걸음 하나만 제안 |
| 목표만 지킨 주 | 총량↓ 목표 6일 | 총량 감소보다 꾸준함을 먼저 짚음 |
| 턱걸이 발행 | 유효일 정확히 3일 | 부족한 데이터로 과장하지 않음 |
| 주말 붕괴형 | 평일 강세, 토일 0분대 | 요일 패턴을 짚되 "몰아치기 반동" 낙인 없이 |
| 폰 사용 증가 | 몰입↑ + 폰 사용↑ | 상충 신호를 얼버무리지 않고 한 축만 선택 |

각 케이스 = `입력 집계 JSON + 기대 성질 목록`. 기대 성질이 곧 루브릭 ②③④의
케이스별 채점 근거가 된다.

## 3. 채점지: 시트 하나로 관리한다

거창한 도구 필요 없다. CSV/구글시트 하나면 된다:

```
케이스ID | 입력 요약        | 프롬프트 버전 | 그물 통과 | ①정합 | ②근거 | ③어조 | ④실행 | ⑤형식 | 합계 | 메모
good-01  | Δ+27% 기록경신    | v3           | ✅       | 2     | 2     | 2     | 1     | 2     | 9    | 제안이 다소 추상적
crash-01 | Δ-40% 목표1일     | v3           | ✅       | 2     | 1     | 2     | 2     | 2     | 9    | 특징 언급 약함
edge-01  | 유효일 3일 턱걸이  | v3           | ❌(숫자)  | 0     | -     | -     | -     | -     | 0    | 없는 숫자 생성 → 그물 정상 작동
```

이 시트가 곧 **채점지 + 회귀 기록부**다. 열이 "프롬프트 버전"인 게 핵심 —
같은 시험지를 버전마다 다시 풀린다.

## 4. 러너: 배치 코드의 dry-run 모드를 재사용한다

벤치마크 실행기는 새 시스템이 아니라 **2편 배치의 dry-run 모드**다:

```
시험지 케이스 JSON 읽기 → (전처리는 이미 끝: 집계 JSON이 곧 전처리 결과물)
  → 5편 프롬프트 vN으로 LLM API 호출 → JSON 파싱·후처리 → 자동 채점(그물 4종)
  → 결과를 시트에 append → 사람이 ②③④ 루브릭 채점
```

- 일반적인 AI 파이프라인이면 이 앞에 전처리(예: 이미지면 OpenCV 크롭·보정)가
  붙지만, 우리는 입력이 정형 숫자라 **3단계 집계 SQL이 전처리 그 자체**다.
- 후처리도 지금은 얇다 — `max_tokens 600` + JSON 스키마 강제로 응답을 짧고
  구조화되게 설계했기 때문. 장문 응답(코칭 리포트 확장 등)을 받게 되면
  섹션 파서 같은 후처리 층이 그때 생긴다. **후처리가 얇은 건 우연이 아니라
  출력 계약을 좁게 설계한 대가**라는 걸 기억할 것.

## 5. 회귀: 시험지는 한 번 쓰고 버리는 게 아니다

프롬프트 한 줄, 모델 버전 하나를 바꿀 때마다 **같은 시험지를 다시 풀린다**:

```
vN 평균 9.1 / 그물 통과 96%  vs  vN+1 평균 8.2 / 통과 91%  →  vN+1 배포 금지
```

이게 5편 "프롬프트도 코드다"의 실행 수단이다. 코드에 테스트가 있듯 프롬프트에는
벤치마크가 있다. 점수가 떨어지면 배포하지 않는다 — 감이 아니라 채점지가 거부한다.

## 6. 실전 임팩트: 출시 후에 루프를 닫는다

벤치마크 점수는 "출시할 자격"이지 "효과의 증명"이 아니다. 효과는 실지표로 닫는다:

- **열람률**: 푸시 → 리포트 열람 전환
- **담기율**: "다음 주에 바꿔볼 것" 담기 클릭 / 리포트 열람
- **행동 변화**: 담은 사용자의 다음 주 해당 지표가 실제로 움직였나 (짝맞춤 비교)
- **운영**: 폴백률·비용 (5편 모니터링과 동일 축)

벤치 점수는 높은데 담기율이 낮다면 "문장은 좋은데 제안이 와닿지 않는다"는 뜻 —
루브릭 ④의 기준을 실데이터로 다시 조정한다. **시험지 ↔ 실지표가 서로를 교정하는
루프**가 완성형이다.

## 발표에서 받을 질문 4개 — 이 시리즈로 답하기

**Q1. AI를 어떻게 활용하나?**
계산·판정·숫자 문장은 전부 서버 규칙이 만들고, LLM은 계산이 끝난 집계 JSON을
받아 **해석 문단과 다음 주 제안만** 생성한다. 모델을 만드는 게 아니라 API를
구조로 감싸서 쓴다. (3편)

**Q2. 어떻게 동작하나?**
월요일 08:00 배치가 사용자별로 멱등 체크 → 발행 게이트 → SQL 집계 → 규칙 채점
→ LLM 호출 → 4중 검증 → 저장 → 푸시 순서로 돈다. 화면은 저장본을 읽기만 한다. (1·2편)

**Q3. 한계는 뭐고 어떻게 극복하나?**
① 비결정성·할루시네이션 → 역할 분리 + 검증 그물 + 폴백 (3편)
② 의미 품질은 기계로 못 잼 → 루브릭 벤치마크 + 회귀 + 표본 검수 (6편)
③ 외부 API 의존(장애·비용) → 페이싱·백오프·캐치업·예산 상한 (5편)
④ 그래도 남는 위험 → LLM이 죽어도 템플릿 리포트는 나가는 구조 (2편)

**Q4. 효과를 어떻게 증명하나?**
출시 전엔 시험지 채점(루브릭 평균·그물 통과율), 출시 후엔 열람률·담기율·행동
변화·폴백률·비용. 벤치와 실지표가 서로를 교정한다. (6편)
