# 5편 — 운영: 터지는 방식들, 돈이 나가는 방식, 막는 방법

> 다이어그램: **`05-운영-실패-비용.drawio`** (페이지 2장: ① 레이트리밋과 배치 페이싱 ② 비용 구조와 모니터링)

여기까지 만들면 "돌아는 간다". 이 편은 그걸 "믿고 돌릴 수 있다"로 바꾸는 내용이다.
외부 API를 배치에서 대량 호출할 때 반드시 만나는 문제 세 가지 — **레이트리밋, 비용,
조용한 품질 저하** — 를 다룬다.

## 1. 레이트리밋: 외부 API에는 속도 제한이 있다

LLM API는 계정마다 상한이 있다 — **분당 요청 수(RPM)만이 아니라 분당 입력
토큰·출력 토큰(ITPM/OTPM)에도** 각각 걸린다. 월요일 08:00에 사용자 수천 명을
한꺼번에 쏘면 서버가 죽는 게 아니라 **429 Too Many Requests** 응답이 돌아온다.
대응은 업계 표준 조합:

- **페이싱(pacing)**: 동시에 쏘는 요청을 소수(예: 동시 5개)로 제한하고 순차 소진.
  사용자 1만 명 × 호출당 3초 ÷ 동시 5 ≈ 100분 — 8시에 시작하면 오전 중 끝난다.
  "월요일 아침 발행"이라는 요구사항에는 충분하다. 단 두 가지 단서: ① 이 100분은
  재시도·지연 변동을 뺀 추정치지 마감 보장이 아니다(그래서 캐치업이 또 필요하다).
  ② 동시 5개는 페이싱 수단일 뿐 상한 준수 보장이 아니다 — 요청당 토큰이 크면
  RPM보다 토큰 상한에 먼저 걸리니, 계정의 실제 상한 수치를 보고 동시성을 정한다.
  (모든 사용자가 같은 초에 받을 필요가 없다는 걸 요구사항 단계에서 확정해 둘 것.)
- **지수 백오프(exponential backoff)**: 429를 받으면 1초 → 2초 → 4초처럼 점점 길게
  대기 후 재시도. 즉시 재시도는 상황을 악화시킬 뿐이다. 실전 디테일 셋:
  ① 응답에 `retry-after` 헤더가 오면 **그 값을 우선**한다(서버가 언제 다시 오라고
  알려주는 것). ② 대기 시간에 무작위 오차(jitter)를 섞는다 — 전부 정확히 같은
  간격으로 재시도하면 다시 한꺼번에 몰린다. ③ 공식 SDK는 **자체적으로도 재시도**
  하므로, 애플리케이션 재시도를 얹으면 곱으로 늘어난다 — 한쪽에서만 관리한다.
  헷갈리기 쉬운 구분: 이 백오프 재시도는 **전송 실패**(429·타임아웃 — 응답을 못 받음)
  이야기다. 3편의 "재시도 1회"는 **내용 검증 실패**(응답은 왔는데 JSON이 틀림 —
  다시 생성시켜 본다) 이야기로, 층이 다르다. 전송은 여러 번 두드려도 되지만,
  생성 재시도는 매번 돈이라 1회로 자른다.
- **우선순위 없음의 자유**: 배치라서 실시간성이 없으니, 밀리면 그냥 뒤로 밀면 된다.
  이게 1편에서 "미리 만들어 저장" 구조를 고른 덤 — 레이트리밋이 사용자 경험에 안 닿는다.

## 2. 비용: 얼마 나가는지 손으로 계산해 보기

과금은 `입력 토큰 × 입력 단가 + 출력 토큰 × 출력 단가`. 우리 호출 1건은:

| 항목 | 추정 | 근거 |
|---|---|---|
| 입력 | ~800 토큰 | system 프롬프트(~400) + 집계 JSON(~400). **원본 로그를 안 보내는 설계 덕에 이 크기로 고정** |
| 출력 | ~250 토큰 | 해석 한 문단 + 제안 2개 (max_tokens 600으로 상한) |

중간급 모델 단가를 입력 $3/백만 토큰, 출력 $15/백만 토큰이라 치면(정확한 값은
구현 시점에 공식 가격표 확인):

```
1건 ≈ 800×$3/1M + 250×$15/1M ≈ $0.006  (약 8원)
주간 비용 = 발행 대상 사용자 수 × 8원
  1,000명 → 주 8천 원, 월 3.5만 원 수준
```

체감 포인트 세 개:

1. **생각보다 싸다.** 설계(집계만 전송 + max_tokens 상한 + 게이트로 미발행자 제외)가
   비용을 구조적으로 눌러 놨기 때문이다. 원본 세션 로그를 통째로 보냈다면 입력이
   10배 이상 커졌다.
2. **비용은 로그로 실측한다.** 3편의 `usage` 응답을 매 호출 저장하면 "추정"이 아니라
   "장부"에 가까워진다. 주간 배치 끝에 `총 호출 수 / 총 토큰 / 환산 비용` 요약 로그.
   완전한 장부는 아니다 — 서버가 응답을 못 받고 죽은 호출은 과금됐어도 로컬에
   `usage`가 안 남는다. 그래서 "시도" 자체를 호출 전에 기록해 두고, 월말에
   공급자 청구 내역과 대사해 오차를 확인한다.
3. **상한을 코드에 박는다.** 주간 예산(예: 호출 수 상한)을 넘으면 남은 사용자는
   폴백 템플릿으로 발행하고 알람. 버그로 무한 호출이 나도 지갑이 뚫리지 않게.

## 3. 조용한 품질 저하: 죽지 않고 나빠지는 문제

배치가 초록불인데 리포트 품질이 무너지는 경우가 더 무섭다. 감시할 지표:

| 지표 | 뜻 | 알람 조건(예시) |
|---|---|---|
| 발행 성공률 | 대상자 중 리포트 생성 완료 비율 | < 99% |
| **폴백률** | LLM 검증 실패로 템플릿 대체된 비율 | > 5% — 프롬프트가 깨졌거나 모델 이상 |
| 게이트 미발행률 | 데이터 부족으로 침묵한 비율 | 급변 시 — 수집 쪽 장애 신호일 수 있음 |
| p95 호출 지연 | LLM 응답 시간 | 배치 총 소요가 발행 마감(예: 11시)을 위협할 때 |
| 주간 비용 | usage 합산 | 예산의 80% |

폴백률이 특히 중요하다: 검증 그물(3편) 덕에 나쁜 응답이 사용자에게 안 가는 대신,
**나빠졌다는 사실이 폴백률에만 나타난다.** 이걸 안 보면 "AI 코치"가 몇 주째
템플릿만 내보내고 있어도 아무도 모른다.

폴백률에도 사각지대가 있다: 문법·스키마·숫자가 전부 멀쩡한데 **내용이 엉뚱하거나
어조가 비난조인** 응답은 그물을 다 통과한다. 이건 기계 지표로 못 잡으므로
사람 눈으로 잡는다 — 지난주 실데이터 몇 케이스를 고정 평가셋으로 두고 프롬프트
변경 때마다 돌려 보고(아래 dry-run), 운영 중에도 매주 표본 몇 건을 직접 읽는다.

## 4. 개인정보: LLM에 뭘 보내도 되나

외부 API 전송 = 데이터가 회사 밖으로 나가는 것. 우리 설계는 노출 면적을 최소로
줄인다 — 이름·이메일·기기 정보·앱 목록·user_id를 보내지 않고, 시간·횟수·비율만
보낸다(LLM은 누구 데이터인지 알 필요가 없다).

단, **"식별자를 뺐으니 개인정보가 아니다"는 성립하지 않는다.** 한 사람의 주간
행동 패턴은 직접 식별자가 없어도 개인정보로 취급될 수 있다. 그래서 이 항목은
"고지 한 줄"이 아니라 릴리즈 게이트 체크리스트다:

- 개인정보처리방침에 "행동 통계의 외부 AI 처리" 명시 (1:1 문의 때처럼 게이트 항목)
- 처리 근거·위탁(제3자 제공) 해당 여부를 약관 기준으로 확인
- 공급자 쪽 데이터 보존·학습 미사용 정책 확인 — 기본값이 아니라 **계정 설정·계약으로
  확정**해야 하는 항목이 있다 (Zero Data Retention 등)
- 서버 로그에 집계 JSON을 통째로 남기지 않기 (로그도 데이터다)

## 5. 프롬프트도 코드다: 버전 관리

프롬프트 한 줄 수정이 폴백률을 5%p 움직일 수 있다. 그래서:

- 프롬프트는 **코드 저장소에 상수/리소스로** 두고 PR 리뷰를 거친다 (DB나 어드민에서
  즉석 수정 금지)
- `weekly_review`에 `prompt_version`을 기록 — 폴백률이 튀면 어느 버전부터인지 즉시 추적
- 바꿀 땐 지난주 실데이터 몇 건으로 **오프라인 리허설**(배치 코드를 dry-run 모드로
  돌려 응답만 눈으로 확인) 후 반영

## 이 시리즈가 다 끝나고 남는 그림

```
믿을 수 있는 이유가 층마다 하나씩 있다:
  숫자를 못 틀림   → LLM에게 계산을 안 시키니까 (3편)
  틀려도 안 나감   → 검증 4중 그물 + 폴백 (3편)
  죽어도 다시 됨   → 멱등 배치 (2편)
  몰라도 들킴     → 폴백률·비용 모니터링 (5편)
  비싸질 수 없음   → 집계만 전송 + max_tokens + 예산 상한 (5편)
```

구현 순서 제안: `weekly_review` 테이블 + 집계·채점(LLM 없이, 여기까지만으로도
템플릿 리포트가 나간다) → 조회 API + 앱 화면 → LLM 붙이기 → 푸시 → 모니터링.
**LLM은 마지막에 붙여도 되는 구조**라는 게 이 설계의 가장 큰 실용적 장점이다.

시리즈 곳곳에서 "prd.md 확정 대상"으로 미룬 결정을 모으면 이렇다:

- [ ] 주 경계의 정확한 정의(KST 반개구간의 UTC 변환)와 자정 걸친 세션 배분 (1편)
- [ ] 마감(08:00) 이후 도착한 데이터 정책 — 무시 확정 or 재계산 (1편)
- [ ] 축별 결측 해석 — 몰입 세션(이벤트)의 "행 없음"을 null로 볼지 0으로 볼지 (README)
- [ ] 유효일·완주율 분모의 정확한 정의 — 세션 완료 상태·최소 시간 조건 (2편)
- [ ] `INSUFFICIENT → PUBLISHED` 승격 재평가 정책과 상태 전이 (2편)
- [ ] 스크린타임 결측 사용자의 "폰 사용" 뱃지·점수 처리 + 측정 대상 변경 감지 계약 (1편)
- [ ] 종합 점수 가중치 40/25/20/15 — 현재 근거 없음, 뱃지형/점수형 선택 포함 (ui.html)
- [ ] LLM 프롬프트·응답 계약과 검증 규칙의 정본화 (3편)
