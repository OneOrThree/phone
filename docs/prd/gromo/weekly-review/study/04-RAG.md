# 4편 — RAG는 뭐고, 우리는 필요한가

> 다이어그램: **`04-RAG.drawio`** (페이지 2장: ① 교과서 RAG 파이프라인 ② 우리 기능의 현실)

## 결론부터: 이 기능에 벡터 DB 기반 RAG는 **지금 필요 없다**

이 결론을 스스로 판단할 수 있게 되는 게 이 편의 목표다.
"AI 기능 = RAG 필수"가 아니다. RAG는 특정 문제를 푸는 특정 도구고,
우리 문제는 그 문제가 아니다.

## RAG가 푸는 문제

LLM에는 근본적인 한계가 있다: **모델은 학습 시점까지의 일반 지식만 안다.**
우리 서비스의 DB, 사내 문서, 오늘 아침 데이터는 모른다. 그렇다고 매 요청에
회사 문서 전체를 넣을 수도 없다 — 토큰 한도(컨텍스트 윈도)와 비용 때문이다.

**RAG(Retrieval-Augmented Generation, 검색 증강 생성)** 는 이 틈을 메우는 패턴이다:

> 질문과 **관련 있는 자료만 찾아서(Retrieval)**, 프롬프트에 **끼워 넣고(Augment)**,
> 그걸 근거로 **답을 생성(Generation)** 시킨다.

## 교과서 RAG 파이프라인 (다이어그램 페이지 1)

두 단계로 나뉜다.

**사전 준비 (문서 넣을 때 1회):**

```
문서들 → 청크로 쪼갬(수백 자 단위) → 임베딩 모델 → 벡터(숫자 배열) → 벡터 DB에 저장
```

- **임베딩(embedding)**: 텍스트를 "의미 좌표"인 숫자 배열(예: 1536차원)로 바꾸는 것.
  의미가 비슷한 문장일수록 좌표가 가깝다 — "몰입이 늘었다"와 "집중 시간이 증가했다"는
  단어가 달라도 좌표상 이웃이다.
- **벡터 DB**: 이 좌표들을 저장하고 "이 좌표와 가장 가까운 것 k개"를 빨리 찾아주는 DB.
  전문 제품(Pinecone 등)도 있지만 **PostgreSQL + pgvector 확장**으로도 된다
  (우리 스택이면 이 선택지가 자연스럽다).

**질문할 때 (매 요청):**

```
질문 → 임베딩 → 벡터 DB에서 유사한 청크 top-k 검색 → [질문 + 찾은 청크들]을 LLM에 → 답변
```

핵심 통찰: **RAG의 본질은 "LLM에게 뭘 보여줄지 고르는 검색 문제"다.**
LLM 부분은 3편에서 배운 API 호출 그대로고, 새로운 건 앞단의 검색뿐이다.

## 그런데 우리 상황을 보자 (다이어그램 페이지 2)

RAG의 "Retrieval"이 필요한 건 **자료가 많고, 뭘 보여줄지 골라야 할 때**다.
우리 주간 리포트는:

| RAG가 필요한 상황 | 우리 상황 |
|---|---|
| 자유로운 질문이 들어온다 (뭘 물을지 모름) | 질문이 없다. 매주 똑같은 작업 1개 |
| 자료가 방대하다 (문서 수천 개) | 필요한 자료 = 그 사용자의 **지난 2주 세션** 뿐 |
| 뭘 보여줄지 의미 검색으로 골라야 한다 | 뭘 보여줄지 이미 안다 → **SQL 한 방** |
| 자료가 비정형 텍스트다 | 정형 데이터(시간·횟수)다. 임베딩할 것도 없다 |

그래서 우리 파이프라인에서 Retrieval 자리는 **3단계 집계 SQL이 이미 차지하고 있다.**
넓게 보면 "DB에서 관련 데이터를 가져와 프롬프트에 넣는다"는 구조 자체는 RAG와
같은 정신이다 — 다만 검색이 벡터 유사도가 아니라 `WHERE user_id = ? AND week = ?`일
뿐이다. 이 구분을 할 수 있으면 "왜 RAG 안 썼어요?"라는 질문에
**"Retrieval이 결정론적이라 벡터 검색이 필요 없었습니다"** 라고 답할 수 있다.

## 그럼 RAG가 진짜 필요해지는 순간은 언제인가

이 기능이 진화하면 생길 수 있는 시나리오 두 개 — 이때 pgvector를 붙이면 된다:

1. **"과거의 비슷한 주" 회상**: 리포트가 12주쯤 쌓인 뒤, "이번 주와 패턴이 비슷했던
   9월 둘째 주에는 ○○로 회복했었죠"라고 말하게 하려면. 단, 여기서도 순서가 있다 —
   주간 패턴은 요일별 분·완주율 같은 **정형 숫자 벡터**라서, 텍스트 임베딩보다
   SQL 거리 계산(숫자 벡터 유사도)이 더 정확하고 왜 비슷한지 설명도 된다.
   텍스트 임베딩 검색이 이기는 건 "해석 문단들" 같은 비정형 텍스트를 뒤질 때다.
   → 교훈 반복: 도구(RAG)가 아니라 "뭘 무엇으로 검색하나"부터 정의한다.
2. **코칭 지식베이스**: 집중력·습관 관련 아티클 수백 편을 넣어 두고, 이번 주 상황과
   맞는 근거 있는 조언을 골라 인용하게 하려면 — 문서가 많고 뭘 고를지 의미 검색이
   필요하니 교과서 RAG 그대로.

둘 다 **지금 버전의 요구사항이 아니다.** PRD에는 "확장 시나리오"로만 적는다.

## 용어 최소 사전

| 용어 | 뜻 한 줄 |
|---|---|
| 컨텍스트 윈도 | LLM이 한 번에 읽을 수 있는 토큰 한도. "다 넣으면 되잖아"가 안 되는 이유 |
| 임베딩 | 텍스트 → 의미 좌표(숫자 배열). 비슷한 의미 = 가까운 좌표 |
| 벡터 DB | 의미 좌표를 저장하고 최근접 k개를 빨리 찾는 DB. pgvector = PostgreSQL 확장판 |
| top-k | 유사도 상위 k개만 골라 프롬프트에 넣는 것 |
| 청크 | 문서를 검색 단위로 쪼갠 조각. 너무 크면 낭비, 너무 작으면 맥락 소실 |
