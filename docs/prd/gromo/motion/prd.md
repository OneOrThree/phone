## 1. 배경 — 왜 지금 모션인가

gromo는 **모션 인프라가 이미 훌륭한데 확산이 안 된 상태**다. 새로 깔 것이 없고, 이미 잘 만든 것을 퍼뜨리는 일이다.

**이미 있는 것**

| 자산 | 위치 | 수준 |
| --- | --- | --- |
| Reanimated 4.5 + worklets | `package.json` | 최신. CSS·imperative·layout 세 API 모두 사용 중 |
| 눌림 피드백 프리미티브 | `PressableScale.tsx` | 스케일 + 스프링 + 햅틱 + 탭사운드 + a11y 기본값 |
| 반응형 '동작 줄이기' 훅 | `useReduceMotion.ts` | reanimated의 비반응형 문제까지 해결. 테스트 3개 |
| 물리 컨페티 | `ConfettiBurst.tsx` | 44조각 · 장애물 물리 · 중력센서 틸트 |
| 축하 모달 | `GoalCelebrationModal.tsx` | 컨페티 + `InteractionManager` 게이팅까지 |
| 탭바 알약 슬라이드 | `TabBar.tsx` | 리퀴드글래스 + 오버슛 커브 |
| 차트 진입 stagger | `FocusResultScreen.tsx` | CSS 애니메이션 API · `fillMode` 활용 |

**섬처럼 고립돼 있다는 것이 문제다**

| 갭 | 근거 수치 |
| --- | --- |
| 주요 탭 화면이 정적 | 6개 중 **5개가 애니메이션 0** (홈·통계·전체·그룹·그룹방·로그인). 홈은 첫 진입 화면인데 840줄 전체에 `Animated` 한 줄이 없다 |
| 모션 토큰 부재 | duration이 파일마다 하드코딩(110·180·220·350·600·800). 오버슛 커브 `cubicBezier(0.34,1.56,0.64,1)`가 `TabBar`·`FocusResultScreen` 두 곳에 복붙 |
| 접근성 결함 | `useReduceMotion`이 **`PressableScale` 한 곳에서만** 쓰인다. 나머지 애니메이션 전부가 시스템 '동작 줄이기'를 무시 |
| 시트 무전환 | `SheetShell`이 `animationType="none"` → **시트 ~14곳**이 전부 즉시 튀어나옴. 딤도 페이드 없음 |
| 로딩 연출 부재 | 스켈레톤 **0개**. `ActivityIndicator`가 **38개 파일**. `StatsScreen`은 카드별 스피너 8개가 제각각 튐 |
| 피드백 표면 부재 | 토스트 **없음**. `Alert.alert` **149곳**(레거시·테스트 제외 85곳)이 성공 통보까지 담당. 캐릭터 장착 성공이 시스템 알럿 |
| 값 변화가 무연출 | 홈 진행바가 `width: '{pct}%'` 직접 대입. 코인·스트릭 칩도 즉시 교체 |
| 진행 어포던스 부재 | 집중 세션(1560줄)에 진행 링·바가 없다. 카운트다운·뽀모도로가 숫자만 바뀜 |
| 보상 연출 편차 | `GoalCelebrationModal`은 최고 수준인데, 리그 승급엔 컨페티가 없고 캐릭터 장착·그룹 생성·베팅 승리는 알럿/평문 |

**한 줄 요약** — 사용자가 매일 마주치는 표면(홈·시트·로딩·성공 통보)이 정적이고, 공들인 연출은 드물게 오는 화면(집중 결과·목표 달성)에만 몰려 있다.

## 2. 목표

**앱이 "완성도 있어 보이게" 만든다.** 조작적으로는 아래 4축에 일관된 모션을 부여하는 것이다.

| 축 | 무엇 | 지금 | 목표 |
| --- | --- | --- | --- |
| **진입** | 화면·카드·리스트·차트가 나타나는 방식 | 즉시 표시 | 아래에서 12pt 올라오며 stagger 진입 |
| **상태 전이** | 로딩→콘텐츠, 값 변화, 진행률 | 스피너→즉시 교체 | 스켈레톤→콘텐츠, 값은 보간, 진행바는 채워짐 |
| **피드백** | 눌림·성공·실패 | 눌림만 있음 | 눌림 톤 상향 + 토스트 도입 |
| **축하** | 목표 달성·승급·구매 | 편차 큼 | 컨페티 + 성공 햅틱으로 평준화 |

**부수 목표 — 접근성 정상화.** 신규 모션은 물론 **기존 모션 9곳까지** '동작 줄이기'를 존중하게 만든다. 이건 부가 기능이 아니라 현재 결함의 수정이다.

## 4. 모션 톤 — 조작적 정의

**"활기 있되 캐주얼하지 않게."** 2026-08-09 재영님이 [animate.html](animate.html) 계측 후 확정.

기존 계약은 `PressableScale.tsx:25`에 "차분한 포커스 앱 — 통통 튀는 연출은 일부러 피했다"로 박혀 있었다. **이 주석은 폐기한다.** 근거는 [정책 D2](policy.md#d2)에 있다.

### 4.1 확정값 — 버튼 복귀 스프링

안착은 **이동량의 2% 허용대** 기준이다(허용대를 마지막으로 벗어난 시각). 허용대를 안 밝힌 안착 수치는 의미가 없다 — 5%면 208/242ms, 1%면 273/402ms로 달라진다.

| | damping | stiffness | mass | scaleTo | ζ | 오버슛(이동량 대비) | **최대 배율** | **안착(2%)** |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 현행 | 18 | 320 | 0.6 | 0.97 | 0.650 | 6.8% | 1.0019 | ≈254ms |
| **확정** | **14** | **300** | **0.65** | **0.96** | **0.501** | **16.2%** | **1.0063** | **≈367ms** |

> ⚠️ **"오버슛 %"는 이동량 대비 초과분**이라 직관과 어긋난다 — 확정값은 이동량의 16.2%를 넘지만 이동량 자체가 0.04라 화면에 나타나는 배율은 1.0063에 그친다. 기존 주석의 "오버슛 거의 없음"도 사실이 아니었다(현행도 6.8% 넘는다). 근거·정정 이력은 [정책 D2](policy.md#d2).

### 4.2 등급표

| 등급 | 무엇 | 허용 커브 | 오버슛 |
| --- | --- | --- | --- |
| **0** 무모션 | 정보 전달만 하는 표면 | — | — |
| **1** 전환 | 시트·드로어·토스트·스켈레톤·진행바 | `standard` · `out` | **금지** |
| **2** 진입 | 카드·리스트·차트 등장 | `standard` · `glide` | 얕게 허용 |
| **3** 축하 | 목표 달성 · 승급 · 장착 · 챌린지 결과 | `overshoot` · `spring.bouncy` | 적극 허용 |

**공통 상한** — 무한 루프 애니메이션은 화면당 1개 이하 · stagger 총합은 6단계까지 · **버튼 오버슛은 1회, 이동량의 16% 이내**.

> ⚠️ **버튼 상한은 배율이 아니라 비율로 건다.** 최대 배율은 `scaleTo`에 비례하기 때문이다 — 기본 0.96이면 1.006이지만 작은 아이콘 버튼(`scaleTo 0.90`)은 **1.016**까지 튄다. `scaleTo`를 0.90보다 깊게 주지 않는 것이 실질적인 상한이다.

## 6. 저사양 기기 성능 허용선

**이 절은 합격/불합격 기준이다.** 아래를 넘기면 그 연출은 톤이 좋든 말든 **뺀다.** 모션은 앱을 좋아 보이게 하려는 것이지 느려 보이게 하려는 것이 아니다.

### 6.1 기준 기기

| 축 | 기준 |
| --- | --- |
| iOS | **최소 지원 iOS 16.4**가 도는 최하위 기기 (iPhone SE 2세대 / iPhone 8 급). 시뮬레이터 측정은 **인정하지 않는다** — 맥의 성능을 빌린다 |
| Android | 보급형 실기기 1대(RAM 4GB급). 기종은 팀 보유분으로 확정한다 |

> 기준 기기 실물이 없으면 **성능 항목은 미검증으로 남기고 PR 설명에 명시**한다. "아마 괜찮을 것"으로 통과시키지 않는다.

### 6.2 허용선

| # | 항목 | 허용선 | 측정 |
| --- | --- | --- | --- |
| P1 | 진입·전환 연출 중 프레임 | **33ms(2프레임) 초과 프레임 0회.** 즉 눈에 띄는 끊김 없음 | Perf Monitor / Instruments Core Animation |
| P2 | 스켈레톤 동시 표시(통계 8~12개) | **60fps 유지** | 네트워크 스로틀링 후 통계 탭 진입 |
| P3 | 컨페티 재생 중 | **45fps 이상** (전체화면 축하는 예외적으로 완화 — 조작이 없는 구간이므로) | 승급·목표 달성 재생 |
| P4 | 시트 등장 첫 프레임까지 | **100ms 이내** (탭 → 패널이 움직이기 시작) | 화면 녹화 프레임 카운트 |
| P5 | JS 스레드 구동 애니메이션 | **화면당 3개 이하** (`AnimatedNumber` 등) | 코드 리뷰 |
| P6 | 무한 루프 애니메이션 | **화면당 1개 이하**, 데이터 도착 시 언마운트 | 코드 리뷰 |
| P7 | 콜드스타트 → 홈 조작 가능 시점 | **진입 연출이 이 시점을 늦추지 않는다.** stagger는 렌더 후 얹히는 층이지 게이트가 아니다 | 앱 실행 → 첫 탭 반응 |
| P8 | 집중 세션 시작 지연 | **0ms 추가.** 시트 퇴장 애니메이션이 세션 시작을 늦추면 안 된다 ([LLD §4.3](low-level-design.md)) | 코드 리뷰 + 실기기 |
| P9 | 메모리 | 축하 연출 후 **누수 없음** — 컨페티·스켈레톤 노드가 언마운트로 회수 | Instruments Allocations |

### 6.3 미달 시 처리 순서

허용선을 넘으면 **아래 순서로 낮춘다. 순서를 건너뛰지 않는다.**

1. **강도 등급을 낮춘다** — 등급 2 진입 연출 → 등급 1 단순 페이드
2. **duration을 한 칸 줄인다** — `entrance 800` → `base 350`
3. **동시 실행 수를 줄인다** — stagger 상한 6 → 3, 스켈레톤 개수 축소
4. **그 화면에서 연출을 뺀다** — 그리고 [정책](policy.md)에 예외로 기록한다

**4번까지 갔다면 그것은 실패가 아니라 결정이다.** 기록하고 넘어간다.

### 6.4 이 허용선이 특히 위험한 지점

| 지점 | 왜 |
| --- | --- |
| 통계 화면 | 스켈레톤 8~12개 + 차트 6종 진입이 겹친다. **P2·P1이 동시에 걸린다** |
| 그룹방 | **개수가 서버 데이터에 달린 유일한 화면.** 스켈레톤 묶음(`GroupRoomScreen.tsx:853-881`)이 걷힌 자리에 챌린지 카드 M개와 멤버 타일 N개가 **한 스크롤 안에서 함께** 뜬다. 정원(`maxMembers`)이 크면 타일이 그만큼 늘고, 각 타일은 `CharacterImage`를 하나씩 안고 있다. **P1** (⚠️ **P2는 아니다** — P2는 위 통계 행처럼 **스켈레톤 8~12개**를 60fps로 그리는 기준인데, 그룹방 스켈레톤은 `SkeletonGroup` 한 묶음(고정 6블록)이고 데이터가 오면 타일이 나타나기 **전에** 언마운트된다. 정원이 커져도 늘어나는 것은 **콘텐츠 단계의 타일 수와 P1 비용**이지 스켈레톤 개수가 아니다 — 2026-08-12 codex 리뷰) (⚠️ **P5는 아니다** — 그룹방 신규 연출은 Reanimated CSS 기반 `enterUp`·`fadeIn`이라 UI 스레드에서 돌고, `CharacterImage`도 정적 RN `Image`다(`:75-86`). JS 스레드 애니메이션 개수 제한인 P5는 `AnimatedNumber` 같은 것을 겨냥하는데 [D25-1](policy.md#d25)이 그룹방에 그걸 붙이지 않기로 확정했다. 타일이 많아도 P5는 걸리지 않는다) |
| 승급 축하 | 컨페티 44조각 × 물리 + 모달 + 카운트업. **P3·P9** |
| 홈 | 하루 10회+ 진입. 여기서 33ms 드랍은 "가끔"이 아니라 "항상"으로 체감된다. **P1·P7** |

> ⚠️ **집중 세션 행은 GROMO-1525에서 지웠다.** 원래 *"진행 링이 초당 갱신되며 타이머·차폐 로직과
> 같은 스레드를 쓴다"*라고 적혀 있었는데 **두 가지가 틀렸다**: ① 링 갱신은 `useAnimatedProps`
> 워클릿이라 **UI 스레드**였고 타이머·차폐는 JS 스레드라 애초에 같은 스레드가 아니었다,
> ② "연속"은 무한 루프가 아니라 `setInterval(…, 1000)` 틱마다 `M.dur.base`(350ms) tween을
> 새로 거는 것이라 듀티가 약 35%였다. 링 자체도 1525에서 제거됐다. 이 화면에서 실제로 100%
> 무한 루프인 것은 **캐릭터 호흡**이며, 그건 이번 범위 밖으로 유지한다.
