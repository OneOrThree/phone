# BFF 요구사항

앱은 화면에 들어올 때 business-api를 한 번 호출해 그 화면의 조회 재료를 받는다. 서버가 같은 시점의 상태를 묶어 주므로 앱이 세션·섬·잔액을 따로 읽다가 서로 다른 상태를 조합하지 않는다. 구매·건설·가입·전송·종료는 사용자의 별도 행동이며 조회에 섞지 않는다.

| 구현 | 화면 |
| --- | --- |
|1785|home,travel,focus,sound,rest|
|1786|hall,island-manage,board,tower|
|1787|explore,visit,shop,boat|

13개는 원본 화면의 진입 GET들을 묶은 새 계약이다. 기존 도메인 API는 행동·상세·다음 페이지·재연결 복구에 계속 쓴다. 화면당1회는 진입/조건 변경의 한 조회를 뜻하며 모든 사용자 행동을 영구히 한 endpoint로 몰아넣는 규칙이 아니다.

초기 구현은 같은 Data DB의 적용 가능한 재료를 **필수 묶음**으로 읽는다. 독립적인 일시 장애 선택 조각을 억지로 만들지 않는다. 일반 주민에게 방장 신청 목록이 적용되지 않거나 방송기가 없어 여행 음악이 적용되지 않는 경우에는 검증 후 그 조회를 생략하고 명시된 상태와null을 반환한다. 실제403이나 계약 오류는 화면 전체 실패다.

수용 조건:

- 13개 경로와 필수 조각·비적용 조건·JSON DTO가 표와 일치한다.
- 현재 사용자/세션/섬·권한과 화면 재료를 같은 Data read snapshot에서 검증한다. Business의 여러HTTP 호출이 하나의DB snapshot이라는 가정을 하지 않는다.
- 서로 다른 자원의 version과 목록 cursor를 보존한다. 집중 주민은 개인 외양 정본의 appearanceVersion도 제공하며 늦은 사건/응답으로 표시 외양을 되감지 않는다. BFF snapshot을 받은 직후 같은 세션·멤버 조회를 다시 반복하지 않는다.
- 화면GET가 돈·상태전이·명령 receipt·도메인 outbox를 생성하지 않는다. 기존 보상 재지급0이다.
- 외부 TTL0/no-store, 현재 인가 재검사, 로그의 민감 값 제외를 적용한다.

정책 미결은 권한 기본값이나0원/0초/빈목록으로 덮지 않는다. 현재 섬 복구, 초기 건설, 집중 정산, 측정 병합, 랭킹 분모/동점, 미완성 도메인 DTO가 필요한 화면은 policy.md의 활성화 조건을 충족할 때 연다. 기술 문서가 준비되었다는 이유로1785~1787 구현 완료라고 표시하지 않는다.

목록 수용 조건: `/me/islands` 재료는 소속 전량과 nextCursor=null을 유지하고 임의 첫30개로 자르지 않는다.
host 신청 목록은 PR741의 명시 cursor 확장을 따라31번째 이후도 원 도메인 GET으로 이어진다.
비페이지 완전 목록이 예산을 넘으면 화면 전체가 실패하며 잘린 목록을 성공으로 반환하지 않는다.
새로운 소속/신청 상한이나 cursor 계약을 이 문서에서 만들지 않는다. 근거는 [LLD §1](low-level-design.md)이다.
