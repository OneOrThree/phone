# 링크·어트리뷰션 요구사항

## 문제

- 릴스·블로그·광고로 사람을 데려와도 **"어느 게시물·어느 광고로 몇 명이 깔고 가입했나"를 우리 데이터로 답하지 못한다.** 클릭 → 설치 → 가입 추적은 초대 링크에만 있고(V21 `group_invite_links`·`invite_link_clicks`), 그룹 없는 링크는 만들 수 없다.
- 유료 MMP SDK(AppsFlyer·Adjust·Tenjin)는 비용 때문에 쓰지 않는다. 티켓 876(Tenjin)은 코드 없이 닫혀 있다.
- 광고 앱 설치는 광고 → 스토어 직행이라 우리 랜딩을 거치지 않는다. iOS 는 기기 단위 추적이 정책상 막혀 있다.

## 목표

1. 팀원이 콘솔에서 캠페인과 캠페인 링크를 만들고, 캠페인별 설치·가입 수를 본다.
2. **광고 플랫폼이 이미 주는 숫자(광고비·노출·클릭·CPI)는 만들지 않는다.** Meta·Google 대시보드에서 본다.
3. 플랫폼이 못 주는 것(가입, 오가닉 링크 퍼널)과 대조용 원본(Apple 포스트백 복사본)만 우리가 센다.
4. 기존 초대 링크는 앱 업데이트 없이 그대로 동작한다.

## 사용자

| 사용자 | 하는 일 |
| --- | --- |
| 팀원 2~4명 | 콘솔에서 캠페인·링크를 만들고 수치를 본다 |
| 앱 사용자 | 링크를 누르고 설치·가입한다. 캠페인 링크는 설치 뒤 지정된 앱 화면으로 간다. 그 밖의 화면 변화는 없다 |

## 범위

| 경로 | 설치 신호 | 가입 연결 | 단위 |
| --- | --- | --- | --- |
| 초대 링크 | fingerprint 매치 (현행) | claim | 기기·유저 (확률) |
| 캠페인 링크 — 오가닉 | iOS 는 fingerprint, Android 는 랜딩이 Play 스토어 URL 에 심은 referrer (없으면 fingerprint) | claim | 기기·유저 |
| 캠페인 — Android 광고 | Install Referrer. Meta 는 복호화로 캠페인까지, Google 은 채널까지 | claim | 기기·유저 |
| 캠페인 — iOS 광고 | SKAN 포스트백 복사본 | 전환값 집계 | 집계. 기본 채널 단위, 네트워크가 대응을 주면 캠페인 단위 |

**범위 밖**: 광고비 입력·CPI 계산 · ROAS·LTV · 광고 플랫폼 API 연동(Google Ads API·Meta Marketing API) · iOS 광고의 유저 단위 귀속 · 알림 콘솔(같은 콘솔에 나중에 붙는다) · 콘솔 2차 비밀번호 · 유료 MMP SDK.

## 요구사항

| ID | 요구 |
| --- | --- |
| R1 | 캠페인: 이름 · 채널(ORGANIC · META · GOOGLE) · 플랫폼(IOS · ANDROID · ALL) · 보관 |
| R2 | 캠페인 링크: slug 발급, 앱 안 목적지(허용 목록에서 선택), 폐기. Android 는 referrer 가 심긴 Play 스토어 URL 을 함께 보여준다. 앱이 이미 깔린 사용자가 링크를 열면 목적지로 바로 간다 |
| R3 | 초대 링크: 현행 URL·slug·발급·claim 계약 유지 |
| R4 | 설치 신호 수신: fingerprint 매치(`/l/match`), Install Referrer(첫 실행에 앱이 로컬 판별, 세션 확보 뒤 `/l/referrer` 저장), SKAN 포스트백 |
| R5 | 가입 연결: 가입·로그인 직후 claim 한 번(slug 또는 referrer 저장 때 받은 식별자). 가입 수에는 신규 유저만 센다 |
| R6 | 콘솔: 로그인 · 캠페인 목록(기간별 설치·가입) · 캠페인 상세(링크 표·발급·폐기·링크별 수치) · 수치마다 신뢰도 표시 |
| R7 | 개인정보: 원본 IP 미저장(현행, 레이트리밋 키 포함), 탈퇴 시 유저 연결 파기 |
| R8 | data-api 는 링크 경로도 공인으로 열지 않는다 |

## 수용 조건

- 기존 초대 링크 `https://link.oneorthree.world/l/{slug}?g=` 가 앱 업데이트 없이 랜딩 · 매치 · claim 까지 동작한다. slug·클릭 이력은 이관 없이 그대로다.
- 캠페인 링크 클릭 → 설치 → 가입이 콘솔 캠페인 상세의 그 링크 행에 반영된다(iOS·Android 각각).
- 앱이 설치된 사용자가 캠페인 링크를 누르면 앱이 그 목적지로 바로 간다(Android 는 App Link 자동 검증 `autoVerify` 가 켜진 앱에서).
- Android 에서 앱을 지웠다가 다른 링크·광고로 다시 설치하면(백업으로 앱 데이터가 복원돼도) referrer·fingerprint 모두 새 설치로 처리한다. 설치 수는 첫 실행 날이 아니라 설치 날에, 가입 수는 claim 날이 아니라 가입 날에 들어간다.
- 광고로 설치한 뒤 **기존 계정으로 로그인**한 사용자는 설치 수에는 들어가고 가입 수에는 들어가지 않는다. Play 가 설치 시각을 주지 않은 설치로 새로 가입한 사용자도 가입 직후(기본 10분 안) referrer 가 저장되면 가입 수에 들어간다. 저장이 그보다 늦으면(오프라인·다음 실행 재시도) 놓칠 수 있다(정책 L22).
- 한 사용자가 여러 링크·광고 귀속을 claim 해도 **가입 수는 1건**이다. 첫 실행에 referrer 를 못 읽어 링크 매치로 먼저 가입이 기록되고 다음 실행에 같은 설치의 referrer 가 들어와도 가입 수는 1건이다.
- 콘솔에서 입력한 Meta 캠페인 ID·SKAN 캠페인 번호는 바꿀 수 없어, 과거 캠페인 수치가 소급해서 바뀌지 않는다. 캠페인을 보관한 뒤 링크 claim 이 성공하는 일은 없다.
- 초대 링크 발급자가 그룹을 나가는 순간과 수신자의 claim 이 겹쳐도, 나간 뒤에 기록되는 claim 은 없다(contract 단계부터).
- 콘솔 비밀번호를 바꾸면 이전에 로그인한 콘솔 쿠키는 바로 무효가 된다.
- 카카오톡·Slack 같은 **링크 미리보기 봇**의 방문은 클릭 수에 들어가지 않는다.
- 같은 IP 에서 랜딩을 반복해 열어도(중간에 매치를 끼워 넣어도) 클릭 행이 한도 넘게 쌓이지 않는다. 같은 와이파이의 여러 사람(같은 IP·OS)은 매치 창 안에서 20명까지 각자 클릭으로 남는다.
- iOS 캠페인 링크로 들어온 Android 설치(또는 그 반대)는 그 캠페인 수치에 섞이지 않고 채널 합계에 보인다. iOS 캠페인에서는 Play 스토어 URL 이 발급되지 않는다.
- 토큰 없는 `/l/referrer` 요청은 저장되지 않고, 한 유저가 KST 하루에 저장할 수 있는 referrer 는 동시에 보내도 3건이다.
- 발급자가 그룹을 나간 초대 링크는 contract 단계부터 쓸 수 없고, 재가입해 다시 발급하면 새 slug 가 나온다. 그 전 단계는 현행과 같다.
- Meta Android 광고 설치의 referrer 가 복호화되어 캠페인에 귀속된다. 복호화 실패는 원문 보존 + 채널 META + 캠페인 미귀속으로 남는다.
- Google Android 광고의 설치와 신규 가입은 채널 GOOGLE 합계로 집계되고, 콘솔에 그렇게 표기된다.
- 콘솔에서 복사한 Play 스토어 URL 로 설치해도 그 캠페인 링크에 귀속된다.
- SKAN 포스트백은 서명 검증을 통과한 우리 앱의 것만 원문과 함께 저장한다. 같은 포스트백 재전송은 1건으로 남는다. 서명 실패·다른 앱 포스트백은 저장하지 않고 건수만 센다. 캠페인이 커져도 정상 포스트백을 발신 IP 단위로 잘라내지 않는다.
- 콘솔 수치 옆에 신뢰도(확률 · 결정 · 집계·지연)가 보인다.
- `/l/match`·`/l/referrer` 는 매치가 없으면 200 `{matched:false}` 이고, 서버 일시 장애면 503 이라 앱이 다음 실행에 다시 묻는다.
- contract 전의 배포 단계는 모두 이전 이미지로 되돌릴 수 있다. 마지막 contract 단계는 roll-forward 전용이고, 직전 RDS 스냅샷을 최후 복구 수단으로 둔다.
- nginx 에 data-api 로 가는 링크 경로가 0개다.
- 탈퇴한 유저의 `claimed_user_id` 가 클릭·referrer 행에서 NULL 이 된다.
- 개인정보처리방침에 IP 해시·기기 식별자·Install Referrer 수집이 적혀 있다(출시 조건).
