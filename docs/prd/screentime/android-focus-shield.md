# 안드로이드 집중 실드 — 설계 (GROMO-996)

집중 세션 중 허용앱 외의 앱을 막는 기능의 안드로이드 구현. 2026-08-18 작성.

iOS 대응물은 `ManagedSettingsStore.shield`(OS 위임)이고, 그 UI는
`app/ios/ShieldConfiguration/ShieldConfigurationExtension.swift` 가 그린다.

## 1. 왜 iOS와 구조가 다른가

iOS는 **OS에 차단을 위임**한다. 앱이 죽어도 OS가 계속 막아준다.
안드로이드에는 대응 API가 없다. 서드파티 앱이 다른 앱을 막을 공개 수단은 둘뿐이다.

| | 접근성 서비스 | **UsageStats 폴링 + 오버레이 (채택)** |
| --- | --- | --- |
| 차단 지연 | 0초(이벤트 기반) | **최대 ~1초**(폴링 주기) |
| 배터리 | 유리 | 1초 주기 깨우기 |
| Play 심사 | **거절·삭제 위험 큼** — 장애인 지원 외 용도를 엄격 심사 | 표준 권한 조합, 국내 집중 앱 다수가 쓰는 방식 |
| 필요 권한 | 접근성 서비스 | 사용 정보 접근(이미 있음) + 다른 앱 위에 표시 |

**채택: 폴링 + 오버레이.** 신규 앱이 접근성 API 심사를 통과하지 못하면 기능이 아니라 **앱 자체가**
막힌다. 1초 지연은 감수 가능한 비용이다.

## 2. 구성 요소

```
FocusSessionScreen (RN)
  └ startFocusShield(subjectName) ──▶ ScreenTimeModule.kt
                                        └ startForegroundService
                                            └ FocusShieldService  ← 1초 폴링
                                                 ├ UsageStatsManager.queryEvents → 앞 앱
                                                 └ ShieldOverlay (TYPE_APPLICATION_OVERLAY)
```

| 파일 | 역할 |
| --- | --- |
| `FocusShieldService.kt` | 포그라운드 서비스. 앞 앱 폴링 → 차단 판정 → 가림막 표시/해제 |
| `ShieldOverlay.kt` | 가림막 창. iOS 실드와 같은 문구·색 |
| `ScreenTimeModule.kt` | JS 계약(`startFocusShield`/`stopFocusShield`/권한 조회·요청) |

### 왜 Activity가 아니라 오버레이 창인가
백그라운드 Activity 시작은 Android 10+에서 막혀 있고 예외 조건이 기기마다 다르게 동작한다.
`TYPE_APPLICATION_OVERLAY` 창은 '다른 앱 위에 표시' 권한만 있으면 제약 없이 올라가 예측 가능하다.

### 앞 앱 판정
`queryUsageStats`의 `lastTimeUsed` 최댓값을 쓰는 흔한 방법은 버킷 경계가 흔들려 방금 닫은 앱을
앞 앱으로 잘못 짚는다. **`ACTIVITY_RESUMED` 이벤트 중 가장 최근 것**을 쓴다.

### 차단 대상
런처에서 열 수 있는 앱 중 (우리 앱 ∪ 허용앱)을 뺀 나머지.
런처·시스템 UI를 덮지 않는 게 중요하다 — 홈 화면을 덮으면 기기를 아예 못 쓰고 빠져나갈 길도 막힌다.

### 상시 알림 = iOS Live Activity 자리

포그라운드 서비스는 알림을 없앨 수 없다(없애면 시스템이 서비스를 죽인다). 그 **강제된 알림을
iOS Live Activity가 하던 일에 쓴다** — 집중 중 과목·경과 시간·다른 과목 누적을 보여주는 자리다.
정본은 `ios/Widget/WidgetLiveActivity.swift`이고, 아래 표대로 옮겼다.

| iOS 잠금화면 배너 | 안드로이드 확장 알림 |
| --- | --- |
| `CharacterView(maxWidth 64, maxHeight 96)` | `ImageView 64×96dp` + `fitCenter` |
| `subjectName` · headline.bold · ink | 17sp bold · `?attr/textColorPrimary` |
| "집중하는 중이에요!" · footnote · inkSub | 13sp · `?attr/textColorSecondary` |
| `ElapsedTimerText` (OS 자체 갱신) | `Chronometer` (시스템이 초당 갱신) |
| 다른 과목 칩 최대 2개 · 색점 + `hh:mm:ss` | `notif_row0/1` · 같은 구성 |

세 형태를 각각 만든다.

| 형태 | 무엇 | 보는 법 |
| --- | --- | --- |
| **확장** | 위 표 전부 (칩 포함) | 알림 우측 `∨` 탭 · 아래로 끌기 · 핀치 아웃. 맨 위 알림은 자동으로 펼쳐진다 |
| **일반** | 캐릭터 + 과목 + 타이머 (칩 없음) | 알림창을 내리면 기본으로 보이는 형태 |
| **축소** | 상태바 별 아이콘만 | 알림창을 안 내렸을 때 |

**`setColorized(true)`를 쓰지 않는다.** 알림 전체를 인디고로 칠하면 눈에는 띄지만 **iOS와
반대**가 된다 — iOS는 GROMO-868에서 잠금화면 배너를 앱과 같은 라이트 톤(paper)으로 정했다
(`activityBackgroundTint(laBg)`). 안드로이드 알림 배경은 시스템 소유라 흰색을 강제할 수 없으니,
통짜로 칠하는 대신 **배경은 시스템에 맡기고 포인트색은 칩·상태바 아이콘 틴트로만** 쓴다.
결과적으로 양쪽 다 '앱 톤 위에 인디고 포인트'가 된다.

**커스텀 뷰(`DecoratedCustomViewStyle`)를 쓰는 이유.** 기본 템플릿은 제목·본문 텍스트뿐이라
캐릭터 비율 유지와 색점 달린 과목 칩을 표현할 수 없다. `BigTextStyle`로 흉내 내면
`자료해석   0분` 같은 나열이 되어 같은 제품으로 읽히지 않는다. Android 12+는 완전 커스텀
알림을 허용하지 않으므로 시스템이 헤더를 그리는 `DecoratedCustomViewStyle`이 정공법이다.

**색을 하드코딩하지 않는다.** 알림은 시스템 테마 위에 그려지고 다크 모드에서 배경이 뒤집힌다.
`ink(#1C1E22)`를 박으면 다크에서 글자가 사라지므로 `?android:attr/textColorPrimary`·
`textColorSecondary`를 쓴다. 칩만 포인트색 저알파(`#1F5E6AD2`)라 양쪽 테마에서 다 보인다.

**캐릭터 비트맵은 두 번 손본다.** ① 캡처본의 투명 여백을 잘라 실제 비율을 되찾고(iOS의
`trimmingTransparentEdges`와 같은 이유 — 안 자르면 정해진 박스 안에서 캐릭터만 쪼그라든다),
② 긴 변 192px로 줄인다. RemoteViews 비트맵은 **Binder 트랜잭션(≈1MB)에 실려 가므로** 캡처
원본을 그대로 넣으면 알림이 조용히 안 뜬다.

**결정 — 누적 0인 과목도 그대로 보여준다(D2).** iOS가 오늘 0초인 과목을 `00:00:00`으로
표시하므로 안드로이드도 같게 둔다. 빈 줄처럼 보이지만 **플랫폼 간 표시가 갈리는 쪽이 더 나쁘다** —
같은 계정을 두 기기에서 쓰면 한쪽에만 과목이 사라져 데이터가 틀린 것처럼 보인다.
바꾸려면 `WidgetLiveActivity.swift`와 `FocusShieldService.kt`를 **함께** 고친다.

## 3. 이탈 정책과의 관계 (중요)

`startFocusShield()`의 반환값은 단순한 성공 신호가 아니라 **이탈 정책의 입력**이다.

- `true` → 차단이 걸렸으니 앱을 벗어난 시간도 집중으로 인정(`AWAY_CREDIT_CAP_S` 상한)
- `false` → 15초 정책(`LEAVE_END_S`)으로 빡빡해짐

그래서 **차단이 실제로 안 걸리는 상황(오버레이 권한 없음)에서 true를 돌려주면 부정 사용이 열린다.**
네이티브는 권한을 확인한 뒤에만 true를 반환한다.

## 4. 한계 (정직하게)

| 한계 | 내용 | 대응 |
| --- | --- | --- |
| **~1초 노출** | 차단 앱을 연 직후 폴링 주기만큼 보인다 | 감수. iOS는 0초 |
| **강제 종료 불가** | 남의 앱을 죽일 수 없다 | 가림막을 덮고 우리 앱으로 유도. 버튼 라벨도 iOS의 '닫기'가 아닌 'gromo로 돌아가기' |
| **설정 앱은 못 덮는다** | 안드로이드가 탭재킹 방지로 설정 화면 위 오버레이를 숨긴다 | **감수한다(D1)** — 아래 결정 참고 |
| **제조사 배터리 최적화** | 삼성 등이 포그라운드 서비스를 죽일 수 있다 | 실기기 검증 필요 — 미완 |
| **권한 의존** | '다른 앱 위에 표시'가 꺼지면 차단 불가 | 허용앱 화면에서 상태 표시 + 설정 이동 제공 |

### 결정 D1 — 설정 앱 구멍은 감수한다 (2026-08-18)

시스템 설정 화면 위에는 오버레이를 올릴 수 없다. 안드로이드가 **탭재킹**(권한 화면을 가짜
화면으로 덮어 사용자를 속이는 공격) 방지로 막아 둔 것이라, 우회 수단이 없고 **우회하는 앱이
곧 악성 앱**이다. 즉 사용자가 「설정」으로 들어가면 차단이 뚫린다.

**셋 중 감수를 택했다.**

| 안 | 왜 아닌가 |
| --- | --- |
| 화면에 고지한다 | 우회법을 알려주는 셈이다. 집중을 도우려는 기능이 탈출구 안내가 된다 |
| 설정 진입을 감지해 세션 이탈 처리 | 오탐이 크다 — 알림 권한·와이파이 등 **정당한 이유로 설정에 갈 때도 집중이 깨진다** |
| **감수한다 (채택)** | 실드는 '못 열게 막는 장치'가 아니라 '무심코 열었을 때 되돌리는 장치'다. 작정하고 빠져나가는 사용자를 막는 건 원래 이 기능의 목표가 아니다 |

**전제**: 우리 사용자는 스스로 집중하려고 이 기능을 켠 사람이다. 작정한 우회를 막는 건
불가능하고(앱 삭제·기기 재부팅도 있다), 막으려 들수록 정상 사용을 해친다.

**다시 논의해야 할 때**: 챌린지·내기처럼 **금전이 걸린 판정**에 실드 결과를 쓰기 시작하면
전제가 깨진다 — 그때는 우회 유인이 생기므로 이 결정을 재검토한다.

### 백그라운드 생존 (2026-08-18 추가 실측)

"앱을 벗어나도 차단이 유지되는가"를 단계별로 확인했다.

| 상황 | 차단 유지 | 비고 |
| --- | --- | --- |
| 앱을 홈으로 내림(백그라운드) | ✅ | 시계 앱 위에 가림막 유지 |
| `am kill` (메모리 회수 시뮬레이션) | ✅ | 포그라운드 서비스가 프로세스를 보호 — pid 그대로 |
| **강제 중지**(설정 > 앱 > 강제 중지) | ❌ | 프로세스·서비스·가림막 전부 사라지고, 이후 차단앱이 그냥 열린다 |

**이게 iOS와 갈리는 지점이다.** iOS는 OS가 차단을 들고 있어 앱을 죽여도 실드가 남지만,
안드로이드는 우리 프로세스가 곧 차단이다. 강제 중지는 사용자가 작정하고 하는 행동이라
'우회 경로'로 봐야 하며, **제조사 배터리 최적화가 같은 일을 사용자 의도 없이 할 수 있다**는 게
진짜 위험이다(→ GROMO-1603 실기기 검증).

**미검증**: 실기기(특히 삼성) 배터리 최적화 하 장시간 세션, 화면 꺼짐 후 복귀, 분할 화면.
