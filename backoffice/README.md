# 콘텐츠 백오피스

FCM 서비스 공지, 앱 내 개발자 공지, 잡지를 작성 → 검토 요청 → 승인 → 발송·게시하는 독립 웹이다. 브라우저에 내부 서비스 토큰을 보내지 않는다.

## 로컬 실행

Node 24 이상이 필요하다. 로컬 모드는 외부 서비스 호출 없이 영구 저장과 승인 절차를 검증한다. 잡지의 섬·랭킹 데이터는 비어 있고 실제 잡지의 미리보기가 아니다.

```sh
npm ci
npm run build
npm start
```

http://127.0.0.1:4310 에서 `test` / `test`로 로그인한다. 로컬 모드는 루프백 주소에서만 실행되고 실제 서비스에 발송·게시하지 않는다. 연결 모드는 `member-1`~`member-3` 계정과 별도의 비밀번호 해시를 요구한다. 연결 모드의 비밀번호 해시는 12자 이상 비밀번호를 `npm run --silent password` 명령의 표준 입력에 전달해 생성한다. 원문 비밀번호나 서비스 토큰을 git에 기록하지 않는다.

Vite 개발 화면을 쓸 때에는 BFF의 `BACKOFFICE_ORIGIN=http://127.0.0.1:5173`을 설정하고 `npm run dev`를 별도 실행한다. 기본 빌드 화면은 4310 포트 하나에서 제공한다.

## 서비스 연결

| 설정 | 의미 |
| --- | --- |
| `BACKOFFICE_MODE=connected` | 내부 API 연결 활성화. 기본 local |
| `BACKOFFICE_ENV=dev` 또는 `prod` | 연결 모드 필수. 검토 저장 파일과 Data·Notification 연결 환경을 고정 |
| `BACKOFFICE_FCM_PROJECT_ID` | 연결 모드 필수. 해당 환경 앱의 FCM 프로젝트와 실제 Notification 설정을 대조 |
| `BACKOFFICE_ORIGIN` | 실제 HTTPS 출처. 경로 없는 `https://운영주소` |
| `BACKOFFICE_OPERATORS` | member-1~3별 `{passwordHash,notificationToken,dataToken}` JSON |
| `NOTIFICATION_URL` | 비공개 notification HTTP(S) 주소 |
| `DATA_API_URL` | 비공개 Data HTTP(S) 주소 |
| `BACKOFFICE_STATE_DIR` | SQLite 및 WAL 영구 저장 폴더. 기본 var |
| `BACKOFFICE_HOST`, `PORT` | 기본 127.0.0.1:4310. 연결 모드 컨테이너는 0.0.0.0 |

운영자별 notificationToken은 Notification의 member-1~3 admin token, dataToken은 Data의 `SVC_TOKEN_CONSOLE_MEMBER_1_TO_DATA`(2/3도 동일)와 맞춘다. member 번호와 토큰의 actor가 다르면 거부된다. 서비스 간 토큰을 공유하지 않는다. 비밀은 프로세스 환경/비밀 관리 시스템으로만 주입한다.

dev와 prod는 **별도 백오피스 인스턴스·HTTPS 주소·영구 볼륨·운영자 자격·Data/Notification 서비스와 DB**를 사용한다. 각 인스턴스에 맞는 `BACKOFFICE_ENV`와 앱 프로젝트의 `BACKOFFICE_FCM_PROJECT_ID`를 명시한다. 검토 데이터는 각각 `dev.sqlite`, `prod.sqlite`에 저장된다. 시작할 때와 미리보기·내부 조회·발행 요청 전에 인증된 서비스가 실제 연결한 DB의 환경 표식과 Notification의 실제 FCM 프로젝트를 대조한다. 표식이 없거나 불일치하면 연결·발행을 거부한다. 서비스는 환경 확인 API를 포함한 버전으로 먼저 교체해야 한다. 로컬 모드는 `local.sqlite`만 사용한다.

서비스 연결 전에 DB 소유자가 dev Data·Notification DB에는 `dev`, prod Data·Notification DB에는 `prod` 표식을 **각각 한 번** 설정한다. Notification DB에는 그 환경 앱의 FCM 프로젝트 ID도 독립적으로 기록한다. `<DB명>`은 실제로 접속할 데이터베이스 이름으로 바꾼다.

```sql
ALTER DATABASE <DATA_DB명> SET gromo.environment TO 'dev';
ALTER DATABASE <NOTIFICATION_DB명> SET gromo.environment TO 'dev';
ALTER DATABASE <NOTIFICATION_DB명> SET gromo.fcm_project_id TO '<dev 앱의 FCM 프로젝트 ID>';
-- 운영 DB에는 prod와 운영 앱의 FCM 프로젝트 ID를 사용한다.
```

이는 DB 자체의 설정이다. 서비스는 `pg_db_role_setting`에서 실제 연결한 DB의 표식과 Notification DB에 기록한 FCM 프로젝트 ID를 읽어 실행 프로파일·실제 전송 설정과 대조한다. `SET`으로 바뀐 세션 값은 표식 판정에 쓰지 않는다. Notification 발송 워커도 대기 중인 알림을 FCM으로 보내기 직전에 같은 검증을 수행한다. 프로파일 누락·환경 불일치 때 전송을 중단하고 60초 뒤 재시도하되 알림별 전송 실패 횟수는 소진하지 않는다. 표식 설정 후 두 서비스를 새 버전으로 교체하고, 각각의 환경 확인 API가 올바른 값을 반환하는지 운영자 자격으로 확인한 다음 백오피스를 시작한다. 이 저장소는 환경 표식이나 운영 자격을 자동으로 운영 DB에 쓰지 않는다.

HTTPS 역방향 프록시 뒤에 단일 인스턴스로 운영한다. 인터넷에 내부 `/internal/**` 경로를 개방하지 않는다. 백오피스 서버만 서비스망에 접속한다. SQLite 폴더는 전용 영구 볼륨으로 두고 일관된 SQLite 백업 방식으로 보존한다. 디스크·백업에는 검토 원문과 사용자 UUID가 있으므로 운영자만 접근할 수 있어야 한다. 로컬/연결 모드는 DB 파일이 분리되어 모의 게시를 운영 게시로 오해하지 않는다.

세션은 HttpOnly·SameSite=Strict·연결 모드 Secure 쿠키, 8시간 수명이다. 모든 변경 요청은 정확한 Origin과 CSRF 값을 확인한다. 서버 재시작은 세션을 종료하며, 진행 중인 발송은 결과 확인 필요 상태로 바꾼다. 같은 최초 발송자가 재시도하면 동일 publication UUID가 사용된다. 멀티 인스턴스 배포는 지원하지 않는다.

## 운영 절차

- 저장 후 검토 요청 → 승인 → 발송·게시 확인. 수정하면 승인은 취소되고 새 수정본이 된다. 승인자와 발송자, 시각은 감사 이력에 남는다. 같은 운영자가 검토·승인할 수 있다.
- FCM: `ADMIN_ANNOUNCEMENT` 전용, 명시적인 사용자 UUID 1~100명. 수신 동의·탈퇴·조용한 시간·dispatch gate를 따른다. 응답 `PENDING`은 접수이며 기기 수신 완료가 아니다. 게이트를 백오피스가 자동으로 켜지 않는다. 추가 payload는 문자열 JSON이고 실제 발송 크기는 Notification이 검증한다. 친구·섬 사건 알림 종류로 발송할 수 없다.
- 개발자 공지: 평문 제목·본문과 게시 시작/종료 시각을 지정한다. 앱 설정의 개발자 공지에서 현재 게시 기간에 해당하는 최신 100개를 읽는다. 전체 과거 공지 아카이브·페이지네이션은 제공하지 않는다. HTML을 렌더링하지 않는다. 게시 후 수정/철회는 이 버전에서 지원하지 않으며 게시 종료 시각으로 노출을 제한한다.
- 잡지: 날짜·편집부 소식(80자)을 작성한다. 최종 미리보기는 발행일 당일 KST 07시 이후에 당일 평균 집계를 마친 뒤 불러올 수 있다. 서버가 보관한 스냅샷을 검토·승인한다. 섬 홍보가 바뀌면 409로 재검토를 요구한다. 실제 앱과 같은 픽셀 배치를 보장하는 화면은 아니다. 당일 KST 07시 이후 게시할 수 있다. 미래 날짜에는 초안만 준비하며 당일 최종 미리보기를 다시 불러 검토·승인한다.
- 응답 유실 시 새 초안을 만들어 중복 발송하지 않는다. 결과 확인 필요 항목의 같은 요청을 재시도한다. 이전 응답 유실이 없는 최초 요청의 명확한 거부만 처리 실패로 남으며 내용을 수정해 다시 검토한다.

**잡지 운영 변경:** 기존 10분 주기 자동 호 생성은 제거된다. 운영자가 승인·게시해야 그날 호가 생긴다. 스케줄러는 하루 종일 10분마다 최근 7호 중 미처리·유효한 호의 알림을 재시도한다. 발행 다음날 07:00 KST 이후에는 새 알림을 만들지 않으며 기존 조용한 시간 정책도 유지한다. 서버 적용 전에 백오피스 운영자 자격과 매일 게시 담당자를 준비해야 한다.

## 결과 확인 필요 상태 복구

응답 유실 뒤 재시도에서 401·403·409가 와도 최초 요청의 반영 여부는 확인되지 않는다. 이 경우 수정 잠금을 유지한다. 운영 담당자는 항목의 publicationId·최초 발송자·감사 이력·오류 시각을 보존하고, 해당 운영자 계정과 서비스 토큰의 actor 매핑을 복구한 뒤 화면에서 같은 항목을 재시도한다. 서비스의 영구 처리 영수증이 같은 요청의 결과를 반환한다.

최초 운영자의 자격을 복구할 수 없거나 동일 요청이 계속 거절되면 서비스 운영 담당자가 해당 publicationId의 영수증과 실제 게시·발송 기록을 조회해 원인을 확인할 때까지 보류한다. SQLite의 상태·발송자·publicationId를 수동 변경하거나 새 초안으로 다시 발송하지 않는다. 현재 버전은 발송자 승계나 강제 잠금 해제를 지원하지 않는다.

Notification의 모든 인스턴스를 새 버전으로 교체한 다음 연결 모드의 발송 기능을 사용한다. 구버전 인스턴스가 고정 메시지를 다르게 처리하지 않도록 롤링 배포 도중에는 발송하지 않는다. 로그인 제한은 연결 소켓의 IP 기준이므로 역방향 프록시 뒤에서는 운영자들이 같은 제한을 공유할 수 있다. 전달 헤더를 임의로 신뢰해 이를 우회하지 않는다.

## 검증

`npm test`는 승인 우회·수정·중복·재시작 복구·스냅샷 검증·인증·CSRF·고정 상류 요청을 로컬에서 검사한다. `npm run build`는 TypeScript와 배포 번들을 검사한다. AWS 부하 테스트와 부하 데이터 생성은 영구 금지이며 이 도구의 검증에 사용하지 않는다.
