# 앱 API와 출시 검증 근거

앱이 요구하는 API의 **목록 → 서버 선언 대조 → 시나리오 등록 → 실제 실행 결과**를 구분한다.
목록 생성기는 네트워크 요청을 하지 않는다. 출시 검사는 별도의 버전 대조와 운영 핵심 검사를 수행한다.
[전체 단계와 활성화 절차](../../docs/engineering/app-release-safety.md)를 참고한다.

## 목록·커버리지 생성

```bash
npm ci --ignore-scripts --prefix smoke/contracts
node --test smoke/contracts/inventory.test.cjs
node smoke/contracts/report.cjs /tmp/phone-api-coverage
```

- `inventory.json`: HTTP 메서드·경로·호출 위치·서버 선언·등록 시나리오·입력 소스 해시.
- `coverage.md`: 사람이 읽는 커버리지 표. 미등록 API를 감추지 않는다.
- 실행 상태는 항상 `NOT_RUN`으로 시작한다. 등록된 테스트 코드가 있다는 이유로 PASS로 처리하지 않는다.
- PR의 Smoke Checks가 보고서를 `api-coverage` 산출물로 보관한다.
- 미해석 앱 호출·서버 매핑·미검토 직접 fetch·서버 경로 누락은 CI 실패다.
- API 목록은 TypeScript AST로 추출한다. 서버는 Spring 매핑 선언과 인증 경로 상수를 해석한다.
- 쿼리·본문·인증·응답 스키마의 호환성은 경로 대조에 포함하지 않는다.
- WebSocket·네이티브 SDK는 범위 밖이다. `external-fetches.json`은 검토한 외부 자산 fetch만 기록한다.

[현재 소스 기준 커버리지 스냅샷](coverage.md)은 검토용이다. 최신 결과는 위 명령이나 CI 산출물로 다시 생성한다.

## 사용자 흐름과 미검증 항목

`scenarios.json`은 사용자 흐름과 API·실행기·TC 번호의 연결이다. 첫 항해·게스트 시작·집중/보상 흐름부터
명시적으로 등록했다. 등록되지 않은 API도 보고서에 그대로 남는다. **전체 앱 시나리오 구현 완료를 뜻하지 않는다.**
새 API를 추가하면 목록이 자동으로 바뀐다. 해당 흐름의 정상·실패·권한·재시도 조건을 명세하고 테스트를
추가한 뒤 등록한다. 현재는 시나리오 미등록 자체를 출시 차단 조건으로 삼지 않는다.

## 첫 항해 dev 회귀 검사

`smoke/server/first-voyage.sh`의 `SMOKE-SERVER-019`는 다음을 확인한다.

1. 이번 실행에서 발급한 새 게스트가 섬에 소속되지 않은 상태인지 확인한다.
2. 망원경에서 무인도 후보를 조회한다.
3. `intro-arrivals`에 도착을 요청해 실제 섬 생성·active 소속·현재 섬을 확인한다.
4. 동일 멱등 키로 재요청해 같은 섬이 반환되고 소속이 하나만 생겼는지 확인한다.
5. 홈 필수 조각이 준비됐는지 확인한다.
6. 기존 run.sh 정리가 생성된 전용 섬의 소속을 해제한다. 영구 계정 삭제는 수행하지 않는다.

기존 main 게스트를 재사용하므로 전체 게스트 로그인 예산을 늘리지 않는다. dev V2의 기존 배포 잠금·
실제 SHA·image ID·digest 조회·검사 전후 버전 비교 안에서 실행한다. 운영 주소와 고정 기기 재사용은 거절한다.
`SMOKE_FIRST_VOYAGE_ENABLED=1`로 선택하며 dev V2 자동 smoke에서 활성화한다.
정리 대상 소속을 조회할 수 없는 실패는 수동 확인이 필요하다. 신규 게스트·명령 기록은 dev DB에 남는다.

첫 항해 후 집중·보상·건설은 기존 별도 TC014가 독립 fixture로 검사한다.
같은 신규 사용자가 모든 기능을 연속 통과하는 단일 E2E 테스트와는 구분한다.

## 소스·실행 결과 연결

dev V2는 전체 16개 TC 성공과 검사 전후 실제 이미지 일치를 확인한 뒤
`compatibility-dev.json`을 `smoke-results` 산출물에 저장한다.

- 앱 테스트 소스 커밋, API 입력 소스 해시
- 실제 네 서비스의 소스 SHA·image ID·digest 정보
- 통과한 TC와 결과 TSV 해시

이 파일은 **그 앱 소스·그 서버 이미지 조합의 등록 dev 시나리오 성공 근거**다.
공유 dev의 최신 성공만 보고 다른 운영 서버 버전의 출시를 승인하지 않는다.
서버 선언 대조는 checkout 소스 기준이며, 전체 경로가 실제 dev 이미지에서도 확인됐다는 의미가 아니다.
전체 API 응답 계약·모든 앱 기능·운영 호환성을 보증하지 않는다.

## 출시와 운영 감시

`release_check.py`는 특정 main dev 성공 실행의 앱 트리와 실제 운영 서비스 소스 트리를 대조한다.
`production.py`는 실행마다 임시 게스트·정원 1명 섬을 만들고 운영 조회와 intro 경로를 검사한다.
성공·실패와 관계없이 섬 폐쇄·계정 탈퇴를 확인하며 정리 실패도 출시를 차단한다.
실제 도착 쓰기는 dev에서 검사한다. 기존 출시 게이트에서 두 검사 실패를 차단한다.
Datadog 모니터 정의·검증·적용 실행기는 `server/observability/datadog/release-monitoring/`에 있다.

보호된 영속 정리 기록 경로·GitHub 실행 ID·새 배포 근거·Datadog 수신처·키가 필요하다. 코드 커밋과 실제 활성화는 별개다.
모든 API 시나리오·과거 모든 앱 버전의 계약 자동 검증은 아니다. 미등록 API는 커버리지 표에 계속 표시한다.
